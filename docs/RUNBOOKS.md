# Operator runbooks

Procedures below define administrative tooling and operational controls. Every business mutation runs through an authorized API/tool with audit; the K0.6 migration CLI is the only normal schema-change path. Direct ad hoc production SQL is a break-glass action.

## KB-00: Verify and apply a Keel release

Download the release archive, SPDX SBOM and `SHA256SUMS` from the Keel GitHub Release. Verify file checksums with `sha256sum -c SHA256SUMS`, then run `gh attestation verify keel-vX.Y.Z-linux-amd64.tar.gz --repo sanskarpan/Keel`. Extract the binary and verify its subject-bound SBOM attestation with `gh attestation verify keel-linux-amd64 --repo sanskarpan/Keel --predicate-type https://spdx.dev/Document/v2.3`. Reject artifacts with missing/invalid checksum or attestation; attestations identify the producing workflow/source but do not prove the release is safe or production-qualified. See [`RELEASES.md`](RELEASES.md) for the full release contract.

Before first use, provision a dedicated login that may `SET ROLE keel_schema_owner`, but is not a superuser, database owner, app, worker or agent login. Configure `KEEL_MIGRATION_DATABASE_URL` in a one-shot migration job secret store. Run the tagged binary's `migrate` command before compatible runtime rollout; never pass this DSN to product-facing workers or the model. The session advisory lock serializes concurrent migration jobs. The command creates `keel_meta.schema_migrations` if absent, verifies every recorded filename and SHA-256 against the binary, then commits one migration and its ledger row atomically.

If a migration fails, stop rollout and preserve logs/checksums. Its transaction is rolled back and the advisory lock is released when the process exits or its DB session is terminated. Transaction-control statements are rejected before execution so a migration cannot commit outside runner ownership. Fix the cause and retry only after confirming the same immutable file is still correct. Once a migration is applied, do not edit it or delete/alter ledger rows; publish a new forward repair. Online/nontransactional DDL is not supported by this runner. Roll application code back only when its schema compatibility allows it; otherwise deploy a forward-compatible repair.

## KB-01: Outbox lag or broker outage

Inspect broker health, outbox oldest age/bytes, publish-head leases and disk forecast. Confirm accepted commands remain durable. Reduce nonessential admissions before reaching the buffer cap. Restore broker/credentials/network and let normal relay retry with original event IDs. Repair a stranded lease only after its worker is terminated/expiry confirmed; never mark rows published to clear a graph. For a trace-metadata quarantine, compare only the schema version and redacted reason through the restricted diagnostic path; never copy raw envelope values into general logs or tickets. Confirm v2 envelope/header agreement in the canonical protected record before repairing source data. Verify contiguous projection versions, deduplication and declining backlog. Exit when age is normal and no gap/conflicting digest remains.

## KB-01A: Use order relay/projector telemetry

When a runtime explicitly wires the K5.3.4 logger observer, filter only on `operation` and the fixed `outcome` values (`published`, `retry_scheduled`, `blocked`, `no_work`, `applied`, `duplicate`, `deferred`, `quarantined`, `error`). Compare bounded `duration_ms`, `schema_version`, and relay-only `retry_count`; correlate with `trace_id` only when present. Schema-v1 traffic has no trace ID. These records contain no event or customer identifiers and cannot identify a single message. Use authorized operational dashboards and restricted canonical diagnostics for investigation; never add IDs or raw broker/database errors to these logs. The hooks are optional and do not represent exporter health or end-to-end tracing. If missing, confirm the runtime actually configured an observer before treating it as an incident; never enable an external endpoint as an ad hoc diagnostic.

## KB-01B: Use order repository telemetry

When a runtime explicitly wires the K5.3.5 observer on the order repository, filter only on `operation` and the fixed `outcome` values (`ok`, `not_found`, `error`). Operations are `order.create`, `order.submit`, `order.read`, `order.history`, `order.view`, `order.page`, `order.readpage`, `order.stream.snapshot`, `order.stream.updates`, `outbox.repair.list`, and `outbox.repair.apply`. Compare bounded `duration_ms` to separate slow database work from upstream request or broker time; correlate with `trace_id` only when present. Envelope `schema_version` and `retry_count` are messaging-only and never appear on these records. `not_found` is a normal read outcome, not a failure signal. These records contain no tenant, order, event, or aggregate identifiers, no SQL text, and no raw database errors, so they cannot identify a single order; use authorized operational dashboards and restricted canonical diagnostics for investigation. The observer is an optional constructor option, so absent records usually mean the runtime did not configure one; confirm configuration before treating a gap as an incident, and never add identifiers or enable an external endpoint as an ad hoc diagnostic.

## KB-01C: Use database statement telemetry

When a runtime explicitly wires the K5.3.6 observer, filter only on `operation` and the fixed `outcome` values (`ok`, `error`). Operations are `query.read` and `query.write`; `error` marks a statement that failed, while a statement that returned no row is reported as `ok`. Compare bounded `duration_ms` to separate database wait time from request and broker time, and count statement failures separately from the operation that raised them; correlate with `trace_id` only when present. Envelope `schema_version` and `retry_count` are messaging-only and never appear on these records. These records name no statement and contain no statement text, argument values, row contents, tenant, order, event, or aggregate identifiers, and no raw database errors, so they cannot identify a single statement; use authorized operational dashboards, query-plan review, and restricted canonical diagnostics for investigation. The observer is an optional constructor option, so absent records usually mean the runtime did not configure one; confirm configuration before treating a gap as an incident, and never add identifiers or enable an external endpoint as an ad hoc diagnostic.

## KB-02: Missing or duplicated order projection

Compare canonical order event versions/digests to applied projection watermark and inbox. Duplicates with identical IDs/digests are normal transport behavior. A digest mismatch is an incident: quarantine affected stream and preserve evidence. Run dry-run projection rebuild into an isolated table, compare state/hash, then authorized switch/repair. Suppress external effects during diagnostic replay. Exit when derived state matches authoritative history and delivery uniqueness remains unchanged.

## KB-03: Workflow stuck or approval near deadline

Inspect case deadline/evidence/policy, durable approval decisions and pending start/signal intents. Inspect Temporal history/activity retries and worker version/task queue. Never start a replacement workflow with a new ID simply because the UI looks stuck. Redeliver stable intent IDs; reload pre-deadline decision records before expiry. Quarantine conflicting evidence/policy and request a new approval. Exit when canonical case and workflow state agree with recorded decisions.

## KB-04: Provider failure or runaway spend

Disable affected provider/operation policy without deleting liabilities. Inspect per-attempt request IDs, quote/token bounds, reservations and confirmed/estimated/unknown usage. Stop new expensive admissions for the affected scope. Reconcile provider usage/invoice export before releasing uncertain reservations. Model retries after streamed content require explicit new bounded requests. Exit when spending is bounded and ledger/account totals reconcile; any unreconciled liability stays visible.

## KB-04A: Explain a tenant's AI cost

Read the tenant cost breakdown for the period under review, then read the bounded per-inference entries. Interpret the classes separately: confirmed is settled spend, estimated is the current expectation for unsettled attempts, unknown is exposure for attempts whose provider outcome is unknown, and outstanding is exposure for admitted attempts that never settled. An attempt with an estimate is both estimated and outstanding; that is expected, not a double charge. Compare the account's committed and reserved liability with the breakdown: a difference means the ledger and the account disagree, which is an incident to escalate rather than to adjust. Use the watermark to confirm the breakdown is current before reporting a number, and re-read after any reconciliation because the watermark moves. A missing period is reported as unavailable; confirm the period head and tenant authorization before investigating, and never query another tenant's period to "check" a value. Cost reads are tenant-scoped and content-free; they are not a billing statement, so do not present them as one. See `docs/K5.5-COST-DASHBOARD.md`.


## KB-04C: Read a tenant cost view

Use the tenant cost reads to explain a number: the period breakdown for the classes and the watermark, the entry rows for the per-inference detail. The tenant comes from the authenticated caller, never from a request value, and a 404 means either a denied view or an unknown period, so do not retry it against another tenant to find out which. Treat a 503 as unavailable rather than as an empty period, and never report zero cost from an error response. The entry page is bounded: raise the limit within its cap rather than expecting an export, and reconcile against the period summary rather than summing a page. The handler is not mounted by any runtime today, so a cost read that reaches production means an unmounted route was exposed; confirm the deployment and close it. See docs/K5.5-COST-API.md.


## KB-04B: Investigate a spend alert

Read the tenant cost breakdown for the period the alert names, then the bounded per-inference entries, before acting on any spend signal. A blocked limit alert means the account has stopped admission: confirm the period, the hard limit and the recorded liabilities, and stop or re-plan the spend rather than raising the limit to clear the alert. A limit or unknown-exposure warning means liability is close to the limit: unknown exposure is not spend but is still exposure, so reconcile the ambiguous attempts before treating it as spend. A settled-spend threshold alert is a budget decision, not a fault. A spend anomaly alert fires only when the tenant history qualified; if the verdict says the history was insufficient or the baseline was empty, the tenant is not judged unusual and you must gather more periods before comparing. Record which policy digest produced the evaluation, because the thresholds are part of the explanation, and re-evaluate after any reconciliation since the numbers and the watermark move. The evaluation delivers nothing by itself, so there is no acknowledgement to record and no escalation to close; assign an owner in the incident record when you act on one. See docs/K5.6-SPEND-ALERTS.md.

## KB-05: Suspected cache wrong answer or tenant leakage

Disable semantic cache globally or for affected scope; revoke/invalidate entries by context/policy version. Preserve redacted diagnostic IDs and access logs in restricted incident storage. Verify retrieval ACLs, session tenant binding, cache scope and document revocation timing. Do not copy customer prompts to ordinary tickets/logs. Tenant leakage blocks release/re-enablement until the root cause and negative suite pass. Rebuild eligible entries rather than manually rescope old ones.

## KB-06: Slow streams or token transport loss

Inspect per-client buffer usage, API RSS, Redis notification/token transport and write-timeout disconnect rates. Increase replicas within DB/global limiter budgets if qualification permits. Prefer disconnect/resync/coalescing to larger unbounded queues. Clients retrieve durable inference result after gaps. Exit when memory is bounded, recovery works and completed jobs do not depend on the browser staying connected.

## KB-07: Webhook failures and replay

Inspect endpoint health, verified DNS/IP/egress policy, response classifications, retry schedule and secret rotation. Run signed test-fire under rate limit after endpoint repair. Preview selected exhausted deliveries in dry-run; replay capped batches preserving event IDs. Verify receiver deduplication and reconciliation watermark. Never disable SSRF or signature checks to make a replay succeed. Exit when backlog drains without duplicate business effects.

## KB-07A: Inbound provider callback conflict or replay

Confirm the provider event ID, the digest the sender presented and the caller tenant. A repeated event ID with the same digest and tenant is a harmless duplicate: the inbox already applied it once and returns the recorded application time. A repeated ID with a different digest, or the same ID under another tenant, is a conflict: nothing was applied, and the append-only callback_conflicts row records payload_mismatch or 	enant_mismatch under the caller tenant. Never retry a conflict with a rewritten payload or under a different tenant, and never delete the original inbox row; inbox rows are immutable. If a conflict repeats, consider a captured delivery being replayed and check the provider's own event history before contacting the integration owner. A failed application is different: it recorded nothing, so a plain provider retry is the correct recovery. Direct table access is not granted to any runtime role; use the admin connection or the future operator surface. See docs/K6.1-CALLBACK-INBOX.md.

## KB-08: Database failover/recovery

Stop write admission and confirm single-writer fencing. Establish the backup/recovery cut and restore point; preserve pre-failure external effect IDs. Verify schema checksums, event/inbox/idempotency data, budget reservations, role bindings, erasure journal and Temporal consistency. Run invariant probes and read-only smoke. Resume writes gradually, then projections, then external effects after reconciliation. Record actual RPO/RTO and unrecoverable/unknown effects.

## KB-09: Tenant erasure or legal hold

Verify privacy authority and hold status. Disable new context/index/cache publication for records being erased. Execute bounded deletion manifest across objects/all versions, chunks/embeddings, prompt contexts, reversible PII records and applicable external provider records. Preserve non-PII event facts/audit required by policy. Verify with independent lookup and storage-version probes; note backup ageing/restore-journal policy. Do not claim immediate deletion from already-retained backups.

## KB-10: Subscription, entitlement or meter discrepancy

Verify tenant/provider mapping and signature/inbox identity. Freeze new costly admissions if entitlement is uncertain; retain billing repair/export and safe workflow closure. Fetch current provider subscription/invoice state, replay deduplicated observations and reconcile meter sources. Never upgrade via a checkout redirect or edit old invoice ledger rows. Apply explicit adjustment/credit with provenance, notify billing owner using safe summary and record customer impact. Recheck grace/downgrade/period timing before removing restrictions.

## KB-11: Procurement budget, PO or accounting mismatch

Stop affected financial transitions and preserve pending authority/line/effect IDs. Compare immutable procurement ledger with counters, reservation/commitment/actual mappings and ERP source versions. Check whether an external export succeeded despite timeout before retry. Correct with reviewed reversal/adjustment; do not zero counters or reissue a PO. Verify approval packet, amendment delta, accepted receipt allocations and no duplicate invoice coverage. Resume only after reference invariants and tenant/entity permissions pass.

## KB-12: Supplier/member offboarding or missed renewal task

Verify actor/scope, revoke grants/sessions/invitations and personal keys, then inspect active approvals/delegations/supplier status. Reassign tasks through an audited command; do not impersonate a departed approver. Stop new supplier approvals/PO issuance when eligibility is withdrawn, and surface existing obligation impact. For a missed notice inspect confirmed date/timezone/source version, durable occurrence and delivery state; create an accountable recovery task and preserve the original missed history.

## KB-13: Blocked outbox stream repair

Alert on any `outbox_delivery.delivery_state='blocked'`, oldest blocked age, and aggregate head lag. First inspect the tenant-scoped diagnostic summary (aggregate/event/version, allowlisted error code and attempt count); diagnostics never return the event payload. Confirm the incident/change reference, identify the serializer or storage correction, and preserve relevant deployment and database evidence in the restricted incident system. A distinct operator identity must pass the repair authorization check. Submit the observed event ID, version, prior error code and attempt count as stale-state guards, plus an allowlisted reason and `INC-`, `CHG-` or `OPS-` reference.

The repair transaction locks the blocked delivery and verifies the current aggregate head, immutable event hashes and contiguous event replay, matches the safe envelope to the canonical event, confirms no earlier version is unpublished or later version already published, and records the actor/reason/evidence before setting only that delivery back to pending. It preserves the event ID, attempt count, last error classification and head version; no event, envelope or claim epoch is rewritten, and the relay still publishes strictly in order. Verify the audit row, then observe the normal relay retry and confirm the same event ID publishes before later versions. If validation fails or the request is stale, stop and escalate; never edit immutable rows, mark an event published, reset a head, or skip a version. Roll back an application deployment only if it remains compatible with the stored schema; correct storage damage through a reviewed forward recovery from verified backup evidence, then retry the guarded repair. Break-glass SQL requires incident approval, a second reviewer and post-action reconciliation.

## KB-14: Supplier case Temporal dispatch backlog or conflict

K2.3 is not runtime-mounted and has no customer traffic. Until an authenticated worker role, a hosted Temporal profile and an accountable on-call owner pass K0/K0.1, use only the pinned synthetic local profile. The intended low-cardinality alerts are: any dead dispatch row, oldest pending/leased intent beyond five minutes, expired lease count above zero for more than two poll intervals, and sustained Temporal delivery errors. Never label metrics with tenant, case, intent, supplier, or evidence identifiers; metric export and paging are not wired yet.

On a local/test failure, stop the dispatcher process while leaving immutable intents and dispatch state intact. Inspect the worker-scoped minimal dispatch row, then compare its case/version/type/hash with the immutable case event and the Temporal workflow's opaque tenant/case-derived ID and history. Confirm that an accepted Temporal signal's event hash/version matches the database before retrying. Transient failures retry with deterministic bounded backoff; expired leases are reclaimed with a higher epoch, and old workers must not acknowledge them. A dead earlier version intentionally blocks later versions. Preserve that block and escalate to the workflow operations owner. K2.5 evidence manual review concerns document content only; it does not repair or unblock workflow delivery. No general-purpose requeue or SQL state reset is permitted in K2.3.

For code rollback, stop dispatch and keep migration `0010_supplier_workflow_dispatch` applied; never drop dispatch rows, immutable intents, or Temporal histories. The V1 workflow type/task queue and minimal signal contract are persisted compatibility surfaces. Roll forward with a versioned workflow and replay qualification if history semantics change. Resume only after the backlog is ordered, event identities reconcile with workflow state, alerting/ownership exists, and a restart/duplicate-signal test passes. These steps do not establish production recovery or an SLO.

## KB-15: Supplier approval deadline or reviewer dispute

K2.4/K2.5 case routes and the expiry/reminder dispatcher remain unmounted and have no customer traffic. For a local/test case, compare the current case version/hash to its immutable event chain, then compare policy version/digest, frozen plan/evidence digest, accepted decision IDs and minimal Temporal event identities. Do not place decision reasons, supplier evidence, actor identifiers or raw event payloads in metrics, general logs or tickets.

An approval is eligible only when the case lock is held, PostgreSQL acceptance time is strictly before the persisted deadline, the exact plan step's direct role grant or one active delegation exists, required prerequisite steps are approved, and the actor is neither creator nor submitter. Rejection is terminal. A completed pre-deadline plan remains approved if the workflow signal arrives late; partial decisions do not prevent expiry. Retry the same decision ID only with identical actor/action/reason; any difference is a conflict. New authorization applies to new decisions only; never rewrite accepted decisions after a role change.

Expiry uses the same case-row lock and is idempotent after any terminal state. A decision/expiry conflict must be resolved from the committed database acceptance timestamp and event chain; do not infer the winner from Temporal arrival time. Missing or contradictory plan rows, digests, events or intents are a correctness incident: stop the affected synthetic worker, preserve the rows and escalate. There is no repair/reset command and direct SQL edits are prohibited. Reviewer/delegation provisioning and authenticated API mounting remain K0/K0.1 gates. Activity polling/provider delivery, paging and an accountable owner remain runtime-operations work; K2.5 persistence/dispatcher code alone does not qualify these paths for customer traffic.

K2.5 lifecycle operations use the same lock and immutable event chain. Cancellation is accepted only before the deadline; verify its event/cancellation ID and invitation revocation, and confirm all writes remain blocked. Never reactivate a canceled case or clear its event/effect rows. Manual-review `replacement-required` does not reopen the frozen case or approve a supplier; create a fresh case for replacement evidence. An open review after a terminal transition is stale and must not be manually forced to resolution.

Reminder and expiry effects live in `supplier_case_activity_effects`. Inspect only the worker-authorized effect metadata and coarse error code. Reclaimed leases increment `lease_epoch`; stale owners cannot acknowledge. Retry the same effect key and payload digest. Do not reset attempt count, change payload, or revive dead/canceled/delivered rows with SQL. Expiry effects invoke the locked idempotent case-expiry repository and should end as canceled/no-op after the terminal-state trigger runs. A notification sink may deliver twice if an acknowledgement is lost; use a provider idempotency key equal to the effect key. Current reminder destinations are active reviewers on a frozen approval plan; supplier/requester routing is not implemented, and an effect due before submission is a no-op. This environment has no qualified provider, poller runtime, paging owner or production notification secret.

Keep additive migrations `0011_supplier_case_approval_arbitration`, `0012_supplier_case_expiry_deadline_guard` and `0013_supplier_case_lifecycle_effects`, together with accepted decision/review/event/intent/effect history, on rollback. The earlier K2.3 worker does not understand later event types or the expanded event bound; pause dispatch rather than deploying that worker against K2.4/K2.5 data. Roll forward with a compatible workflow/worker and replay qualification; there is no destructive down migration.

## Lexical corpus build and publication (K3.2)

The PostgreSQL lexical index is not a serving endpoint. Builds are created and published only by the isolated `keel_retrieval_indexer` database role through the repository lifecycle: stage bounded batches, finalize (which reconciles manifest counts and postings), then publish with the expected cohort generation. Never set the active head manually or bypass the generation check. A stale generation is a normal conflict: reload the active generation, confirm the candidate still represents the intended source snapshot, and retry only if that remains true. Failed publication rolls back head and build state together. Raw text and normalized tokens must not be added to index tables or logs. Retired builds are retained because deletion and safe compaction are not implemented yet; do not issue ad hoc deletes. If a key/analyzer/chunker identity changes, build a parallel version and evaluate it before cutover; never reinterpret old term IDs using a new key.

## Embedding model and ANN provisioning (K3.3)

Register a new model ID/revision only after artifact, provider, tokenizer/analyzer, input limit, dimensions, cosine metric and normalization have been reviewed and a canonical manifest digest is fixed. A changed field is a new immutable model identity. The K3.3 CI fixture is synthetic and must never be enabled for tenant content. Model index provisioning runs through the restricted schema-owner function and creates a partial halfvec HNSW index for one exact revision/dimension. Index creation takes a table lock in this transactional implementation; it is not an online production migration procedure. Do not invoke it on a populated customer index until a separately reviewed online/concurrent rollout and rollback plan is qualified. HNSW queries set strict iterative scan, ef-search, tuple and memory bounds inside a read-only transaction. An underfilled scan falls back to exact search only when the whole eligible build is within the configured hard limit; otherwise retain the smaller candidate list and degraded flag. Never remove tenant/cohort/source-build predicates to improve recall. Exact vectors contain sensitive derived data: apply the approved database encryption, backup, retention and access policies before a production model is enabled. Provider quality, capacity and erasure procedures remain unqualified.

Each source adapter must return candidates only after its tenant/cohort scope is fixed and must report the exact active build/generation. Vector provenance must identify the same lexical source build/generation; stale combinations are rejected. Do not blend BM25 and cosine magnitudes. ## Retrieval withdrawal and erasure request handling (K3.5)

`Repository.WithdrawSource` is the immediate logical-suppression action for an indexed document version in one exact tenant and `visibility_key` cohort. It atomically marks eligibility withdrawn and inserts a durable job in `fenced` state. Retrying the same job ID is idempotent. Never clear the tombstone, edit eligibility rows manually, or reuse the same document-version identity for replacement content; replacements require a new immutable source version. Lexical/vector searches and publication lock source eligibility in repeatable-read transactions. If a concurrent withdrawal causes a serialization error, discard all candidates and retry the whole bounded query before exposing results.

Migration `0017` and `internal/retrieval/postgres` provide the erasure-job lease control plane. A worker claims one due job for an explicitly trusted tenant/cohort scope with `SKIP LOCKED`; lease epochs fence stale workers. Leases are 1 second to 15 minutes, retries use a separate budget of at most 12 counted failures and a 1-second to 24-hour delay; successful bounded cleanup progress does not consume this failure budget, while expired leases and actual errors do. Permanent failures or exhausted failure budgets become `blocked`. A worker must use `CompleteErasureJob` only after every configured cleanup action has completed; its call changes job state but performs no deletion. Do not call it manually.

PRs #153, #155 and #158 provide the manifest processor plus supplier-object and derived-index executors. PR #167 adds a bounded polling runtime package that accepts one pre-authorized tenant/cohort scope, renews the active lease before dispatch and during long actions, and reports aggregate low-cardinality outcomes. This is an injectable runtime harness; there is no deployable service entry point or production composition. `SupplierSourceObjectsExecutor` resolves work from the current claimed job and delegates to the generation- and lease-fenced eraser; that eraser requires the configured serialized legal-hold authority and persists its content-free receipt before releasing the permit. `DerivedIndexCleanupExecutor` holds the same clearance boundary through a bounded unpublished-index cleanup pass and receipt persistence. `erasureworker.Metrics` can be supplied as a `health.MetricsExtension` to `health.NewHandlerWithMetrics` or `health.RunWithMetrics`; its fixed counters and gauges do not label tenant or cohort. PR #172 adds an oldest-first, at-most-10,001-row sample for the configured scope, caps reported counts at 10,000 and marks overflow. `Runtime.Run` refreshes it before processing and no more often than every 30 seconds, with a 500 ms query deadline. Completed jobs are excluded; blocked jobs remain in the outstanding count. A failed refresh leaves the last sample and timestamp visible and goes to the configured error handler. This still is not a deployable production worker composition, and alert thresholds, paging and operations ownership remain unqualified. Test authority and storage are synthetic. The six-action processor still requires a production executor for every manifest action. PR #174 adds an injectable `LegalHoldCheckExecutor`; an active or unknown decision becomes a durable blocked job with no automatic retry or later action dispatch. Do not manually edit blocked rows or receipts. No production legal-hold authority or operator-authorized reprocessing path is configured; those remain gated under #142. `not_applicable` receipts are permitted only for cache-revocation and queued-work-revocation, which the documented profile does not mount. Legal hold, source objects, derived indexes, and backup expiry require completed action receipts; absent production providers must leave work blocked. Migration 0022 rejects new out-of-scope N/A receipts. Constraint validation also stops an upgrade if legacy rows exist; inspect under controlled DBA access and do not bypass RLS or alter append-only receipts. Cache-revocation, queued-work-revocation and backup-expiry actions have no production executors/providers. The system also has no production object-store adapter, approved retention/reference policy, backup-retention integration, or production operations ownership. Do not deploy the harness or enable automated physical deletion. Keep any future adapter disabled until its authority/provider, runbooks and adversarial PostgreSQL evidence are qualified.

## KB-18: Langfuse OTLP export (disabled by default)

The internal Langfuse adapter has no application wiring or production endpoint. Do not enable it until K0.1 approves the identity/secret source, TLS egress host allowlist, Langfuse retention/deletion policy, and an operational owner. The immutable v1 adapter contract emits only bounded enum metadata, latency/retry values, and optional validated W3C traceparent correlation plus a random opaque context-vault UUID; never pass a tenant/user/business identifier or add prompt, completion, tool, or arbitrary attribute fields. A schema change requires a new version. It uses OTLP/HTTP `/api/public/otel/v1/traces`, Basic auth and `x-langfuse-ingestion-version: 4`; legacy Langfuse ingestion endpoints are not supported.

The queue is memory-bounded and best-effort. A full queue increments a drop counter and does not retry the model/business operation. Export failure/timeout increments a local counter and does not expose provider error text or credentials. During shutdown, call `Close` with a bounded deadline; timed-out exports are abandoned. Do not log payloads or auth headers during diagnosis.

Vault expiry, record deletion, and legal-hold release do not delete data already ingested by Langfuse, including copies or provider backups. Use the independently approved Langfuse [retention](https://langfuse.com/docs/administration/data-retention) and [deletion](https://langfuse.com/docs/administration/data-deletion) controls, account for asynchronous deletion and downstream copies, and verify provider-side completion evidence before asserting telemetry erasure. A telemetry outage does not authorize retrying model work or increasing queue bounds without review.

# K5.2.1 order stream reconnect and backpressure

This is a partial implementation of [K5.2](https://github.com/sanskarpan/Keel/issues/40), tracked by [issue #275](https://github.com/sanskarpan/Keel/issues/275) and implemented by [PR #276](https://github.com/sanskarpan/Keel/pull/276). PR #276 merged as `36532b19fdfd202c47e077be524da2d56cb6d7f6`; contract CI [#462](https://github.com/sanskarpan/Keel/actions/runs/37644554284) passed on reviewed head `5140d602825dc2f0f9b668f4e35378409bd1ab3e`. It bounds durable order-state SSE connections; it does not implement model-token delivery or provider interruption events.

## Contract

- A new stream without `cursor` or `Last-Event-ID` starts with a privacy-safe order snapshot and order-bound cursor. The order state and per-tenant feed high-water mark are read in the same repeatable-read transaction, preventing updates between snapshot and cursor from being skipped.
- A reconnect with a valid order-bound cursor resumes after it without sending another snapshot. If retention has removed required history, the server emits `resync_required` and closes; the client reloads the authorized order snapshot before reconnecting.
- Each SSE frame has a five-second write deadline. A timeout or write/flush error terminates only that client stream. The server verifies deadline support before database access and fails closed when its response writer cannot enforce the limit.
- Fanout uses direct synchronous writes. There is no per-client event or token queue. Database pages are limited to 100 rows; heartbeat comments are sent every 15 seconds while polling once per second.
- No durable order work depends on the connection. A disconnect does not cancel or abandon the underlying operation.

## Verification scope and limits

Handler tests cover initial snapshots, explicit-cursor reconnects, bounded cursor checkpoints, retention resync, malformed/future cursors, cancellation, deadline setup/clear, unsupported writers and write failure. PostgreSQL integration coverage checks the snapshot cursor and order head under one read transaction, bounded feed pagination, resume, typed payloads and tenant isolation.

K5.2 remains open for production deployment/runtime limits and provider interruption events. No production inference executor currently publishes token frames, and authentication/runtime deployment remains gated by K0. This implementation bounds frame writes, not the maximum number of concurrent connections; deployment concurrency limits and alerting must be qualified before customer traffic.

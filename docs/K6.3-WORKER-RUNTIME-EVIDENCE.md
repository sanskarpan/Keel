# K6.3 slice: webhook worker runtime and tenant scheduling

Issue #372 (parent #48, checklist item K6.3). PR #374 merged as
`701ac18081575979982b83b198ff27a9dde39abf`; contract CI #611 passed on reviewed head
`13bf45503ad33b27712b65bbfe16fc115c13b363`. This slice makes the reviewed delivery loop runnable:
a database-backed scheduler discovers tenants with due or expired deliveries and the
`webhook-worker` runtime role wires the store, keyring, egress, executor, retry and breaker
policies, and management health endpoints.

## Tenant discovery

Migration `0049_webhook_tenant_scheduling` adds global partial indexes for due `pending` state and
expired `in_flight` leases, plus `keel_meta.list_webhook_delivery_tenants(limit)`:

- Requires membership in `keel_webhook`.
- Accepts a limit from 1 through 1000.
- Returns only tenant IDs that have a `pending` delivery with `next_attempt_at <= now` or an
  `in_flight` lease with `lease_expires_at <= now`.
- Groups by tenant, so multiple due deliveries do not duplicate a tenant, and orders by the
  earliest due time, then tenant ID.
- Returns no delivery, endpoint, URL, payload, attempt or state data, grants execute only to
  `keel_webhook`, and runs as a fixed-`search_path` security-definer function.

`postgres.TenantSource` validates every returned tenant ID, rejects the zero tenant and
deduplicates defensively.

## Scheduler

`internal/delivery/webhook/scheduler`:

- `RunOnce` discovers up to the tenant limit and runs one bounded batch for each tenant through
  the existing `worker.Runner`.
- A per-tenant error increments the failure count and does not stop the remaining tenants; the
  joined error is returned with the aggregate report.
- `Run` polls until context cancellation, retries discovery and per-tenant failures on the next
  pass, and records the last successful discovery time for readiness.
- Defaults: 1-second poll, 100 tenants, the worker's 20-delivery batch and sequential per-process
  execution. The runtime role overrides the batch to 5.

Multiple replicas rely on the existing `SKIP LOCKED` lease and monotonic epoch fence; tenant
discovery itself is not a lease.

## Runtime wiring

`webhook-worker` is registered in `runtime.RegistryFor` and builds:

- a dedicated PostgreSQL pool over `KEEL_WEBHOOK_DATABASE_URL`, with staging/production requiring
  `sslmode=verify-full`;
- a keyring from `KEEL_WEBHOOK_ACTIVE_KEY_ID` and `KEEL_WEBHOOK_ACTIVE_KEY_SECRET_B64`, plus an
  optional previous pair, with all secrets base64-decoded and validated before use;
- the K6.2 egress client and executor, the default retry policy and the default breaker policy;
- a scheduler with `KEEL_WEBHOOK_POLL_INTERVAL` (100ms-1m), `KEEL_WEBHOOK_TENANT_LIMIT` (1-1000),
  `KEEL_WEBHOOK_BATCH` (1-100) and `KEEL_WEBHOOK_LEASE_DURATION` (5-300 whole seconds);
- management health endpoints on the configured listen address.

Readiness requires a successful database ping and a successful tenant-discovery pass no older
than three poll intervals. It does not prove receiver health.

The keyring holds one active and at most one previous key, so endpoints must reference those key
IDs. There is no per-endpoint key provider or KMS integration in this slice.

## Security

Tenant discovery is a metadata-only capability. The webhook role is already trusted to lease and
process any authorized tenant, so returning tenant IDs lowers the cost of guessing a UUID but does
not expose delivery content. The process never logs the database URL or signing secret, and an
endpoint whose key ID is absent from the keyring fails closed as a permanent attempt. The
scheduler rejects zero or malformed tenant IDs before setting any tenant context.

## Verification

Coverage runs against a fresh PostgreSQL database with migrations through `0049`:

- due pending and expired in-flight tenants are returned; future pending and future in-flight
  tenants are excluded;
- multiple due deliveries for one tenant produce one row, ordered by earliest due time;
- the tenant limit is honored and invalid limits are rejected;
- the application role cannot execute discovery and the webhook role cannot read the state table
  directly;
- the scheduler processes every due tenant, isolates a failing tenant, honors batch/limit options,
  records a successful poll and stops on cancellation;
- runtime settings accept valid defaults/custom values and reject missing or malformed database,
  keyring, interval, tenant-limit, batch and lease configuration without leaking credentials;
- `webhook-worker` is registered in the runtime dispatcher.

Linux CI covers the race detector.

# K8.11/K8.2 slice 15: identity-api runtime mount

Related to #70 and the K8.1/K8.2 tracks. All identity surfaces were
unmounted; this slice mounts them in a real `identity-api` role that
follows the operator-api composition pattern: env-configured database
and deploy-time pepper file, loopback-only listener by default, content-free
operational logging, and `/health/*` + `/version` probes. No demo
credentials are baked in.

## Contract

- `config.RoleIdentityAPI = "identity-api"`, registered in the supported
  role allowlist and the runtime `RegistryFor`/`Dispatch` map (unwired
  roles still fail closed).
- `internal/platform/runtime/identity_api.go`:
  - required `KEEL_IDENTITY_DATABASE_URL` (postgres[d], user, db;
    `sslmode=verify-full` enforced in staging/production) and
    `KEEL_IDENTITY_PEPPER_FILE` (read via `auth.ReadPepperFile`,
    never logged); optional `KEEL_IDENTITY_RP_{DISPLAY_NAME,ID,ORIGINS}`
    that must arrive complete to enable WebAuthn ceremonies, else the
    ceremony routes stay `501`; optional loopback override flag.
  - pool sizing, 5 s DB readiness probe, `auth.DefaultArgonParams`
    hashing, log-only senders that record content-free send events
    (production must inject a real mailer; K8.10 owns transport
    qualification).
  - `GET /health/live|ready|startup`, `GET /version`,
    `GET /metrics` plus the mounted `POST /v1/auth/*` handler with
    read/header timeouts.
- `make local-identity-api` (ephemeral generated pepper file, deleted on
  exit; nothing secret committed).

## Verified

- `go vet` clean; `go test ./internal/platform/config/
  ./internal/platform/runtime/` pass, including settings validation
  (missing/bad DB, missing/bad pepper, partial RP, bad flag,
  staging TLS), loopback enforcement, and registry wiring.
- `--- PASS: TestIdentityAPIServesMountedRoutes` — boots the real role
  in-process against real PostgreSQL and proves health readiness,
  unauthenticated `401`, bad-input `400`, unknown-login `401` and a
  full `201` registration through the mounted handler.
  Runs in-container following the repo's local-integration pattern
  (same as `local-identity-test`).

## Limits and notes

- Docker Desktop on Windows currently publishes no host ports for the
  compose PostgreSQL (`docker port` empty), so a host-loopback boot
  cannot reach the database here; the in-container serve test is the
  boot evidence. Retrying a host boot is worthwhile once publishing
  recovers — expected result is startup with readiness, not a silent
  refusal.
- Debugging note: `cmd/keel` logs a static `role_not_registered`
  message for ANY runner failure (including DB-unreachable), because
  the underlying error is discarded at the log site. A host boot that
  fails after "role requested" is almost certainly a dependency
  (database/pepper), not dispatch: `RegistryFor` unit-proves the
  wiring, and the in-process serve test proves end-to-end boot.
- No production RP identity, no real mailer, no tenant-context
  consumers yet; compose service wiring stays future work.

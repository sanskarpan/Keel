# K4.7.2 durable safe-read degradation evidence

This is a partial implementation of [issue #198](https://github.com/sanskarpan/Keel/issues/198), under parent [issue #37](https://github.com/sanskarpan/Keel/issues/37). It builds on the Redis admission authority from #196. It does not qualify production traffic or complete issue #198.

## Implemented contract

- PostgreSQL is the shared authority for fallback admission. No limiter-local counter exists; regional fleet tokens, per-tenant/route tokens, outage state and replay receipts survive API process restart and replica changes.
- A control-plane provisioned enabled fleet policy and tenant/route policy form the safe-read route allowlist. Missing/disabled policies reject. Application roles cannot directly inspect or change policy or bucket tables. The limiter and policy repository also require explicit configuration; the fallback is disabled unless configured.
- Admission supports a fixed one-unit request cost. The coordinator rejects fallback for any request whose Redis policy cost is not exactly one unit, avoiding a cheaper SQL retry for a more expensive request. Fleet and tenant capacity plus refill policies bound request count; richer weighted costs are not implemented.
- The first degraded admission opens one regional window capped at 60 seconds by a database constraint. Once expired, it stays closed until the separately credentialed rate-control observer has observed five consecutive seconds of successful home-region Redis PINGs and records recovery. Pod restart, elapsed time, and Redis flapping do not themselves reset the window.
- A stable request UUID replays the exact stored decision for ten minutes. The receipt binds tenant, region, route, request ID, tenant policy digest, fleet policy digest and outage ID. Reusing a request ID with a changed policy conflicts; changing the active policy generation rejects a stale admission. Cleanup is bounded to 100 expired receipts per call, plus deletion of an expired receipt for the exact key before that key is reused.
- The coordinator only attempts SQL fallback after the primary limiter reports `ErrUnavailable`, while the request context remains live. Model/write routes have no provisioned safe-read policy and fail closed. If PostgreSQL or policy lookup is unavailable, admission fails closed.
- `DegradedMetrics` exports admission result counters and cumulative duration/count series through the existing structural Prometheus `MetricsExtension`. Its result label is a fixed enum; tenant, route, request, region, and outage IDs are excluded. A health-handler test verifies the output and label bound. No current runtime role constructs this limiter or attaches the extension to a live scrape endpoint.
- Redis and PostgreSQL cannot atomically coordinate an ambiguous Redis timeout. A Redis decision may have consumed capacity even if the caller receives `ErrUnavailable`; fallback can then admit a separately charged request. This additive allowance is bounded by the shared SQL fleet and tenant buckets, but is not strict global exactly-once admission across both systems.

## Verification performed

Local verification used the repository's PostgreSQL and Redis Compose containers and test-only identities. Migration `0028_rate_limit_degraded_fallback` was applied as `keel_schema_owner`. The integration tests ran with separate app, admin, and `keel_rate_control` database connections plus the local Redis service.

- `TestPostgresDegradedAdmissionIsFleetBoundRestartSafeAndTenantScoped`: twenty independently constructed limiter instances contend across tenants; accepted admissions must remain within the five-token burst plus the policy's one-token-per-second refill over measured test runtime. It also checks that a stale digest does not open the outage window, application policy-write denial, sixteen concurrent exact retries, replay through a newly constructed limiter, policy conflict, stale-generation rejection, and expiry remaining closed.
- `TestPostgresDegradedRecoveryRequiresRateControlRoleAndHealthyRedis`: app credentials cannot reset recovery; five seconds of successful Redis probes through the rate-control identity closes the old window and a subsequent outage receives a new outage ID.
- `TestPostgresDegradedRecoveryProbeFlapRestartsHealthInterval`: a scripted failed Redis probe interrupts the healthy streak; recovery closes the window only after five later consecutive successes.
- `TestPostgresDegradedAppPoolExhaustionFailsBeforeAdmission`: an exhausted app connection pool returns fail-closed and creates no outage-window row.
- `TestCoordinatorUsesPostgresFallbackOnlyForApprovedSafeRead`: a real Redis connection failure falls back to the provisioned route, returns the same decision on retry, enforces the tenant cap, and rejects an unprovisioned model route.
- `TestAdmissionCoordinatorFallsBackOnlyOnRedisAvailability`: unit coverage verifies other Redis errors and a request cost above one unit do not enter fallback.
- `TestDegradedPostgresUnavailableFailsClosed`: an unreachable PostgreSQL endpoint returns degraded-unavailable and increments the bounded `db_error` metric.
- `TestPostgresDegradedExpiredReceiptKeyCanBeReusedAfterBoundedCleanup`: after the exact request receipt expires and 101 older stale receipts exist, bounded cleanup plus exact-key deletion permits a fresh admission without an idempotency collision.
- The coordinator unit test also verifies a canceled request context does not enter PostgreSQL fallback.
- Package tests, race detector, `go vet`, and `git diff --check` are run locally for this revision; the GitHub Actions run for the final PR head remains the merge gate.

These are local deterministic/integration checks, not production load or multi-process host failure qualification. PostgreSQL serializes regional admission on one outage-window row; latency/lock contention under the production-small load target still needs measurement.

## Security and operational boundaries

`keel_rate_control` is a trusted service identity. PostgreSQL checks that identity for recovery and policy writes, but it cannot prove that a caller actually ran the Redis health probe or that an injected policy authorizer approved a write. The recovery helper takes the configured primary limiter, so callers cannot independently pair an arbitrary Redis client with a different recovery region string; the deployment must still bind that limiter's endpoint/DNS/TLS identity to the declared home region. Only the reviewed control/observer service may hold the rate-control credential; it must not be shared with API, worker, or operator shells. The current local Compose password is synthetic and must never be used outside local development.

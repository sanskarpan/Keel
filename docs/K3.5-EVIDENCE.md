# K3.5 implementation evidence (in progress)

Migration `0016_retrieval_source_eligibility_erasure` adds one eligibility row per tenant, visibility cohort, and immutable document version. Existing indexed sources are backfilled as active. A withdrawal advances the row once to a sticky `withdrawn` state; the database rejects deletion, reactivation, and reintroduction of withdrawn versions into staged lexical builds.

`Repository.WithdrawSource` commits the withdrawal fence and an idempotent, durable erasure request in one transaction. The current job state is `fenced`; the immutable job records the requesting principal ID supplied by the future authenticated caller. Repeating the same job ID with the same actor returns the same request. The app role may withdraw an existing indexed source but has no path to reactivate it. Requesting an unregistered source returns `ErrSourceNotRegistered`.

Lexical and vector candidate reads require current active eligibility. Before query results are returned, the repository locks every candidate source row in its repeatable-read transaction. Lexical and vector publication similarly lock every source version in their build before switching the active head. A withdrawal that commits first suppresses results and blocks publication. If a query or publication locks active eligibility first, it is ordered before a concurrent withdrawal; repeatable-read serialization failures must be retried before any result is exposed.

`Repository.NewCitationResolver` implements K3.4's live citation-resolution interface. It rechecks and locks current source eligibility before invoking an injected range reader, then verifies exact byte length, UTF-8 validity, nonblank content, and the immutable chunk digest before returning an excerpt. Integration coverage verifies successful resolution while active and that the range reader is not called after withdrawal.

The concrete `internal/retrieval/source/intake.Reader` maps `DocumentVersionID` to the immutable `supplier_uploads.upload_id`. Under forced tenant/cohort RLS it locks the active eligibility row, requires an exact match for the persisted retrieval chunk identity, byte range and digest, and loads only uploads in the `extracted` state. It bounds the object read at `MaxExtractedSize+1`, verifies the stored byte count and SHA-256 over the full extracted object, validates the requested UTF-8 range, and returns a copy of only that range. There is no content cache, and object contents are not logged. The end-to-end PostgreSQL integration test builds and publishes a real chunk through the retrieval indexer role, resolves it through the app role, rejects an unindexed byte range and a different cohort, and rejects the citation after a withdrawal.

Migration `0017_retrieval_erasure_leases` and `internal/retrieval/postgres/erasure_worker.go` add the bounded erasure-job control plane. Claims are tenant/cohort-scoped, ordered, and use `FOR UPDATE SKIP LOCKED`; each claim advances an epoch and attempt count, and every mutation requires a live owner/epoch lease. Lease duration is capped at 15 minutes, retry delay at 24 hours, and attempts at 12. Retry exhaustion and permanent failures become durable `blocked` outcomes. Integration coverage exercises app-role denial, duplicate-claim exclusion, lease renewal, backoff, stale-epoch refusal, poison blocking, successful terminal transition, and final-attempt crash recovery under real forced-RLS roles. This is orchestration only: the supplier source-object and unpublished derived-index actions now call through the manifest processor, while `CompleteErasureJob` does not delete data and no executable worker runtime is configured.

## Scoped polling runtime (PR #167)

`internal/retrieval/erasureworker` runs one explicitly authorized tenant/cohort scope per process; it performs no scope discovery. Poll intervals are bounded to 1–30 seconds, idle rounds back off exponentially to a 60-second base and then add less than 20% positive jitter (so the actual delay stays below 72 seconds), and each poll processes at most one job. The processor renews the lease immediately before dispatch and during long actions. Lease loss or the 30-minute action timeout signals cancellation through the handler context; it is cooperative, so handlers must observe the context, and already accepted provider effects may still complete. Executors must be context-aware, lease-fenced and idempotent, and reconcile unknown outcomes. Poll observations expose aggregate outcomes without tenant or cohort labels. PostgreSQL integration exercises a long action outliving the original lease and cancellation when renewal is blocked by a row lock. Final PR head `4c6a0e9393f0f7e0a32c76d292fd61f83783045d` passed contract CI run [#37335807136](https://github.com/sanskarpan/Keel/actions/runs/37335807136) and merged to `main` as `4f9da3516435a851cf95126c5ff8a0a00af58fb9`. This package is not a deployable service composition and does not provide the remaining production action handlers or provider configuration; issue #140 remains open.

## Bounded erasure progress and failure accounting

Migration `0020_retrieval_erasure_progress_budget` adds a separate `failure_count` for unsuccessful erasure work. `attempt_count` and lease epochs remain monotonic. Successful bounded `derived_index` cleanup passes that yield because unpublished rows remain do not consume the failure budget; expired worker leases and actual errors do. Twelve failures still poison the action. The database refuses manifest completion until every required action receipt is durably present.

PostgreSQL tests exercise thirteen bounded progress yields, rejection of a stale yield after lease ownership changes, and successful completion after the remaining cleanup pass. ## Scope and remaining work

Residual K3.5 work is tracked as child issues [#138](https://github.com/sanskarpan/Keel/issues/138) through [#142](https://github.com/sanskarpan/Keel/issues/142) under parent issue [#28](https://github.com/sanskarpan/Keel/issues/28). The supplier object action [#137](https://github.com/sanskarpan/Keel/issues/137) is closed by PR #136, and the receipt gate [#144](https://github.com/sanskarpan/Keel/issues/144) is closed by PR #145. Safe cleanup of never-published index rows is implemented by [PR #147](https://github.com/sanskarpan/Keel/pull/147), which closes [#146](https://github.com/sanskarpan/Keel/issues/146). Source-object lease/hold gating is implemented by [PR #151](https://github.com/sanskarpan/Keel/pull/151), which closes code-level acceptance issue [#150](https://github.com/sanskarpan/Keel/issues/150); production authority and storage qualification remain under [#142](https://github.com/sanskarpan/Keel/issues/142). The generic processor in [PR #153](https://github.com/sanskarpan/Keel/pull/153), supplier source-object adapter in [PR #155](https://github.com/sanskarpan/Keel/pull/155), and derived-index adapter in [PR #158](https://github.com/sanskarpan/Keel/pull/158) advance [#140](https://github.com/sanskarpan/Keel/issues/140), which remains open for cache, queued-work, backup executors and runtime wiring.

Cache and retrieval-work policy is documented in [`K3.5-CACHE-AND-QUEUED-WORK.md`](K3.5-CACHE-AND-QUEUED-WORK.md). There is no retrieval content cache or asynchronous retrieval/reranking queue mounted. Existing source-eligibility generations and publication fences protect synchronous reads and index publication; they do not provide future per-user ACL generations or a cache/queue provider. Cache and queued work remain disabled pending #138 and the documented provider, runtime, invalidation, and adversarial-test gates.

The current query authority is Keel's tenant plus `visibility_key` cohort boundary. The principal identifier is persisted but no authenticated route currently binds it to a verified identity; there is no upstream identity/ACL service or per-user source authorization adapter in this repository. The concrete reader is coupled to supplier intake's extracted object metadata, but there is no production object-store implementation, content cache, legal-hold authority, backup lifecycle, or end-to-end erasure completion. PR #167 adds a bounded polling runtime package for one explicitly authorized tenant/cohort per process, including lease renewal, aggregate low-cardinality observations, idle backoff and cancellation. It does not add a deployable service entry point/configuration or production handler set. Supplier source-object and derived-index actions are adapted through injection. The `legal_hold_check` action still lacks a production executor and authoritative hold provider; cache, queue and backup actions have no production executors/providers. Test hold/storage fixtures are synthetic, and no production provider evidence exists. The withdrawal fence remains logical suppression; published and retired index contents remain immutable pending approved retention windows and reference checks. No physical deletion, cryptographic erasure, backup expiry, or end-to-end erasure completion is claimed. Remaining work includes per-user ACL, cache/queue/backup adapters and runtime wiring, approved retention policy, production legal-hold/storage authority, audit, operational ownership, and adversarial race evidence.

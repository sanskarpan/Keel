# K3.1 retrieval contract and evaluation corpus evidence

## Scope

K3.1 establishes immutable analysis/build identities and a reviewable evaluation fixture before lexical postings, production embeddings, serving, or relevance claims. No database migration or customer data is introduced.

## Implemented contracts

- `internal/retrieval/contracts` pins NFKC + Unicode full case folding, Unicode word segmentation, invalid UTF-8 and input bounds, original-source byte offsets, bounded query terms, and deterministic paragraph token windows with overlap and heading context.
- `research/retrieval/v1/build-manifest.json` binds analyzer/chunker IDs, immutable model/provider/revision and tokenizer identity, artifact digest, dimensions, input bound, normalization, distance, corpus-build and dataset IDs, and the SHA-256 of the exact corpus bytes. `SHA256SUMS` pins corpus and manifest file bytes; the linter verifies their adjacent digest files.
- The corpus and manifest JSON Schemas are checked in and validated by contract tests. Strict Go decoding rejects unknown fields.
- `research/retrieval/v1/corpus.json` is a small CC0-1.0 synthetic-only seed with train/dev/holdout partitions, positive span judgments, same-scope hard negatives, explicit no-answer queries, and out-of-scope tenant fixtures. It contains no real customer or personal data.
- The linter checks source/version references, tenant/visibility eligibility, UTF-8 byte spans, answer/no-answer consistency, immutable IDs/digests, explicit access-denial fixtures, and exact or >=0.80 token-bigram Jaccard leakage across partitions for queries and judged source documents. The heuristic is a guardrail for this small corpus, not a general semantic de-duplication guarantee.
- `keel.hash-vectorizer.v1` is an evaluation-only fixture identity. It is not a qualified semantic model and is forbidden as a production serving-quality basis.
- `internal/retrieval/eval/reference.go` and `cmd/keel-corpus-eval` provide an independent deterministic in-memory BM25 reference (`k1=1.2`, `b=0.75`, no stopwords/stemming) over exactly matching tenant/visibility cohorts. `reference-results.json` pins the corpus and manifest digests and all top-five labels/scores. CI regenerates and byte-compares it.

## Validation

Local validation passed:

- `go test ./... -count=1`
- `go test -race ./... -count=1`
- `go vet ./...`
- `go build ./...`
- `go run ./cmd/keel-corpus-lint research/retrieval/v1/corpus.json research/retrieval/v1/build-manifest.json research/retrieval/v1`
- `go run ./cmd/keel-corpus-eval research/retrieval/v1/corpus.json research/retrieval/v1/build-manifest.json research/retrieval/v1/reference-results.json`
- `git diff --check`

The corpus linter reports 9 queries, 20 source versions, and the `train`, `dev`, and `holdout` partitions. The reference results rank the one authored positive first for all 7 answerable queries, while both no-answer queries have a lexical false positive. The sample is too small and authored too directly from its sources to support general relevance claims. Relevance, recall, precision, latency, capacity, multilingual quality, tenant isolation under serving, and production-provider qualification remain unmeasured and belong to later K3 issues and gates.

## Trust and rollback

This change adds no runtime route, index, database table, embedding-provider call, customer content, or permission policy. Rollback is a normal revert of the implementation PR; the CI linter step and contract artifacts revert with it. Future persisted chunks and vectors must bind to the immutable IDs defined here, and incompatible versions must be built and evaluated in parallel rather than mixed.

# K6.3 slice: jitter retry policy and fenced attempt scheduling

Issue #341 (parent #48, checklist item K6.3). PR #342 merged as `d3284a5d112c021a858da5b301baa53c5404ae78`; contract CI #563 passed on reviewed head `22cd9814f441322ca8680c77355c23d268e370a1`. This slice adds the retry policy and the durable
attempt scheduler behind the K6.2 delivery ledger. It is a policy library plus a database state
machine; no delivery worker, HTTP client loop, endpoint registry, circuit breaker or replay UI is
wired.

## Retry policy

`internal/delivery/webhook/retry.go` fixes one policy:

| Bound | Default | Meaning |
| --- | --- | --- |
| `MaxAttempts` | 12 | Attempts started per delivery, including the initial one |
| `Window` | 24h | Time from the first attempt in which retries are allowed |
| `Base` | 5s | Uncapped delay of the first retry |
| `Cap` | 6h | Ceiling of one retry delay |

The uncapped delay for retry index `n` (retry 0 is the first retry after the initial attempt) is
`min(Cap, Base*2^n)`. The actual delay is full jitter: uniform in `[0, min(Cap, Base*2^n)]`, so
receivers that fail together do not retry together. A retry index large enough to overflow
saturates at `Cap` instead of wrapping. `RetryPolicy.Validate` rejects an attempt ceiling outside
1-100, a window outside 0-7 days, a base above one hour, a cap below the base and a cap above 12
hours.

`Scheduler` owns the jitter source. `NewScheduler` uses the package random source;
`NewSchedulerWithRand` accepts an injected `func() float64` for deterministic tests and rejects a
source that returns NaN or a value outside `[0,1)`. `Next(firstAttempt, now, attempts)` returns the
next attempt time, or `exhausted` when `attempts` already equals the ceiling or
`now-firstAttempt` reached the window. Exhaustion is decided before drawing a delay, and an
exhausted delivery must be recorded with no next attempt time. The scheduler is pure: it does not
sleep, retry, persist or observe a receiver.

## Attempt classification

`ClassifyStatus` maps a response to one durable outcome:

| Response | Outcome | Rationale |
| --- | --- | --- |
| 2xx | `delivered` | Receiver accepted the attempt |
| 408, 425, 429 | `retryable` | Transient request/timeout/rate condition |
| 5xx | `retryable` | Receiver or intermediary failure |
| Other 4xx | `permanent` | The same request cannot succeed |
| Unexpected 1xx/3xx | `permanent` | No progress can be inferred; redirects are denied by egress policy |

A status outside 100-599 is rejected. `ClassifyError` marks a transport failure `retryable` so a
timeout or connection failure is retried, except that an egress policy denial, an invalid delivery
identity or an invalid keyring is `permanent`: repeating the same destination cannot help, and
neither classification is a reason to relax policy.

## Durable state

Migration `0041_webhook_delivery_attempts` adds two tables. `keel_meta.webhook_delivery_state` has
one row per delivery with state `pending`, `in_flight`, `delivered`, `failed` or `exhausted`, an
attempt counter, first-attempt time, next-attempt time, lease epoch, lease expiry, delivered and
finished times. A shape check ties each state to exactly the timestamps it may carry, and
`attempts = 0` if and only if `first_attempt_at` is null. `keel_meta.webhook_delivery_attempts` is
the append-only log of one row per recorded attempt: attempt number, attempt ID, lease epoch,
outcome, HTTP status and latency. Attempt rows reference the delivery and are unique by
`(tenant, delivery, attempt number)` and by attempt ID.

A delivery insert creates its `pending` state row at the delivery's database creation time, so a
new claim is immediately eligible. Existing rows are backfilled. Partial indexes serve due pending
rows by `(tenant, next_attempt_at)` and expired leases by `(tenant, lease_expires_at)`.

Both tables use forced RLS, a schema-owner policy and revoked privileges for every runtime role.
Deletes are refused. A state row may not change its identity, decrease `attempts` or `lease_epoch`,
rewrite `first_attempt_at`, leave a terminal state or skip the state machine; attempts may not be
updated or deleted. Direct access is not granted to `keel_webhook` either.

## Lease and fence

`keel_meta.lease_webhook_deliveries(p_limit, p_lease_seconds)` requires `keel_webhook` membership
and an authorized tenant context. A limit of 1-100 and a lease of 5-300 whole seconds are
mandatory. It selects due `pending` rows and expired `in_flight` rows ordered by their due time
with `FOR UPDATE SKIP LOCKED`, then moves up to the limit to `in_flight`, increments `attempts` and
`lease_epoch`, records the first attempt time and sets the expiry from database time. It returns
the delivery identity, attempt number, a fresh attempt ID, the epoch and the expiry. Re-leasing an
expired attempt is intentional: delivery is at least once, and the higher epoch invalidates the
previous holder.

`keel_meta.record_webhook_attempt(...)` requires the same capability and tenant, validates the
outcome/status/latency and then updates the state only where the delivery is `in_flight`, the epoch
matches and the attempt number matches the leased attempt. A mismatch raises an error and writes
nothing, so a slow worker whose lease was re-issued cannot record. Retryable with a next attempt
time returns to `pending`; retryable with no next attempt time is `exhausted`; permanent is
`failed`; 2xx is `delivered`. Terminal states get a finished time, delivered gets a delivered time,
and a retry time older than 30 seconds is refused (future times are owned by the caller's
scheduler). The attempt row is inserted in the same statement, after the fenced update.

## Go API

`internal/delivery/webhook/postgres` exposes `Store.Lease(ctx, tenant, limit, ttl)` and
`Store.RecordAttempt(ctx, lease, result)` over the webhook capability's connection. Both run in one
tenant transaction that sets `keel.tenant_id` with transaction-local scope. `Lease` validates the
tenant, limit and whole-second TTL before touching the database and validates every returned
lease. `RecordAttempt` validates the outcome, status, latency and next-attempt combination before
touching the database and rejects a delivered result that is not 2xx. The caller must derive the
tenant from a trusted scheduling source, never from an endpoint or receiver payload.

## Coverage

- Unit: backoff sequence and cap saturation, policy bounds, full-jitter bounds and invalid sources,
  next-attempt/exhaustion/window behavior, the full status classification table, transport
  classification and state vocabulary.
- PostgreSQL: lease and record lifecycle (two attempts, retry then delivery), lease expiry and
  stale-epoch rejection, exhaustion and permanent failure, terminal-state update refusal, attempt
  log append-only refusal and state delete refusal, direct-access denial, capability denial via the
  application role, and concurrent leasing without duplicate grants.

## Boundaries

This slice does not run a worker or HTTP delivery loop, register endpoints, store URLs or secrets,
persist response snippets, enforce a per-endpoint circuit breaker or tenant delivery quota, emit
metrics, expose replay, or implement reconciliation. The retry delay is computed by the caller; the
database enforces fencing, state transitions and append-only history. Replays and retries keep the
event and delivery identity and take a fresh attempt ID through the lease, matching the K6.2 wire
contract. `K6.3` and parent #48 remain open. There is no down migration; `0041` is additive and the
code is not wired into a serving path.

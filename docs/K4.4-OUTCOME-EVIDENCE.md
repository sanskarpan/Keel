# K4.4 outcome and reconciliation evidence

## Implemented boundary

Migration `0027_ai_job_outcomes.up.sql` extends the existing queue with a monotonic outcome state machine. A worker's outcome transition is fenced by tenant, inference, worker ID, and lease epoch. The original outcome worker ID remains on terminal rows so an exact repeated delivery can be accepted without accepting an old epoch. Immutable source references identify external evidence without copying provider payloads or secrets into Keel.

| Current state | Allowed transition | Budget liability | Provider concurrency |
| --- | --- | --- | --- |
| `queued` | claim to `leased` | reserved | not held |
| `leased` | ambiguous result to `unknown` | unknown; full reserve retained | held |
| `leased` | confirmed charge to `succeeded` | settled at full observed charge | released |
| `leased` | definite no-charge to `no_charge` | reserve released | released |
| expired `leased` | bounded reaper to `unknown` | unknown; full reserve retained | held |
| `unknown` | authorized confirmed/no-charge reconciliation to terminal state | settled from reconciliation entry | released |

The budget-ledger transition and queue transition execute in one PostgreSQL transaction. A failed lease fence, policy check, ledger insert, or queue update rolls the whole transaction back. Exact same-source/same-amount replays are idempotent. Conflicting outcomes, sources, or epochs fail closed. Unknown jobs cannot be renewed, reclaimed, or automatically retried. Reconciliation cannot infer that a request was uncharged from a timeout; the injected authorization boundary must approve the actor, reason, decision, and opaque evidence reference.

Outcome transactions use the dedicated `keel_ai_worker` database identity; queue admission continues to use `keel_app`. Workers cannot directly update budget counters or reservations or insert ledger rows; a single guarded database routine couples each worker outcome and budget update. Reconciliation uses the separate `keel_budget_control` identity only after the injected authorizer approves the exact actor, reason, decision, and evidence reference. Deferred account checks reject counters that do not equal durable reservation and ledger totals. The integration contract attempts forged settlement, counter understatement, and reconciliation SQL as app and worker identities. Deployments must keep worker and budget-control credentials separate from ordinary app credentials and grant them only to their respective execution services.

The expiry scan is tenant-scoped and bounded to 1–100 candidates. Listing is advisory; each candidate is rechecked against the exact worker, epoch, and database-clock expiry while recording unknown budget liability and job state atomically. Concurrent reapers can safely race. Unknown attempts retain their execution-profile concurrency slot until reconciliation.

## Authorization and evidence limits

The repository fails closed when no K4.3 reconciliation authorizer is injected. The queue does not implement provider lookup, operator authentication, or evidence verification. Before an operator resolves an unknown attempt, an approved control plane must verify the provider's request/usage record or other authoritative billing evidence, enforce tenant and role scope, and record actor, reason, and immutable evidence reference. Only then may the injected authorizer approve the financial decision. `source_ref` is a locator, not proof by itself.

Confirmed usage records the full provider-reported amount, including any quote overrun; the K4.3 account blocks new admission when its hard limit is exceeded. A no-charge resolution is valid only when authoritative evidence proves no billable request was accepted. Unknown or unavailable provider evidence leaves the job and reserve unknown.

## Operations contract for a future runtime

The database slice ships no reaper process, heartbeat, metrics exporter, alert rules, or customer-facing recovery UI. These are release gates, not claims about current behavior. When the runtime is assembled, use these initial operational targets and qualify them with load tests:

- Run the bounded expiry scan at least once per minute per active tenant partition. Alert if the reaper heartbeat is older than two minutes.
- Warn when the oldest expired leased attempt has remained unreconciled for five minutes; page the on-call owner at fifteen minutes. Unknown attempts are expected to remain held when evidence is unavailable, so alert on age and count without automatically releasing them.
- Alert on provider concurrency saturation, blocked incompatible queued jobs, budget overruns/admission blocks, repeated reaper failures, and an increasing unknown-liability count. Include tenant-safe aggregate identifiers only; never put prompt, response, credentials, or provider payloads into metrics/logs.
- Track reaper candidates, successful transitions, stale-candidate skips, unknown attempt count/age, per-profile in-flight slots, queue age/depth, and reserved/committed/overrun spend. Export bounded-cardinality labels; tenant IDs belong in restricted diagnostics, not metric labels.

## Operator recovery

1. Stop new dispatch for the affected provider/model profile if attempts are accumulating or the provider's outcome API is degraded. Do not delete queue rows or reset lease epochs.
2. Inspect the job state, attempt ID, lease epoch, expiry, budget reservation, and append-only ledger using the approved tenant-scoped control plane. Repeatedly run the bounded reaper only to mark expired leased attempts unknown; do not interpret a successful reaper count as provider resolution.
3. Query the provider using its idempotency/request reference in the approved evidence system. If the provider confirms usage, reconcile the exact charge. If it authoritatively confirms no accepted/billable request, reconcile no-charge. If it cannot establish either result, keep the attempt unknown and escalate to the provider and finance/on-call owners.
4. Reconciliation must use an authenticated, tenant-scoped actor, a permitted reason code, and an immutable evidence reference. Review the resulting queue terminal state and budget ledger entry before restoring dispatch. Do not retry an unknown attempt; a future retry requires a separately admitted/reserved attempt and proven provider idempotency semantics.
5. For queued jobs no longer compatible with the active execution profile, keep dispatch disabled for those jobs and retain reservations until a separately authorized cancellation/settlement workflow exists. Do not edit the profile digest or job row directly.

## Migration and rollback

Migration `0027` is transactional and forward-only under the migration runner's checksum ledger. It adds outcome metadata, constraints, database functions, grants, and an expiry index. Applied migrations must never be edited or manually reversed. If rollout fails, disable AI admission/dispatch and preserve all queue and budget rows. Diagnose from a disposable copy, then ship a new forward migration or application fix. Do not roll application binaries back to a version that does not understand `unknown`/terminal outcome states; database rollback to `0026` is unsupported. Re-enable dispatch only after the fixed build passes migration, forced-RLS, settlement, and reconciliation checks.

## Verification

The disposable PostgreSQL 18 integration coverage exercises bounded expiry reconciliation, unknown reserve retention, no-charge and confirmed settlement, authorized reconciliation, identical delivery replay, stale epoch rejection, tenant isolation, app/worker direct-SQL rejection, counter consistency, queue fairness/concurrency, and atomic rollback when a queue terminalization trigger fails. Final CI results are the release record for merge.

# K2.3 Temporal workflow dispatch evidence

Tracked by [Keel issue #19](https://github.com/sanskarpan/Keel/issues/19) and [PR #120](https://github.com/sanskarpan/Keel/pull/120), which closes the issue. Each changed file is committed separately.

## Delivered behavior

- Migration `0010_supplier_workflow_dispatch` keeps mutable delivery state separate from immutable K2.2 intents. A trusted trigger creates one minimal dispatch record for every intent, including existing intents at migration time.
- A forced-RLS worker-only repository leases the earliest undelivered case version. Lease owner and monotonically increasing epoch fence stale workers. Database acknowledgement is conditional on the current, unexpired lease.
- Retries use deterministic bounded backoff and allowlisted error codes; raw Temporal errors and intent event data are never copied into dispatch state. After 12 attempts an intent dead-letters and blocks later versions for that case rather than silently introducing a gap.
- Temporal workflow IDs are opaque SHA-256 derivations of tenant and case UUIDs. Workflow type, task queue, and signal name are versioned. The signal contains only case ID, intent ID, event version/type and hash; tenant ID, policy, supplier, evidence, actor, upload metadata and PII are excluded.
- Workflow state accepts at most the K2.2 lifecycle bound of 102 distinct events, requires contiguous versions, ignores exact duplicate identities and fails on conflicting IDs/hashes or gaps. With at most 12 sends per intent, the initial case lifecycle is bounded to at most 1,224 signal attempts; K2.6 must qualify continuation/version changes before later K2 event types extend that bound.

## Security, operations and rollback

The database worker receives only the dispatch projection needed to signal Temporal; application, agent and supplier roles cannot read or mutate lease rows. The worker has no runtime mounting yet, and no external customer route or Temporal endpoint is live. Temporal is qualified only as a local synthetic dependency; hosted identity, credential rotation, retention, SLOs and production access controls remain K0/K0.1 gates.

`docs/RUNBOOKS.md` documents queue alert thresholds, dead-letter containment, escalation to the workflow operations owner, compatibility and rollback. K2.5 manual evidence review does not repair or unblock workflow delivery. Metrics, paging, a general repair/requeue operation and a named on-call owner remain unimplemented/unassigned; dead rows must not be reset by ad hoc SQL. Rollback stops delivery and retains the additive migration, immutable intents, dispatch state and Temporal histories. Workflow V1 and its signal contract remain persisted compatibility surfaces. There is no destructive down migration.

# K2.2 supplier case, evidence and workflow-intent evidence

Implementation is tracked by [Keel issue #18](https://github.com/sanskarpan/Keel/issues/18) and [PR #119](https://github.com/sanskarpan/Keel/pull/119), which closes issue #18. The PR is kept at one commit per changed file.

## Delivered behavior

- Review policies are immutable tenant-scoped versions with normalized digests, a deadline from one hour through 72 hours, at most 100 required evidence kinds and at most 32 explicit reviewer steps. Missing dependencies, duplicate steps and cycles are rejected; no tenant-supplied code is evaluated.
- Case creation freezes the policy ID/version/digest and takes its deadline from PostgreSQL time. A required principal-scoped `Idempotency-Key` deterministically identifies the tenant case; replay with a different supplier or policy conflicts.
- Cases have tenant-forced-RLS snapshots, append-only versioned events with a SHA-256 predecessor chain, and append-only evidence slot revisions. Case evidence is bounded to 100 records/100 MiB. The latest version in each slot must satisfy required policy kinds at submission; material evidence cannot change after submission.
- Evidence attachment reads facts from PostgreSQL and accepts only a clean extracted upload with matching media, byte count and digest, linked to an accepted, unexpired invitation for the same case. The DB trigger independently checks those facts, case state/deadline and aggregate evidence budget.
- Every event and its workflow intent are committed in one transaction. Deferred constraints require one matching intent per event, keep the snapshot version equal to a contiguous event history, and pair evidence rows with their exact evidence-added event. Intents are append-only. Case create, same-upload evidence attach, policy publish and submission retries are idempotent.
- Authenticated policy, case, evidence-attachment and submission HTTP handlers are specified and tested. They are intentionally not mounted by Keel's current runtime because trusted OIDC/session resolution remains a K0 gate.

## Boundaries and operational notes

These tests prove the deterministic domain and PostgreSQL contract; they do not prove Temporal dispatch/retry or approval/deadline race behavior (K2.3/K2.4), public API authentication/runtime exposure (K0), production identity/roles, notification delivery, provider qualification or operational SLOs. No customer case route is currently live.

Migration `0009_supplier_case_evidence_workflows` is additive and has no destructive rollback. A binary rollback must retain the applied migration and new tables; disabling the unmounted handlers does not remove case or evidence records. Any future data erasure must be a separately reviewed retention-safe operation. Operational ownership is Keel platform; a named on-call owner remains unassigned.

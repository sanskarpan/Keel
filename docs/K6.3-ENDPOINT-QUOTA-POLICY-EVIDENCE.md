# K6.3 slice: configurable tenant endpoint quota

Issue #401 (parent #48, checklist item K6.3). This slice makes the active-endpoint cap a per-tenant
policy with a safe default of 100, expected-version changes and append-only audit history.

## Durable model

Migration `0056_webhook_tenant_quota_policy` adds:

- `webhook_tenant_policies` with the tenant limit, monotonic version and update time;
- append-only `webhook_tenant_policy_history` with the change ID, new policy version, prior/new
  limit, operator principal and bounded reason.

Both tables are forced through RLS with all direct runtime grants revoked. History cannot be updated
or deleted. The effective limit is the policy value or 100 when no policy exists.

## Operator change

`keel_meta.set_webhook_endpoint_limit(change_id,requested_by,limit,reason,expected_version)`:

- Requires `keel_operator` and derives the tenant from the trusted context.
- Validates a bounded change ID, actor, limit (1-10000), non-control reason and expected version.
- Serializes per tenant and rejects a duplicate change ID.
- Creates at expected version zero, or updates only when the stored version matches.
- Appends the prior/new limit and new version to history.
- Returns the change ID, new version, effective limit and update time.
- Lowers a limit below the current active count without deactivating endpoints; new registrations
  and reactivations then fail closed until the tenant is under the limit.

`webhook.EndpointLimitChange`/`EndpointLimitPolicy` and
`postgres.Store.SetEndpointLimit` validate and map conflicts to `ErrEndpointPolicyConflict`.

Endpoint registration/status functions from migration `0054` are re-created to read
`webhook_active_endpoint_limit(tenant)`. No direct table access is granted.

## Verification

Coverage runs against a fresh PostgreSQL database with migrations through `0056`:

- create a limit of 1, register one endpoint, and reject the second with `ErrEndpointQuota`;
- raise to 2 and register the second;
- lower to 1 while two endpoints remain active; third creation is rejected and existing endpoints
  are not deactivated;
- updating an existing endpoint over the lowered limit remains allowed;
- stale expected versions and duplicate change IDs return `ErrEndpointPolicyConflict`;
- policy history contains one row per change and is immutable;
- app/webhook roles cannot change policy; the operator cannot read the policy table directly;
- request validation covers tenant, change ID, actor, limit, reason and expected version.

## Limits

No due-delivery/attempt/payload quotas, HTTP/UI, billing integration, automatic over-cap remediation
or production identity/mounting is added. The policy is tenant-wide; there are no per-endpoint
overrides.

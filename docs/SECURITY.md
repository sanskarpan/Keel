# Security and privacy design

## 1. Trust boundaries

Untrusted inputs include users, suppliers, uploaded files, document text, model output, provider responses and incoming callbacks. A model does not acquire authority because its output names a valid API command. Trusted policy is supplied by authenticated server configuration and signed deployment provenance, not user prompt text.

Public ingress, application workloads, extraction sandbox, database, event bus, identity provider, context vault and external integration egress are distinct boundaries. Each has separate credentials, network policy and audit. Tenant isolation is enforced at API authorization, storage, retrieval, cache, stream and database layers.

## 2. Threat and control matrix

| Threat | Required control | Verification |
|---|---|---|
| Cross-tenant record/cache/stream exposure | Auth-derived tenant, FORCE RLS, composite FKs, query-time ACLs, scoped keys/cursors | Malicious two-tenant suite across every surface |
| Agent changes custom tenant GUC or requests SQL writes | Session-user binding, SELECT-only roles, typed query tools, credentials withheld from model | GUC/SET ROLE/DDL/DML/function abuse tests |
| Prompt injection in supplier documents | Treat documents as quoted data, allowlisted read tools, independent command approval | Adversarial corpus; no approval/order mutations |
| Semantic cache wrong/unauthorized hit | Scope before search, context/version/access digests, entity/numeric/polarity checks | Labeled equivalence and permission-revocation suite |
| PII in logs/telemetry/errors | Structured allowlists, pre-emission redaction, no prompt content by default | Canary PII scans of logs/traces/metrics/error stores |
| Malicious PDF/DOCX/extraction payload | Quotas, type/magic checks, malware scan, sandbox/no network/resource limits | Bomb/recursive/archive/parser failure corpus |
| Webhook SSRF/DNS rebinding | Safe resolver/egress proxy, IP-range policy, connect-time recheck, redirect policy; K6.2 adds resolve-every-dial, any-answer denial, vetted-address pinning and redirect denial in `internal/delivery/webhook` | Metadata/private/IPv6/rebinding integration cases |
| Replay bypasses approvals or causes duplicate effects | Separate permission, sandbox read-only replay, same event/effect IDs | Replay and revocation tests |
| Model spends after budget/connection loss | Durable bounded reservation, token ceilings, per-attempt liability, pinned provider capability, no fallback after ambiguous acceptance/output, provider reconciliation | Concurrent admission, idempotency replay, pre-token fallback, and unknown-usage cases |
| Tenant quota bypass or doubled charge after Redis timeout | Home-region atomic token bucket, opaque tenant/route scope, stable request-ID replay; model/write routes fail closed; optional safe-read fallback uses durable PostgreSQL fleet and tenant caps, a <=60s regional window, policy-digest-bound receipts, and fixed-label telemetry | Multi-client shared Redis budget, exact replay/conflict, tenant isolation, PostgreSQL restart/scale and cap tests, expired-window closure, recovery-role/health-probe tests, and checks that fallback metric labels contain no tenant/request values. Redis failover ambiguity can add bounded fallback admissions; strict cross-authority exactly-once admission is not claimed. |
| Forged callback or key confusion | Exact-byte HMAC, timestamp tolerance, provider ID dedupe, key rotation; K6.2 implements the exact-byte HMAC, a strict key-ID header, a positive timestamp window, one-key overlap and the logical delivery identity | Signature/key-ID/timing/body-tamper tests |
| Compromised workload reads all secrets | Per-role workload identity, minimum IAM/DB grants, separate key providers | Runtime effective-access audit |
| Operator abuse | JIT break-glass, separate admin routes, immutable audit and approval policy | Administrative-action negative tests |

The K4.5 cache core binds opaque lookup keys to tenant, access, policy, prompt, tool, provider/model, context/source-set, locale, classification and cache-policy digests. This initial package permits only general-classification inputs and fails semantic candidates closed unless the verifier artifact and entity, numeric, date and polarity evidence match. It does not implement response storage or a production verifier; those require the separately reviewed encrypted-store, live-revocation and independently labeled quality gates in `docs/K4.5-CACHE-EVIDENCE.md`.

The K6.1 callback inbox is the verified-delivery side of the forged-callback control: only an injected verifier's event is trusted, the tenant comes only from that event, and the provider event identity is globally unique across tenants. The event record and its domain effect commit in one tenant transaction, so an exact redelivery cannot apply twice and a failed application leaves nothing to mistake for a duplicate. A same-ID/different-digest delivery or a same-ID delivery under another tenant applies nothing, returns one indistinguishable conflict error, and is written to an append-only ledger under the caller's tenant without disclosing the other tenant. Direct table access is revoked from every runtime role and all access goes through a keel_callback-gated security-definer pair under forced RLS; inbox rows are immutable. Digest binding exists, but signature verification, exact-byte HMAC, timestamp tolerance and key rotation are not claimed by migration 0039; K6.2 delivers them in `internal/delivery/webhook`. See docs/K6.1-CALLBACK-INBOX.md.

The K6.2 webhook package is the outbound counterpart. A signature is HMAC-SHA256 over the decimal timestamp, a dot and the exact body bytes, with the timestamp, key ID and MAC in one strictly parsed header; verification is constant time inside a positive five-minute window, and a one-key overlap keeps the previous secret verifying during rotation. The logical delivery identity (tenant, event, endpoint, subscription revision) is length-prefixed and stable across retries and replays, while each attempt takes a fresh ID, timestamp and signature. Egress is HTTPS-only on an explicit port allowlist, never uses environment proxies, requires TLS 1.2 or newer, resolves on every dial, denies a host if any answer is loopback, private, link-local, multicast, CGNAT, documentation, benchmark or reserved, and pins the vetted numeric address so a rebinding answer cannot move the destination; redirects are denied by default and re-validated when enabled. Migration `0040` enforces the identity durably: a `keel_webhook`-gated security-definer claim derives the tenant from the authorized transaction context, forced RLS and revoked direct privileges keep the ledger private, and rows are immutable. The package stores no delivery URL or signing secret; the reviewed worker runtime consumes it, but no production deployment is qualified. See `docs/K6.2-WEBHOOK-SECURITY.md`.

The K6.3 retry slice adds a durable schedule without widening that trust boundary. Migration `0041` stores per-delivery state and an append-only attempt log (outcome, status, latency, attempt ID and lease epoch) but no response body, snippet, URL or secret. Leasing and recording are capability-gated security-definer functions that derive the tenant from the authorized transaction context; direct privileges stay revoked, state rows cannot be deleted and attempts cannot be rewritten. A lease returns a bounded number of due or expired deliveries under a strictly increasing epoch, and the record function refuses a stale epoch or attempt number, so a duplicated or slow worker cannot overwrite a newer attempt. Exhaustion and permanent failure are terminal, and retry times are still chosen by the caller's scheduler, which rejects retries older than 30 seconds. This is not an SSRF or signature relaxation: a policy denial remains a permanent outcome. Circuit breaking, the delivery worker and tenant scheduling were added by later slices. Replay selection is pure and fails closed at the cap; it refuses delivered, pending or in-flight deliveries, stale subscription revisions, inactive or unresolved endpoints and missing signing keys, and returns only content-free skip reasons. Selection is not authorization or audit; the requeue slice adds the audited authorization, while the operator HTTP surface remains open. See `docs/K6.3-RETRY-EVIDENCE.md` and `docs/K6.3-REPLAY-EVIDENCE.md`.

The K6.3 endpoint registry adds a narrow, versioned target store without widening the webhook trust boundary. `keel_meta.webhook_endpoints` is reachable only through `keel_app`-gated register/status functions and a `keel_webhook`-gated resolve function; direct table privileges are revoked, forced RLS applies, identity and creation time are immutable, rows cannot be deleted and every change consumes a version so a stale registration or status change fails. Resolution returns the URL and key reference only for an active endpoint at the exact subscription revision, so a delivery cannot drift to a new URL under an old revision. URLs are sensitive because they may embed a receiver token: they are never logged, stored in an attempt row or included in an error, and only the resolving capability receives them. Registration enforces the static egress rules (HTTPS only, port allowlist, no userinfo or fragment, public host or literal address, bounded length and bytes) but deliberately leaves DNS and per-dial address vetting to K6.2 egress, so a hostname that later resolves privately is refused at send time. See `docs/K6.3-ENDPOINT-REGISTRY-EVIDENCE.md`.

## 3. Database agent boundary

The model invokes reviewed typed tools such as `search_policies`, `get_supplier_summary` and `get_order_summary`; it never receives a DSN, database credential, raw SQL tool or arbitrary database session. A query broker maps the authenticated principal to a per-tenant read-only PostgreSQL login. A protected `session_user -> tenant_id` mapping and fixed-path `SECURITY DEFINER` function bind each agent login to one tenant; RLS ignores caller-set tenant GUCs for those logins. Agent logins inherit only the SELECT-only `keel_agent` capability role and cannot become app, worker or migration roles. Provisioning creates the login and protected mapping together; revocation removes both under a controlled operation.

Read-only transaction mode is defense in depth, not the privilege boundary; a role may otherwise try to turn it off. Revoke INSERT/UPDATE/DELETE/TRUNCATE/CREATE and unsafe function execution. Use fixed search paths and qualified SECURITY DEFINER function names. Revoke PUBLIC schema-create privileges. Do not expose database introspection or unrestricted network/file functions through tools.

Trusted API and worker roles use `WithTenantTx` to set a transaction-local `keel.tenant_id` only after server-side authorization. PostgreSQL custom GUCs are caller-settable, so this protects against omitted tenant predicates and routine application mistakes; it does not make a compromised cross-tenant app/worker credential tenant-bound. Agent identities are separately bound by `session_user`. Scope service roles, audit context changes, enforce network separation, and offer a dedicated tenant database tier for customers requiring a stronger physical boundary.

Order read handlers accept tenant and principal identity only from trusted middleware context and require a resource authorization decision before querying. They return non-enumerating 404s for denied resources. Public timeline rows use a reviewed allowlist of event ID, version, type and occurrence time; private event payloads, actor references, evidence digests and trace/correlation IDs are excluded. History cursors use AES-256-GCM with a key ID, associated-data domain and seven-day expiry; the encrypted claims bind tenant, order and page size. Cursor key material is injected into the handler, never accepted from a request, and old keys remain available for the full token lifetime after rotation.

## 4. PII handling and context retention

Central Go logging and extraction/model adapters accept structured allowlisted fields. PII scrubbing runs before emission; raw request bodies, SQL parameters, document text, provider headers and tokens are not log fields. Unknown text is dropped or hashed when safe redaction cannot be established. Redaction is best effort for content supplied to a model; publishing a recall claim requires an evaluated entity corpus.

Encrypted prompt/context retention is disabled by default. A context write requires the tenant’s current enabled purpose policy and consent reference; immutable snapshots have bounded retention, and PostgreSQL derives record expiry from its own clock rather than a caller timestamp. The policy-authoring role cannot read ciphertext, and the vault role cannot author policy. Use envelope encryption with a production KMS/HSM key scoped to the qualified account/region and authenticated tenant/record context; object permissions verify tenant/context independently. Langfuse/OTel carries safe metadata and protected record references. Full-text prompt telemetry is disabled unless an explicit reviewed configuration enables an isolated, access-controlled deployment. Expired rows are hidden immediately. Context writes create a content-free expiry job in the same transaction. A separate erasure worker can only call tenant-scoped claim, process, and retry functions; it has no direct access to job metadata, receipts, or live ciphertext. The processing function inserts an immutable receipt with a SHA-256 digest over a versioned, length-prefixed binary envelope serialization and retention/consent references, deletes the expired envelope, and completes the fenced job atomically. The polling package is not deployed. A separate legal-hold capability writes content-free append-only events, cannot read ciphertext or retention policy, and requires bounded reviewed holds. Hold placement/review/release and every supported delete path serialize on the same record row; an overdue unreviewed hold remains active. No external actor-identity provider or legal workflow endpoint is wired. Provider backup/PITR/replica/restore qualification remains open under #300. Do not claim end-to-end erasure until hosted qualification and deployment gates are complete.

The read-only replay core (#306) uses a dedicated database capability and one-use content-free audit identity. It authorizes the exact tenant, actor, record, version, purpose and reason before storage or key access; the database checks expiry and holds again while locking the record across diagnostic delivery. The plaintext consumer is synchronous, receives a five-second context deadline, and handles at most 1 MiB, and the service exposes no model/tool/business mutation API. Replay-audit retention/archival and storage monitoring are not yet qualified; events are append-only and have no routine deletion path. The HTTP replay route remains unmounted. No production identity adapter, KMS/HSM profile, replay deployment or configured Langfuse export is qualified; do not use synthetic actor IDs or treat this library as an available customer endpoint. The internal Langfuse adapter (#308) constructs spans from a closed enum-only event contract, validates an optional opaque vault UUID, emits no arbitrary attributes/content, uses the current OTLP/HTTP API with TLS, explicit host allowlisting, bounded queue and finite request deadlines, and is disabled by default. It must not be connected until the K0.1 egress, credential, identity, retention and ownership decisions are approved. Context-vault erasure does not remove accepted Langfuse data or downstream copies; retention and deletion require separate provider controls and verification.

Context read/replay requires a diagnostic grant, current resource access, audit and expiry/legal-hold checks. Model replay is not authorized to issue writes, payment/order changes or outbound webhooks. Deletion invalidates lookup/cache/index references and removes all object versions; encrypted key destruction follows documented legal/backup commitments.

## 5. File and invitation security

Presigned URLs bind key, content length/type constraints, checksum and expiry; server-side completion validates actual stored object/version and authoritative type detection. A guessed upload ID is insufficient. Invitation tokens are purpose-scoped, short-lived, hashed and revocable. Supplier upload roles cannot read all case attachments or tenant search.

Extraction jobs run with no cloud admin credentials, restricted object access, no external network, CPU/memory/time/output-size bounds and isolated temporary files. Never pass an uploaded filename into a shell command. Virus scanning and content classification precede publication/index eligibility.

K2.1 enforces these boundaries in `internal/supplier/intake`: 256-bit purpose-separated invitation/session tokens are stored only as digests; recipient addresses are peppered HMAC digests; upload capabilities bind tenant, invitation, upload ID, declared size/hash, purpose and a <=15-minute expiry. The ingress validates the actual body before storing it and never persists the supplier filename. The local filesystem adapter is synthetic-only (0700 directory, 0600 UUID-named files, atomic create-if-absent). The separately granted `keel_file_processor` role has tenant RLS and only upload-row read/update access; lease epochs fence expired workers. Tika connects directly to the fixed internal endpoint, ignores proxy environment variables and rejects redirects. The CI sandbox runs ClamAV/Tika with no egress and bounded resources. Its bundled ClamAV signatures prove a deterministic contract only; production signature freshness/update ownership and encrypted/versioned cloud object storage are not yet qualified.

K2.2 case, policy, event, evidence and workflow-intent rows are tenant forced-RLS and app-role only. Policy versions and case evidence/history/intents have no app-role update/delete grants. Deferred PostgreSQL constraints couple each event to exactly one matching workflow intent and each evidence row to one evidence-added event; a separate trigger rejects case state/version changes without a corresponding contiguous event snapshot. Commands re-read and verify the full event/evidence digest chain while holding the case row lock. Evidence association independently checks active invitation case scope, the extracted upload's original checksum/size/media metadata, and 100-record/100-MiB case budgets. These controls protect application mistakes and tenant isolation; the unkeyed event digest is corruption detection, not a signature against a privileged database owner who can rewrite all related data. The deterministic case identifier is scoped by tenant, authenticated principal and required idempotency key. The API handler is not runtime-mounted and cannot be exposed until trusted identity resolution and authorization are wired under K0.

K2.4 adds FORCE-RLS approval-plan, reviewer-grant, delegation and decision tables. Submission freezes each exact policy step and evidence digest; deferred constraints reject an incomplete plan. The case app can read grants/delegations but cannot mutate them or decision history. Decision triggers lock the case row before capturing PostgreSQL acceptance time, deny the creator/submitter, validate one active direct grant or non-chained delegation, require approved prerequisites, and reject the deadline boundary. Each immutable decision must match its event timestamp/content, case snapshot and durable workflow intent. Migration `0012` independently rejects expiry events unless the case is collecting or submitted, the persisted deadline matches the event, the expiry actor is the service principal, and event time is between deadline and database now. Submitted cases must have the frozen complete plan; collecting cases can expire without one. The API body cannot choose tenant, actor or role; the handler takes identity from trusted context and PostgreSQL derives the role from the frozen plan. Grant/delegation provisioning and hosted identity remain unavailable until K0/K0.1; the route is unmounted. Direct app credentials are trusted workload credentials, not a defense against arbitrary SQL under a stolen app login.

K2.5 adds an independent lifecycle-event trigger for cancellation and manual-review request/resolution. Cancellation requires a principal actor and database time strictly before the persisted deadline; the locked case transition revokes invitations and terminal-state triggers cancel pending/leased activity effects. Intake guards separately reject new invitation/session/upload writes after collection ends while allowing safe rejection/expiry cleanup. Manual review binds an existing extracted evidence digest, requires a current reviewer grant/delegation and denies creator/submitter; confirmation only attests to evidence content and never bypasses scanning or the approval plan. The effect table is worker-only for reads/updates, uses stable unique keys and immutable payload digests, bounded attempts, owner/epoch leases and a restricted context function that returns only current principal refs/state/deadline. Current reminder routing includes only active reviewers in the frozen plan; supplier/requester notification routing is absent, and effects due before submission are no-ops. External reminder effects are at-least-once unless the configured sink deduplicates by effect key and payload digest. No provider credentials, recipient addresses, evidence, reasons or supplier identifiers enter workflow payloads/general logs. Runtime mounting and provider qualification remain gated; arbitrary SQL under a compromised app login remains outside the database-role threat boundary.

## 6. Identity and keys

OIDC exact issuer/audience and asymmetric algorithm allowlist; reject algorithm confusion and missing expiry. Key cache has bounded stale use only for already-known signing keys; unknown keys fail closed during issuer outage. API keys are high-entropy secrets hashed at rest, scoped, rate-limited and rotated/revoked; display once.

History-cursor encryption keys are separate from OIDC, API-key and database credentials. Keep a versioned key ring in the deployment secret provider; do not log tokens or claims. Removing an old key before its seven-day token expiry intentionally invalidates those cursors and should be treated as a user-visible pagination reset.

Cloud access uses workload identity, not static environment credentials shared across roles. DB/API/provider secrets rotate with overlap and short cache lifetimes; rotation does not require image rebuild. TLS is required to every remote dependency; private networking does not justify disabled verification.

## Kafka broker transport

Only the named `NewLocalSyntheticBroker` and `NewLocalSyntheticConsumer` constructors permit plaintext, and they accept only loopback endpoints or the fixed `kafka` alias used by the local Compose network. Runtime/remote callers must use `NewSecure` and `NewSecureConsumer`; those constructors require an explicit non-empty CA pool, TLS 1.2 or newer, normal Go hostname verification, and SCRAM-SHA-512 credentials. The client does not fall back to system roots or plaintext. Client certificate overrides, custom verification callbacks, and TLS key logging are rejected so application callbacks cannot weaken broker identity checks or expose session secrets. Client TLS session caches are cleared for each generation so trust rotation requires a fresh certificate handshake.

Production deployments must load the CA bundle and SCRAM username/password from the secret/configuration provider. Keep the broker DNS name in the address (or set the exact expected `TLS.ServerName` when connecting through a proxy); the certificate SAN must cover that name. Trust is limited to the configured CA pool. Roll CA trust with an overlap pool containing both old and new roots, deploy/reload clients, then remove the old root after brokers have rotated certificates. Rotate SCRAM credentials with a second valid principal: call the relay's `RotateSecurity` after provisioning it, then revoke the old principal only after all clients have reconnected. Rotation validates the next config before swapping generations; publishes and consumer runs serialize with the swap, close old connections, and use the new TLS/SASL config on reconnect. Consumer offsets not committed before rotation are replayed through the idempotent projector inbox.

Kafka transport errors are redacted for the active username and password before returning to callers. Do not log `SecurityConfig`, TLS config dumps, secret-provider payloads, or raw authentication handshake data. The CI contract generates ephemeral broker/CA keys and tests valid SASL-over-TLS, untrusted CA, hostname mismatch, rejected credentials, and producer/consumer reconnection using rotated credentials. These fixtures do not qualify any managed Kafka service or replace runtime secret injection and deployment-specific broker trust configuration.

## 7. Security release requirements

Order trace correlation crosses Kafka only in additive schema v2 and only from protected event metadata that passed the strict W3C parser. The broker header must occur once and exactly match the envelope. The projector quarantines malformed, duplicate, unsupported or mismatched values before changing projection state. The traceparent is not an identity, tenant claim, partition key, authorization input or deduplication key. Public APIs and state feeds remain trace-free. A child consumer span is correlation context only; this does not enable an exporter. See `docs/K5.3-OUTBOX-CORRELATION.md`.

Relay/projector telemetry uses the fixed `outbox.publish` and `projector.process` operations and allowlisted outcomes. It omits event, tenant, aggregate, partition, offset, payload, header, and raw error values. A trace ID is emitted only after strict traceparent parsing; trace/span IDs are omitted for schema v1 or invalid context. The logger adapter bounds elapsed duration, schema version, and retry count before logging. Custom observers must remain non-blocking; panics are contained and cannot alter durable publish/projection results or offset-commit decisions. These hooks are not a telemetry exporter; see `docs/K5.3-RELAY-TELEMETRY.md`.

Order repository telemetry uses fixed operations and the `ok`, `not_found` and `error` outcomes, and runs after the transaction has finished rather than inside it. It omits tenant, order, event, aggregate, idempotency-key and principal-binding values, SQL statements, argument values, query plans, row contents, and raw database errors, so constraint names and connection details cannot reach the log pipeline. Envelope schema and retry fields are restricted to the messaging operations. Observation is an optional constructor option with a no-op default and cannot change a transaction, FORCE RLS, authorization, idempotency, ordering, or return value; observer panics are contained. This is not a SQL span or exporter; see `docs/K5.3-REPOSITORY-TELEMETRY.md`.

Database statement telemetry uses only the `query.read` and `query.write` operations with the `ok` and `error` outcomes. The recorder accepts a statement class, an elapsed duration, and the statement error, so statement text, argument values, row contents, identifiers, and raw database errors have no field to travel in and are dropped where the statement is executed. Statement timings are buffered while the transaction runs and published after it finished, so observation cannot extend a transaction or hold database locks open. A statement that returned no row is reported as a successful statement. Buffering per operation is bounded, and observer panics cannot alter a transaction, RLS decision, authorization result, idempotency outcome, or ordering guarantee. This is not a SQL span, query-plan record, or exporter; see `docs/K5.3-QUERY-INSTRUMENTATION.md`.

Release fails on tenant leakage, agent privilege escalation, plaintext credential/PII canary leakage, unbounded parser resource use, unsigned/unverifiable artifacts or an unresolved exploitable critical dependency issue. Lower findings require a named owner, exploitability assessment and bounded exception expiry. Threat-model changes accompany new tools, endpoints, external providers or tenant-scope changes.

## 8. Expanded SaaS and purchasing boundaries

Organization/customer billing mapping is server-owned; signed subscription metadata does not replace verified tenant mapping. Billing role can reconcile entitlements/invoices but cannot approve orders or transfer procurement/AI balances. Subscription restriction blocks costly admissions while preserving safe closure/export and established workflow authority. Hosted processor handles subscription cards; supplier banking/card/payment instructions are outside product scope.

Supplier principals have tenant/supplier/resource grants, no internal membership. Internal/external threads, exports, notifications, search diagnostics and counts enforce current visibility. Business-unit scope adds permission filtering beyond tenant RLS; its revision participates in retrieval/cache/context eligibility. Owner/group/delegation changes revoke new authority; accepted decisions remain historical until an audited invalidation/supersession command. Final plan completion and budget conversion remain atomic.

K3.5 adds a forced-RLS retrieval source eligibility ledger keyed by tenant, exact visibility cohort, and immutable source version. A withdrawal is one-way and blocks new lexical staging, current lexical/vector candidates, and stale build publication. Query and publication transactions lock candidate/source eligibility so concurrent revocation has defined ordering; stale repeatable-read serialization errors must fail closed. The app role can suppress an existing source and create a durable `fenced` erasure request, but cannot reactivate a tombstone. The citation resolver rechecks the live fence while a supplied source-range reader fetches exact bytes, then checks byte length, UTF-8, nonblank content, and digest. The scope is cohort eligibility only: upstream user/group ACL resolution, a concrete source-content store, caches, and physical/cryptographic/backup erasure are not implemented. A fenced request is not proof of erasure completion, and no physical-cleanup worker is enabled.

Scoped workers keep distinct billing, email/chat, ERP and context/provider secrets. All new provider inputs use signature/inbox/dedup and bounded egress; notification templates and exports prevent header/HTML/spreadsheet injection. Risk questionnaires/contracts/invoices are untrusted documents, not model system instructions. Simulations/analytics are read-only, bounded and authorized; an AI suggestion cannot become an approval/override/PO issue by sharing a backend library.

The tenant cost read model exposes spend classes, not content. It returns confirmed, estimated, unknown and outstanding amounts in integer micro-USD, a liability state, the tenant-scoped opaque inference identifier, period bounds, currency, hard limit and a watermark; it never returns prompts, responses, model or provider identifiers, rate-card contents, principal bindings, request digests, ledger source references or ledger reasons. Both reads run inside one read-only repeatable-read tenant transaction, so the account, reservation and ledger tables enforce forced tenant RLS and a tenant cannot observe another tenant's cost, including by naming another tenant's period. A period the tenant cannot read is reported as unavailable rather than as an empty period, and the per-inference result set is bounded. The read model recomputes from the append-only ledger instead of maintaining a rollup, so it cannot drift from the durable cost record. It has no mounted route, exporter, alerting or entitlement effect; exposing it to a tenant or operator surface requires its own authorization, identity and audit review. See `docs/K5.5-COST-DASHBOARD.md`.

The tenant cost read API derives the tenant only from trusted authentication context and requires an explicit authorization decision for every read. A denied view is answered as not found, so the response cannot be used to probe for cost data, and an unavailable authorization decision is answered as unavailable with no data. Responses carry only allowlisted cost fields: period identity and bounds, currency, limit, the cost classes, the carried amount, the blocked flag, the watermark, and per-row cost class, liability state and the tenant-scoped opaque inference identifier. They are uncacheable, carry the standard security headers, and are correlated by the shared HTTP middleware without adding identifiers to the body. The routes are documented in the OpenAPI contract and a contract check fails when a served route is not documented. No runtime mounts the handler, so exposing cost data to a tenant or operator surface still requires its own identity, authorization, audit and retention review. See docs/K5.5-COST-API.md.

Spend alert evaluation produces fixed codes, fixed severities, micro-USD amounts, thresholds and period identity, and nothing else: no prompt, response, model or provider identifier, principal binding, request digest, ledger source reference or customer content. Thresholds are immutable and code-owned, every ratio is bounded integer arithmetic, and each evaluation is bound to the policy digest that produced it, so an alert cannot be explained by thresholds that were not applied. The anomaly check compares a tenant only with its own settled history and never with another tenant, so a spend signal cannot become a cross-tenant side channel. A tenant without qualifying history is reported as not qualified rather than as a clean result, so a missing signal is never read as an all-clear. The evaluation persists nothing and delivers nothing; wiring alerts to a notification, escalation or tenant-visible surface requires its own authorization, delivery, acknowledgement and audit review.

Enterprise federation/SCIM/domain claims are verified and cannot hijack organizations; directory disable defeats stale JIT events. Support access is JIT/purpose scoped and audited. New product releases must pass malicious supplier, member-revocation, billing/order-decision races, form/rule cycles, entity leakage and connector scope tests before expanding availability.

K2.3 Temporal dispatch state is isolated from immutable intent/evidence data. Only `keel_worker` can read and update the forced-RLS lease table; it uses the tenant context to authorize the claim and hash the tenant/case pair into an opaque workflow ID. App, agent and supplier-facing roles cannot read dispatch metadata or mutate lease state. Expired claims increment a fencing epoch, so an old worker cannot acknowledge a newer claim. The worker sends no tenant ID, case event body or supplier/evidence field to Temporal; signals contain only the case ID, intent ID, version, event type and hash. Signal payloads are schema-validated and sequence-checked in deterministic workflow code; gaps and conflicting duplicates fail closed. Retry records store an allowlisted error code, never raw provider errors. Temporal logs and histories still contain durable case identifiers and hashes and require the configured service's access controls/retention; production hosting and a named alert/repair owner remain unqualified.

The K6.3 breaker state is tenant-scoped and content-free, and it stays behind the webhook capability. `keel_meta.webhook_endpoint_breakers` stores only status, counters, cooldown timing and admitted probes; load and save are `keel_webhook`-gated security-definer functions, direct privileges are revoked, identity is immutable and rows cannot be deleted. Saves are optimistic: a stale worker receives a version conflict instead of overwriting a newer decision, so an outdated view cannot close a breaker that another worker just opened or revive a cooldown. The application capability cannot read or write this state, and the row holds no URL, key, body or receiver data. See `docs/K6.3-BREAKER-STATE-EVIDENCE.md`.

Manual replay requests are an operator audit record, not a delivery authorization. `keel_meta.webhook_replays` stores only the tenant, delivery ID, caller-supplied replay ID, operator principal and a bounded non-control reason; it holds no URL, key, signature, payload or receiver response. Rows are immutable, cannot be deleted, are forced through RLS and grant no direct access to any runtime role. Record and lookup are `keel_operator`-gated security-definer functions that derive the tenant from the authorized transaction context; an exact retry is idempotent, while reuse of a replay ID with different fields or a second replay for the same delivery is refused. The record proves who asked and why; the requeue slice below adds the authorization and state transition, and the worker still rechecks the endpoint and key at send time. Replay execution and the operator HTTP surface remain open. See `docs/K6.3-REPLAY-REQUEST-EVIDENCE.md`.

The replay requeue is an operator capability, not a webhook one. `keel_operator` alone can execute `authorize_webhook_replay_requeue`, which derives the tenant from context, locks the failed/exhausted state, rechecks an active endpoint at the exact subscription revision (without returning its URL), records the immutable replay and transition rows atomically, and returns the delivery to pending. It preserves the attempt counter, first attempt and lease epoch, so replay cannot manufacture extra attempts. The transition table is append-only, forced through RLS and denied to every runtime role; the state guard admits only the matching audited transition. The database checks a key reference, but the runtime keyring is still checked at send time, so a key removed after authorization fails closed. See `docs/K6.3-REPLAY-REQUEUE-EVIDENCE.md`.

The K6.3 worker keeps the existing capability split: it uses only the `keel_webhook`-gated lease, record, breaker and endpoint-resolution functions over one authorized tenant, and it never accepts a tenant from a lease, endpoint or payload. Breaker admission is persisted before a half-open probe is sent and the outcome is saved with the loaded version, so workers cannot silently exceed the probe bound or overwrite a newer decision; a conflict before sending skips the lease. A breaker denial is recorded as a retryable HTTP-0 attempt with a next time after the cooldown, which is content-free and spends the delivery's attempt budget, so an outage can exhaust a delivery. The loop does not log: delivery IDs are safe, but endpoint URLs and transport errors may carry receiver tokens. Content-free metrics now cover backlog, attempts and outcomes; a content-free log contract remains open. Payload bytes are fetched by an injected source and bounded by the executor; no payload, URL or response body is written to the attempt ledger. See `docs/K6.3-WORKER-LOOP-EVIDENCE.md`.

The fanout producer runs under the application capability but returns no endpoint data. `keel_app` alone can execute `fanout_webhook_deliveries`; the function derives the tenant from context, accepts only a canonical event that exists in that tenant's outbox, selects only active endpoints and inserts through the schema-owner RLS policy. A caller cannot name a tenant or an endpoint and receives only an inserted count, so a compromised application session can trigger deliveries for its authorized tenant but cannot enumerate destinations, read URLs or keys, or cross the tenant boundary. The delivery ledger's unique identity makes repeat and concurrent calls harmless. Fanout failure aborts the order command, which is a deliberate availability trade-off rather than a security bypass. See `docs/K6.3-DELIVERY-FANOUT-EVIDENCE.md`.

Tenant discovery is a narrow metadata capability. `keel_webhook` alone can execute `list_webhook_delivery_tenants`, which returns only tenant IDs with a pending delivery due now or an expired in-flight lease, bounded and ordered by due time; it returns no delivery, endpoint, URL, payload, attempt or state data. The webhook capability is already trusted to lease and process any tenant context, so this lowers the cost of guessing tenant UUIDs but does not widen access to delivery content. The scheduler validates every returned ID and never takes a tenant from a lease, endpoint or receiver. The `webhook-worker` process holds one active and at most one previous signing key from base64 environment configuration; it never logs the key or DSN, and an endpoint whose key ID is not in that keyring fails closed as permanent. The process keyring is not a per-endpoint key provider, and production secret-provider/KMS qualification remains open. Readiness requires a live database and a recent successful discovery pass, so a failed scheduler is not reported as ready. See `docs/K6.3-WORKER-RUNTIME-EVIDENCE.md`.

Webhook metrics are content-free and low-cardinality. The recorder emits only fixed outcome labels (`delivered`, `retry_scheduled`, `exhausted`, `failed`, `deferred`, `skipped`) plus aggregate counts and ages for due tenants, due deliveries, discovery, attempts and tenant errors; it never records tenant, endpoint, event, delivery, URL, payload or error strings. The series are process-local and reset on restart, so they are operational telemetry, not an audit or billing source. The management endpoint must stay private and authenticated by network policy before deployment. Fanout itself is not counted at the producer; due deliveries are the worker-visible backlog. See `docs/K6.3-WEBHOOK-METRICS-EVIDENCE.md`.

The payload source stays inside the webhook capability. `keel_meta.read_webhook_delivery_body` derives the tenant from the authorized context, resolves the delivery's canonical UUID event to `event_outbox.safe_envelope`, and returns only `application/json` bytes bounded at 1 MiB; it never returns a URL, key, signature, private `order_events` content or receiver response. The function is `SECURITY DEFINER` with a fixed `search_path`, and execute is granted only to `keel_webhook`; the webhook role still has no direct outbox select. The worker receives the trusted tenant explicitly, validates delivery/tenant/event agreement, and treats a missing, oversized or mismatched body as permanent. The command-time fanout producer commits the outbox row and its deliveries together, so a claimed delivery has a committed envelope. See `docs/K6.3-PAYLOAD-SOURCE-EVIDENCE.md`.

The K6.3 attempt executor is the only path that produces a signed outbound request. It refuses to send when the delivery and the resolved endpoint disagree on tenant, endpoint ID or subscription revision, when the endpoint is inactive, or when the keyring does not hold the endpoint's key reference, so a stale registry row cannot redirect an event under an old revision or key. The request body is bounded at 1 MiB and the receiver body is drained at most 64 KiB and discarded; nothing from the response is returned or stored. The destination comes from the registry, is re-checked against the static egress rules and is resolved/vetted again on the dial; proxies are never used and redirects are not followed by default. Send-time errors are converted to content-free outcomes because Go transport errors can embed the destination URL, which may contain a receiver token; only invalid input and data-integrity mismatches return errors, and those consume no attempt. See `docs/K6.3-ATTEMPT-EXECUTOR-EVIDENCE.md`.

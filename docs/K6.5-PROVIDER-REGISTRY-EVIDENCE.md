# K6.5 slice: multi-provider HMAC registry

Issue #456 (parent #50, checklist item K6.5). This slice generalizes the synthetic verifier
into a configured multi-provider HMAC registry. No migration was needed and no inbox
behavior changes.

## Contract

- `Registry` holds one entry per provider name with its own secret, tenant binding, key
  reference and skew window; `Verify` dispatches on the request provider and rejects unknown
  providers fail-closed with `ErrUnauthenticated`, applying nothing.
- `SyntheticVerifier` behavior is preserved exactly (including the provider-mismatch
  `ErrInvalidCallback`) by delegating to the shared entry logic; all pre-existing tests pass
  unmodified.
- Registry construction rejects empty configs, malformed providers, duplicate names, zero
  tenants, short secrets and bad key references.
- Coverage includes per-provider dispatch with tenant/key checks, cross-secret rejection,
  unknown-provider and nil-registry denial, a seven-case config matrix, and an inbox
  integration test proving the same event ID applies once per tenant under two providers
  with one observation row each and no conflict.

## Limits

Every entry still uses the same code-owned HMAC wire contract; vendor-specific signature
schemes, rotation and tenant-resolution rules remain open, as do late-callback business
policy and production deployment.

  isolated database provisioned with tenant roles, `vector` and the full migration bundle
  (max applied 62).

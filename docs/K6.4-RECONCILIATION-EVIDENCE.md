# K6.4 slice: dry-run webhook delivery-gap reconciliation

Issue #379 (parent #49, checklist item K6.4). PR #380 merged as
`cd6d85f3cb046537d0c905186295144164ac6d73`; contract CI #619 passed on reviewed head
`be0ddc7fd2430c4aca88795ee1a51a0971737fc9`. This slice adds a bounded, operator-audited dry-run
scan that reports outbox events missing deliveries for current active endpoints, persists the run
and per-event gaps, and advances a durable cursor. It creates no deliveries.

## Durable model

Migration `0051_webhook_reconciliation` adds:

- `event_outbox(tenant_id,created_at,event_id)` for cursor scans;
- `webhook_reconciliation_cursors` with one monotonic `(created_at,event_id)` watermark per tenant;
- append-only `webhook_reconciliation_runs` with the operator principal, start/next cursor,
  scanned event count, gap-event count and missing-delivery count;
- append-only `webhook_reconciliation_gaps` with one event ID, creation time and missing count per
  run.

All three tables are forced through RLS, expose only a schema-owner policy, and grant no direct
access to any runtime role, including `keel_operator`. Run and gap rows cannot be updated or
deleted; cursors cannot move backward or be deleted.

## Planner

`keel_meta.plan_webhook_reconciliation(run_id,requested_by,from,limit)`:

- Requires membership in `keel_operator` and derives the tenant from
  `keel_private.current_tenant_id()`.
- Validates a bounded run ID, audit actor and page size of 1-500.
- Serializes per tenant with a transaction advisory lock.
- Resumes from the cursor; `from` is required only when the tenant has no cursor and cannot be in
  the future.
- Scans outbox events in `(created_at,event_id)` order, up to the page limit.
- Joins current active endpoints at their current subscription revision and counts endpoints whose
  ledger identity has no delivery.
- Writes the run, per-event gaps and next cursor atomically, then returns every scanned event with
  its missing count.
- Refuses a duplicate run ID and never creates or mutates a delivery.

The Go `ReconciliationRequest`, `ReconciliationEvent` and `ReconciliationPage` types validate the
same bounds, and `postgres.Store.PlanReconciliation` maps duplicate runs to
`ErrReconciliationConflict` and missing/invalid start input to `ErrInvalidReconciliation`.

## Semantics and limits

The registry stores only the current endpoint status and revision. The planner therefore cannot
distinguish an endpoint that was inactive when the event was appended from an endpoint that was
missed by a producer failure. It reports against current active endpoints and does not reconstruct
historical endpoint state. It also does not scan events below the cursor, reset the cursor, create
deliveries, re-run fanout, fetch remote provider state or expose an operator HTTP surface.

Repair execution is covered by a separate slice (`docs/K6.4-RECONCILIATION-REPAIR-EVIDENCE.md`).
That repair is an explicit operator action against current active endpoints and records an
append-only audit; the planner itself still creates no delivery and reconstructs no historical
endpoint status.

## Verification

Coverage runs against a fresh PostgreSQL database with migrations through `0051`:

- a two-event first page advances the cursor, records two gaps and creates no delivery;
- the second page resumes at the third event and a third page is empty;
- duplicate run IDs return `ErrReconciliationConflict`;
- an existing delivery for the current endpoint/revision is not reported;
- a fresh tenant without `from` returns `ErrInvalidReconciliation`;
- another tenant's event is not scanned;
- application and webhook roles cannot execute the planner; the operator cannot read the
  reconciliation tables directly; run rows are immutable;
- request validation covers tenant, run ID, actor, start time and page bounds.

Linux CI covers the race detector.

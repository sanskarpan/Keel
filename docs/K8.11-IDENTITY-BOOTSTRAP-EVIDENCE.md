# K8.11 slice: first-party identity bootstrap, verified email and session lifecycle

Related to #70 (K8.11 partial; does not close it). This is the slice that makes
sign-in possible at all: a first-party principal can register with an email and
password, verify the email within a bounded window, and hold exactly one usable
session that can be revoked. Owner MFA, recovery, lockout protections and any
HTTP surface remain open under #70.

## Contract

- New `internal/auth` domain package (per `internal/README.md` the auth boundary
  belongs to the auth/tenancy/organizations group):
  - `token.go`: 256-bit URL-safe secrets, purpose-separated SHA-256 digests
    (`identity-session-v1` / `identity-email-verification-v1`; a digest for one
    purpose never verifies as another), peppered HMAC email digests
    (>= 32-byte pepper) and canonical email validation. Raw emails, tokens and
    passwords are never stored; only digests/hashes leave the process.
  - `credential.go`: Argon2id hashing in PHC form (`$argon2id$v=19$m=...`) with
    bounded parameters (64 MiB / t=3 / p=1 production default, reduced profile
    only for tests), bounded password lengths and fail-closed verification
    (parse failure is an error, mismatch is a boolean).
  - `session.go`: TTL bounds (session 1 min - 30 days, verification 5 min -
    24 h) and `Session.Valid`, which fails closed on any stored revocation,
    expiry, empty principals or a principal that is not `active`.
- Migrations 0063-0065: four forced-RLS `keel_meta` tables
  (`identity_principals` keyed by unique email digest, `identity_credentials`,
  `identity_email_verifications`, `identity_sessions` with a 30-day window
  constraint) plus guard triggers and seven SECURITY DEFINER functions gated on
  the new `keel_identity` capability (mirroring `keel_callback`/`keel_webhook`
  from 0039/0053). The capability login has zero direct table grants; access
  exists only through the functions, which re-check `pg_has_role` internally.
- `internal/auth/postgres` repository over those functions with sentinel
  outcomes (`ErrNotFound`, `ErrConflict`, `ErrTokenReuse`, `ErrNotVerified`,
  `ErrCapabilityDenied`, `ErrInvalidRecord`); per-call transactions, no shared
  state, race-checker compatible.
- `deploy/compose/init/20-keel-tenant-roles.sql`: adds `keel_identity` (NOLOGIN
  capability role) and `keel_local_identity` (local-only login carrying the
  capability). `Makefile` adds `local-identity-test`; `.github/workflows/
  contract.yml` passes `KEEL_TEST_IDENTITY_DATABASE_URL` in both env blocks.
- Sign-in flow semantics encoded at the DB boundary: bootstrap duplicates are an
  outcome (`duplicate_email`), verification tokens are single-use and
  replace-on-resend, sessions require an active principal, and a revoked
  session is terminal.

## Verified

- `go test ./internal/auth/`: pass - purpose separation, short-pepper and
  malformed-email rejection, hash/verify lifecycle (including algorithm
  downgrade refusal, truncated-hash mismatch, bounds), session validity
  (revoked/expired/pending/disabled all invalid) and TTL bounds.
- Full migration chain applied live in the local compose PostgreSQL through the
  runner (`/tmp/keel-migrate migrate`): `keel_meta.schema_migrations` records
  0063, 0064 and 0065; all four identity tables exist.
- `go test -c ./internal/auth/postgres` run inside the PostgreSQL container
  against the real capability roles
  (`KEEL_TEST_IDENTITY_DATABASE_URL` as `keel_local_identity`):
  `--- PASS: TestPostgreSQLIdentityBootstrapAndSessionLifecycle`.
  The test proves on a real database: bootstrap with a pending principal;
  duplicate email as a distinct conflict (via the 0064 forward repair, not a
  raw 23505 abort); unknown-vs-malformed email convergence; wrong/right
  password against a stored Argon2id hash; session refusal before
  verification; under-min TTL rejection; single-use verification with
  `duplicate` and `unknown` outcomes; pending->active transition through
  `consume_identity_verification` (guard trigger); session record/resolve at
  30 days and token reuse refusal; revoke then re-resolve judged invalid;
  unknown-session lookup; second principal isolation; plus the structural
  lockdown check - FORCE RLS on, and no grants to any non-owner principal on
  the four tables - and denials for `keel_local_app` (function execution) and
  `keel_local_identity` (direct table read).
- Cross-role environment reproducibility requires the updated role bootstrap;
  `make local-roles` re-applies it idempotently to an existing volume.
- `go build ./...`, `go vet ./internal/auth/...` and `gofmt` clean for the new
  files; `go test ./...` green except a pre-existing Windows-only quarantine
  file-mode test failure in `internal/supplier/intake` (mode readback 666 vs
  want 600 - a Unix permission check; CI runs on Linux).

## Limits

- No HTTP route mounts yet: registration, login, verification and logout
  endpoints are unmatched; this slice is the storage/domain contract only.
- No owner MFA, no recovery flow, no lockout/rate limiting, no password
  rotation, no credential-rotation trigger, no audit trail: explicitly out of
  this slice per #70's scope.
- Pepper provisioning is not wired: tests pass a fixed in-process pepper;
  production needs a pepper source with the same fail-closed property
  (deployment config work under K8).
- Delivery of the verification email (actual email transport) is unimplemented;
  K-F01/K8.10 email sandbox qualification stays open.
- Tenant binding of principals (`tenant_id` is nullable, unused by the
  capability functions) is deferred to the K8.1/K8.2 organization/membership
  slices.
- The DB `identity_sessions` window caps at exactly 30 days; session
  refresh/sliding expiry is not modeled and needs a later explicit decision.

# K7.5 slice: free Grafana OnCall escalation targets replace PagerDuty

Related to #56 (K7.5 partial; does not close it). Owner direction 2026-11-02 selected
Grafana OnCall (self-hostable, free/OSS) as the paging escalation product after the
2026-11-01 cost-based PagerDuty removal, so the two receivers now expose OnCall
integration URLs without giving up the verified local delivery path.

## Contract

- `deploy/monitoring/alertmanager/alertmanager.yaml`: each receiver (critical and
  warning) posts to two targets in order of width: the committed loopback alert sink
  `http://127.0.0.1:19095/hooks/ops-alerts` that keeps the PR #475 delivery evidence
  valid, and a Grafana OnCall integration URL read from
  `/run/secrets/oncall-critical-url` / `/run/secrets/oncall-warning-url`. Real
  integration URLs are NOT committed; each operator mounts them at deploy time.
- Routing, fixed-label grouping (`service/component/alertname`) and the WorkerDown
  inhibition rule are unchanged; only receiver internals changed.
- Schedules, rotations, escalation chains, acknowledgement and repeat paging become the
  responsibility of Grafana OnCall once an integration URL is mounted; Alertmanager
  route editing is no longer the escalation mechanism.

## Verified

- `amtool check-config` (pinned `prom/alertmanager:v0.28.1` image): SUCCESS - global
  config, route, 1 inhibit rule, 2 receivers.
- `promtool check config` (pinned `prom/prometheus:v3.13.4` image, Compose mount
  layout): SUCCESS, 4 rule files, 18 rules (4 rate-limit + 8 webhook + 4 reconciliation
  + 2 SLO). Compose `--profile monitoring config` validates.
- Live boot with the new dual-target config under Docker Desktop: configuration loads,
  gossip settles, `/-/healthy`-equivalent serving on `127.0.0.1:19093`.
- End-to-end delivery re-proven: `amtool alert add alertname=KeelWebhookWorkerDown
  severity=critical` reached the sink
  (`{"alertname":"KeelWebhookWorkerDown","status":"firing","severity":"critical"}`).
  With no OnCall URL file mounted, `webhook[0]` (sink) delivered while `webhook[1]`
  (OnCall) fails closed and loudly:
  `Notify for alerts failed ... keel-critical-oncall/webhook[1]: ... read url_file:
  open /run/secrets/oncall-critical-url: no such file or directory`. Nothing is lost
  silently; firing state stays visible in the Alertmanager UI. Test container also
  proved boot does not fail on a missing `url_file` (file read is lazy at notify time).
- Test container was then expired and the monitoring profile stopped.

## Limits

- No mounted OnCall URL files and no running Grafana OnCall instance yet: escalation,
  on-call rotation and acknowledgement are unqualified. The contract is webhook-URL
  compatible with the OnCall Alertmanager/webhook integration, so only the secret-file
  contents change when an instance is stood up.
- The monitoring profile uses host networking (Linux Docker Engine oriented; on Docker
  Desktop for Windows containers are reachable from inside the VM, not from Windows
  host loopback).
- Escalation policy, schedules and mobile/paging delivery remain open under K7.5/%56;
  no production deployment.

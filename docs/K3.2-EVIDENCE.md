# K3.2 PostgreSQL lexical index evidence

## Delivered scope

PR [#125](https://github.com/sanskarpan/Keel/pull/125) closes issue [#25](https://github.com/sanskarpan/Keel/issues/25). Migration `0014_retrieval_lexical_publication` adds tenant/visibility-cohort scoped builds, immutable chunk citation metadata, tenant- and key-version-bound HMAC term postings, and build-local document-frequency statistics. The separate `keel_retrieval_indexer` role can stage/finalize/publish; `keel_app` has read-only access. Forced RLS and composite foreign keys scope rows to both tenant and exact visibility cohort.

The repository stages bounded batches, reconciles expected chunk counts, aggregate token lengths, posting frequencies and document frequencies before finalization, then publishes a ready build through a row-locked, expected-generation-fenced atomic head switch. A failure rolls back the candidate publication and head together. Search uses a repeatable-read snapshot, deterministic BM25 ordering and explicit term, posting-row and top-k limits; posting-budget overflow returns no partial candidates. Plaintext document text and tokens are not stored in these index tables.

## Validation evidence

Final implementation-head contract CI run [#110](https://github.com/sanskarpan/Keel/actions/runs/37269277805) passed on October 5, 2026. Its disposable PostgreSQL service applied the full migration chain and ran the database integration suite with separate non-owner app and indexer roles, plus an admin-only failure injector. The tests cover:

- tenant and visibility-cohort isolation, including overlapping terms in separate cohorts;
- staged/ready invisibility, publication, expected-generation fencing and replacement/retirement;
- exact score equality with an independent BM25 calculation;
- wrong key-version rejection and fail-closed posting-budget overflow;
- application write denial and immutable published chunks;
- rollback after injected head-update failure and successful retry;
- database refusal to finalize inconsistent chunk/posting counts.

Local checks also passed: `go test ./...`, `go test -race ./...`, `go vet ./...`, `go build ./...`, focused retrieval tests/vet, and `git diff --check`. Local DB-backed tests were skipped because this workspace deliberately leaves its persistent Compose database untouched; CI supplied the disposable PostgreSQL integration evidence.

## Boundaries and operations

This phase delivers a lexical index repository and scorer, not an HTTP search route, caller authorization decision, embedding/vector search, hybrid fusion, reranker, relevance or capacity qualification, or a customer-serving deployment. The synthetic K3.1 seed is not used as customer data or as a production quality benchmark.

Retired publications remain immutable and query-inactive. Abandoned staged/failed rows cannot become active; this phase does not ship automated retention or physical cleanup. Operators must not delete or edit index rows manually. Safe abandoned-build cleanup, prior-publication retention windows, source withdrawal/erasure propagation, and key lifecycle/rotation procedures require the later K3.5 lifecycle policy before cleanup is enabled. This is an explicit storage-growth limitation, not a claim of operational deletion readiness.

The migration is additive. A code rollback leaves the new tables and rows in place and removes no source data; the old application version does not depend on them. Do not down-migrate populated retrieval data or manually change a head pointer. Roll forward with a compatible indexer if a candidate is faulty; expected-generation conflicts are retried only after revalidating the candidate source snapshot.

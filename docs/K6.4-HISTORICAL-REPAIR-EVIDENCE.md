# K6.4 slice: historical repair

Issue #413 (parent #49 and #48, checklist item K6.4). PR #414 merged as
`49846fbafd31b10e9ac9297aa2953dba9713d796`; contract CI #665 passed on reviewed head
`38c5f2cd46a23b1b388bfa86b94e18dc713f5b96` (two earlier attempts hit the known unrelated flaky
`TestPostgreSQLKafkaConsumerReplaysUncommittedDBEffectAcrossGroupRebalance`). This slice makes
repair revalidate each gap event against the endpoint status recorded at the event's time,
instead of backfilling old events to endpoints merely active now.

## Contract

- Migration `0059` adds an audited `skipped_identities` count to repair runs, a lookup index on
  the status history, and re-creates `repair_webhook_reconciliation_run` with a fourth return
  column. For every selected gap event crossed with currently-active endpoints, the function
  reads the latest history record at or before the event's recorded time: active-then endpoints
  become candidates at their then-current subscription, while identities with no history or an
  inactive status are skipped and counted. Delivery dedup, the 10,000-candidate fail-closed
  bound, idempotent repeats, advisory serialization and capability/immutability guards are
  unchanged.
- Go adds `RepairResult.SkippedIdentities` with store validation; no other API changes.
- The planner still scans against current active endpoints, so a planned gap may repair to zero
  inserts with a matching skip count; planner history-awareness is a later slice.

## Limits

No planner change, scheduler integration, reconciliation UI/metrics or HTTP exposure. Events
predating the status history cannot be reconstructed and are skipped, never guessed.

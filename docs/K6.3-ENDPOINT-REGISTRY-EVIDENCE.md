# K6.3 slice: versioned webhook endpoint registry

Issue #350 (parent #48, checklist item K6.3). PR #351. This slice adds the durable destination
registry behind webhook delivery: which URL and signing key an endpoint revision uses, whether it is
active, and how delivery resolves it at the exact subscription revision. It does not sign, dial,
retry or replay; it also does not expose an operator HTTP surface.

## Schema

Migration `0042_webhook_endpoints` adds `keel_meta.webhook_endpoints`:

| Column | Contract |
| --- | --- |
| `tenant_id`, `endpoint_id` | primary key; the tenant-visible endpoint identity is immutable |
| `url` | HTTPS destination, 8-2048 bytes, no control, whitespace or fragment bytes |
| `key_id` | bounded signing-key reference matching the keyring pattern |
| `subscription_version` | 1-1,000,000, the revision the URL belongs to |
| `status` | `active` or `inactive`; deactivation keeps the row |
| `version` | starts at 1 and increases by exactly one per accepted change |
| `created_at`, `updated_at` | database clock; creation time is immutable |

Forced row-level security, a schema-owner-only policy, revoked direct grants for every runtime role,
no delete path and a guard trigger for identity, creation time and the single-step version rule.
Rows are never removed, so resolution history is not silently rewritten; deactivation is a status
change with a version bump.

## Registration

`keel_meta.register_webhook_endpoint(endpoint_id, url, key_id, subscription_version,
expected_version)` requires membership in `keel_app` and derives the tenant from the authorized
transaction context. `expected_version = 0` creates; `ON CONFLICT DO NOTHING` makes duplicate
creation fail loudly instead of overwriting. A positive `expected_version` updates only when the
stored version matches, so two integrations racing on the same revision produce one winner and one
version-conflict error. Updating changes the URL, key reference and subscription revision only; the
endpoint identity and creation time stay fixed.

`keel_meta.set_webhook_endpoint_status(endpoint_id, status, expected_version)` uses the same
capability and version fence to activate or deactivate. A status change is not a free write: a stale
caller cannot re-enable an endpoint that changed since it read it.

## Resolution

`keel_meta.resolve_webhook_endpoint(endpoint_id, subscription_version)` requires membership in
`keel_webhook` and returns the URL and key reference of an `active` endpoint only at the exact
requested revision. A missing, stale-revision or inactive endpoint returns no row, which the Go
store surfaces as `ErrEndpointUnavailable`; delivery therefore fails closed instead of sending an
old payload to a new URL under an old subscription.

The URL is the sensitive field: it may embed a receiver token. It is returned only to the capability
that is about to use it. This slice never logs it, stores it in an attempt row or includes it in an
error; operator surfaces must follow the same rule.

## URL rules

`webhook.ValidateEndpointURL` applies the static egress rules plus registry bounds:

- HTTPS only, with the egress port allowlist (443 by default).
- No userinfo, fragment, opaque URL or empty host.
- A dotted hostname or public literal address; loopback, private, link-local, multicast, CGNAT,
  documentation, benchmark and reserved answers are refused.
- No control bytes, whitespace or bytes outside 1-2048 total length.

The check is static: DNS is not resolved and no address is pinned at registration. Every delivery
dial still re-resolves the host and vets every answer through the K6.2 egress path, so a hostname
that later turns private fails at send time. Registration accepts a hostname it cannot vet yet
instead of turning DNS into a write dependency, but it never accepts a URL the egress policy would
refuse on its face. The database repeats the scheme, length and character checks as defense in
depth.

## Concurrency

`version` is the optimistic token for both registration and status changes. A caller reads the
endpoint, decides, and submits the observed version; a mismatch returns a version-conflict error and
changes nothing. Two concurrent updates at the same expected version produce exactly one success in
PostgreSQL integration coverage. There is no read-modify-write lock exposed to callers and no
last-write-wins path.

## Coverage

Unit tests cover URL acceptance and rejection (scheme, userinfo, fragment, loopback/private/metadata
literals, unallowed ports, missing host, spaces, control bytes, length cap), registration/key/version
validation, endpoint identity validation and input guards on both Go entry points. PostgreSQL
integration tests cover create, duplicate creation, stale update, URL/key/revision update, resolution
at the matching revision, stale/unknown/cross-tenant resolution, deactivation and reactivation,
stale status changes, concurrent single-winner updates, direct table access denial for both runtime
roles, capability denial in both directions (webhook cannot register, app cannot resolve) and delete
rejection.

## Boundaries

No HTTP route, operator UI, key storage/KMS, signing, delivery worker, breaker persistence or replay
record. The registry resolves a target but does not send to it; attempt rows still store no URL or
secret. K6.3 and parent #48 remain open.

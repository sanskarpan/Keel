# K6.3 slice: command-time webhook fanout

Issue #369 (parent #48, checklist item K6.3). PR #370 merged as
`b7592015fe4b77afdbaf52cab116bb941d6af4c9`; contract CI #606 passed on reviewed head
`f03161cacac5d2fc8d91eebf9b6b5efded0eddb6`. This slice is the first production delivery
producer: an accepted order event creates one immutable delivery row per active endpoint in the
tenant. It does not add event-type subscriptions, backfill, an asynchronous relay, endpoint
quotas, process wiring or replay execution.

## Fanout contract

Migration `0048_webhook_delivery_fanout` adds
`keel_meta.fanout_webhook_deliveries(event_id) RETURNS integer`:

- Requires membership in `keel_app` and derives the tenant from
  `keel_private.current_tenant_id()`, never from the caller.
- Accepts one bounded canonical UUID event ID and requires the event to exist in
  `event_outbox` for the same tenant. A malformed, unknown or cross-tenant event raises a fixed
  error and inserts nothing.
- Inserts one row into `webhook_deliveries` for every `webhook_endpoints` row in the tenant with
  `status='active'`, using the endpoint's current `subscription_version`.
- Generates a `whd_`-prefixed delivery ID and returns only the inserted row count.
- Relies on `webhook_deliveries_identity_unique` plus
  `ON CONFLICT (... ) DO NOTHING`, so a repeated or concurrent call inserts nothing and preserves
  the original delivery IDs.
- Runs as `SECURITY DEFINER` with a fixed `search_path`, revokes `PUBLIC`, and grants execute only
  to `keel_app`. The schema-owner RLS policies on `event_outbox`, `webhook_endpoints` and
  `webhook_deliveries` supply access; runtime roles still have no direct table access.
- Returns no endpoint URL, key reference, payload, signature or receiver data.

Delivery rows have no state until the scheduler's `Ensure` creates the state row, as with the
existing delivery ledger. Fanout does not call the network.

## Command integration

`appendCommandSideEffects` calls the function after inserting the outbox row and before
`outbox_delivery` and the state update. It is the same tenant transaction as the order event, so:

- a fanout failure rolls back the order command;
- the event and its deliveries become visible together;
- endpoint count and delivery-table contention add command latency; and
- an inactive endpoint, or one registered after the event, receives no delivery for that event.

The current endpoint registry has no event-type filter, so every active endpoint receives every
order event. There is no backfill for outbox rows that predate this slice and no cap on the number
of endpoints per tenant.

## Verification

Coverage runs against a fresh PostgreSQL database with migrations through `0048` and separately
through the order repository:

- one delivery per active endpoint, with inactive endpoints excluded;
- the endpoint's current subscription revision is used, and a later event uses the new revision;
- repeat and concurrent fanout insert exactly once and preserve delivery IDs;
- unknown, malformed and cross-tenant events are rejected without writes;
- `keel_webhook` cannot execute the fanout function;
- an order created through the repository fans out to two active endpoints.

The existing webhook, order and repository suites pass locally on the isolated database. Linux CI
covers the race detector.

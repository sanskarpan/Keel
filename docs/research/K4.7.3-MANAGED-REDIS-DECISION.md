# K4.7.3 managed home-region Redis qualification

**Research checked:** 2026-10-07 UTC
**Decision:** Amazon MemoryDB is the recommended pilot candidate for Keel's home-region Redis admission authority. This is a service candidate, not an approved deployment or a claim of production qualification.

## Why MemoryDB is the leading candidate

Keel's primary limiter spends a shared allowance through one atomic Redis Lua script. A lost or reordered primary write can make the limiter admit more requests than its configured bucket. MemoryDB is the strongest AWS managed Redis-compatible fit found for that correctness shape: AWS documents strongly consistent primary nodes, durable writes in a distributed Multi-AZ transaction log before successful writes return, and preservation of primary consistency across failover. Replica reads are eventually consistent, so admission decisions must use the primary path. These properties reduce the risk that an acknowledged token spend disappears after failover; they do not remove ambiguous client timeouts or make Redis and PostgreSQL one transaction. See the [MemoryDB consistency contract](https://docs.aws.amazon.com/memorydb/latest/devguide/consistency.html) and [service feature overview](https://docs.aws.amazon.com/memorydb/latest/devguide/servicename-feature-overview.html).

MemoryDB supports VPC-only clusters, security-group restrictions, TLS, ACL users and AWS IAM. Its IAM authentication is available for Redis OSS/Valkey engine version 7.0 or later. Tokens are valid for 15 minutes; authenticated connections are closed after 12 hours unless refreshed. This supports short-lived workload authentication without placing a permanent Redis password in Terraform state. The code now has a caller-supplied AWS credentials callback, a SigV4 token signer, and a cluster-aware Redis client constructor; these are not wired into a runtime role and have not been exercised against a MemoryDB endpoint. Runtime configuration, connection refresh behavior and the managed endpoint/client contract still require implementation and qualification. See [MemoryDB security](https://docs.aws.amazon.com/memorydb/latest/devguide/memorydb-security.html), [TLS](https://docs.aws.amazon.com/memorydb/latest/devguide/in-transit-encryption.html), [IAM authentication and its limits](https://docs.aws.amazon.com/memorydb/latest/devguide/auth-iam.html), and [ACL access strings](https://docs.aws.amazon.com/memorydb/latest/devguide/clusters.acls.html).

The source-owned limiter uses Redis scripts and colocates each replay record with its bucket by using a Redis Cluster hash tag. AWS's MemoryDB metrics include `EVAL`/`EVALSHA` command counts, which is evidence these command paths exist in the service, but not a compatibility test of Keel's specific scripts. The managed-service contract must run the exact scripts, expiration behavior, TLS hostname verification, primary endpoint discovery, and failover replay against the selected engine version before this service can be enabled. The service's [cluster endpoint documentation](https://docs.aws.amazon.com/memorydb/latest/devguide/nodes-connecting.html) describes Redis Cluster protocol discovery and failover endpoint use. Keel now has a cluster-aware client constructor, but the endpoint/client contract remains unverified against MemoryDB.

An opt-in `TestMemoryDBManagedClusterContract` now exercises verified TLS, IAM authentication from the standard AWS credential chain, concurrent shared-bucket limits, and receipt replay/conflict across two cluster clients. It writes only uniquely scoped HMAC-obscured limiter keys with bounded TTLs and never flushes the database. It requires an explicit mutation acknowledgment plus `KEEL_TEST_MEMORYDB_ADDR`, `KEEL_TEST_MEMORYDB_REGION`, and `KEEL_TEST_MEMORYDB_USERNAME`. This provides a repeatable first endpoint check, not failover, DNS-change, overshoot, production-load, or recovery qualification; it skips by default and has not run against an AWS endpoint.

## Alternatives considered

| Service profile | Advantages | Risk or qualification required for Keel |
|---|---|---|
| **MemoryDB, Redis OSS compatible** | Strongly consistent primary, durable Multi-AZ transaction log, TLS, ACLs, VPC-only access, IAM authentication. | Node-based cost and capacity need a region-specific estimate. Validate exact EVAL/EVALSHA scripts, client cluster/endpoint behavior, IAM token refresh and failover overshoot. Replicas are eventual; do not read admission state from replicas. |
| **ElastiCache Serverless, Redis OSS** | Managed scaling and a familiar Redis-compatible API. | AWS documents that ElastiCache durability is not supported with Serverless; validate write-loss/overshoot behavior before using it as an admission authority. |
| **ElastiCache node-based replication group** | Mature Multi-AZ/automatic failover, TLS, ACLs, and Redis-compatible endpoint options. | Standard replica propagation is asynchronous and AWS documents possible lost writes on primary failure. Newer Valkey 9 durability provides a transactional-log option, but requires Multi-AZ plus a replica, is not available on Serverless or Global Datastore, and is limited to 100 MiB/s writes per primary. Its engine and topology would need separate client-compatibility and cost qualification. |

The ElastiCache limitations are from AWS's [durability support matrix](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/Durability.Limitations.html) and [replication/failover behavior](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/Replication.html). They do not mean that ElastiCache is unusable; they make it a less direct default for this correctness-sensitive single-home-region workload until its selected durability mode is qualified.

## Proposed pilot topology

- One AWS region and one MemoryDB cluster in private subnets spanning at least two Availability Zones, with one shard and a primary plus replica for the initial production-small test. One shard keeps the rollout small; capacity and shard count must follow measured load, not be inferred from this proposal.
- Application nodes use the MemoryDB endpoint/client mode that passes the managed compatibility test, with TLS certificate and hostname verification. Network access is limited to the Keel application security group on the MemoryDB port. No public endpoint and no cross-region writes are configured.
- Use an IAM-authenticated MemoryDB user with an explicit command/key access string for the limiter. Give the EKS workload role only `memorydb:Connect` to that user and cluster. Keep management permissions in a separate infrastructure role. Keel must refresh tokens for new connections and re-authenticate long-lived pooled connections before the 12-hour server limit.
- Use a dedicated home-region endpoint/identity, bounded client pool and timeouts, and keep the existing SQL fallback disabled until the independent fallback evidence is complete. On transport ambiguity, retry with the same request ID so the stored Lua receipt preserves the exact decision.
- Export CloudWatch availability, engine CPU, successful read/write latency, replication lag, connection and memory metrics. Alert on primary failover, sustained latency, connection saturation, replication issues, and limiter errors. Keep tenant/request identifiers out of dimensions.

This topology is a proposal based on current AWS service documentation, not an applied infrastructure design. One-shard operation, actual endpoint DNS behavior, IAM permission syntax, VPC/subnet IDs, account quota, region availability, pricing and node sizing remain to be established in an owned AWS environment.

## Required work before deployment or closing #199

1. Confirm the AWS account, home region, budget envelope, service owner and on-call/rollback owners. Check MemoryDB engine, node-type, quota and IAM-auth availability in that region. No region, cost, account, or owner is selected in repository evidence today.
2. A gated Terraform module candidate now consumes existing subnets, the Keel workload security group and IAM role, and an approved KMS key; it configures a private single-shard/one-replica topology candidate, IAM ACL user, scoped `memorydb:Connect`, TLS, snapshots, and an explicit enable/approval gate. Its disabled plan validates as zero resource actions. Before apply, select the account/region/cost/owner, verify subnet route tables and the ACL against the live client contract, choose the supported engine/node type, configure reviewed remote state, and rehearse snapshot restore and cleanup. No resource has been provisioned.
3. Resolve single-address versus cluster-aware endpoint behavior, then extend Keel's Redis client accordingly. Add short-lived AWS IAM authentication with token refresh on pool connection creation and re-auth on long-lived connections; reject missing AWS identity and fail closed.
4. Run the exact Redis contract suite against the chosen MemoryDB engine and TLS endpoint. Exercise same-key concurrent admissions, a primary failover during admission, timeout after server commit, client reconnect, DNS change, and receipt replay. Measure request overshoot, outage duration, p50/p95/p99 latency, throughput, connection count and node utilization at an approved production-small load envelope.
5. Install owned dashboards and alerts; rehearse failover, endpoint recovery, workload credential revocation, kill switch and restore/rollback. Record observed rather than promised failure bounds.

Until these gates pass, this research supports a service direction only. It does not authorize customer traffic, route enablement, issue closure, or production claims.

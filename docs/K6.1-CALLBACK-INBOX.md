# K6.1 Authenticated callback inbox

Issue [#332](https://github.com/sanskarpan/Keel/issues/332) under parent [#46](https://github.com/sanskarpan/Keel/issues/46) adds the inbound provider callback boundary: one callback is authenticated, recorded once, and applied in the same tenant transaction that records it.

## Trust boundary

The package `internal/delivery/callbackinbox` never verifies a signature itself. It accepts only a `VerifiedEvent` produced by an injected `Verifier`, so the signature algorithm, key selection, provider-specific canonicalization and payload parsing stay in the adapter. The verifier must bind the signature to the exact payload bytes and must not invent a tenant or change the provider/event identity it was asked to verify; the inbox rejects a verified event whose provider or event ID differs from the request.

The tenant is authoritative only in the verified event. It is never read from the payload, path, headers or a request field, and the inbox opens the tenant transaction from that identity. A zero or malformed tenant is rejected before the database is touched.

## Idempotent application

`Inbox.Accept` authenticates, claims the event and applies its effect in one tenant transaction:

- The claim records `(tenant, provider, provider event ID, SHA-256 payload digest, event type, key ID, provider occurrence time)` with state `received`.
- On a first delivery the applier runs inside that transaction and the row transitions to `applied` with a database-derived timestamp before commit.
- An exact redelivery (same provider event ID and digest) returns `Duplicate: true` with the recorded application time and does not run the applier.
- A failed application rolls back the record and the effect together, so a provider retry applies the event rather than being mistaken for a duplicate.

The provider event ID is unique across tenants, not only within one tenant. A provider event belongs to exactly one tenant, so replaying a captured event under another tenant is a conflict rather than a second accepted delivery.

## Conflict handling

Two conflicts fail closed with one stable `ErrConflict`:

- **payload mismatch**: the same provider event ID arrives with a different digest;
- **tenant mismatch**: the same provider event ID arrives under another tenant.

Either way nothing is applied and the original record is unchanged. The reason, the caller's tenant, the provider/event identity and the digest the caller presented are written to the append-only `callback_conflicts` ledger. The caller cannot distinguish the two cases from the response, and the ledger never exposes the other tenant's identity, digest, or content to the caller.

## Access control

- Migration `0039_callback_inbox` adds a dedicated `keel_callback` capability with a local `keel_local_callback` login in the synthetic profile.
- Both tables use forced tenant RLS, and direct privileges are revoked from every runtime role, including `keel_callback`. All access goes through two `SECURITY DEFINER` functions: `claim_provider_callback` and `confirm_provider_callback`.
- The functions require `keel_callback` membership on the session user, derive the tenant from the transaction-local authorized context, and re-validate every input.
- Inbox rows are immutable: the only allowed transition is `received` to `applied` with a database timestamp. Conflicts are append-only.
- The claim function uses `ON CONFLICT DO NOTHING` on the global provider/event identity, so concurrent identical deliveries serialize: exactly one applies and the other sees the committed record as a duplicate.

## Bounds and content

Provider names, event IDs, event types, key IDs and digests are bounded by regular expressions and length. A raw payload is capped at 1 MiB and is never stored; only its digest is. No prompt, response, customer, ledger or model content crosses this boundary, and the inbox returns fixed errors rather than provider or database detail.

## Validation

- Unit coverage: canonical SHA-256 digest, nil database/verifier rejection, provider/event type/key/payload bounds, empty signature, zero tenant, zero time, verifier provider/event identity drift, and stable mapping of verifier rejection and verifier outage to `ErrUnauthenticated` and `ErrUnavailable`.
- PostgreSQL coverage: apply exactly once; exact redelivery returns the recorded application time; payload conflict records `payload_mismatch` and applies nothing; cross-tenant replay records `tenant_mismatch`, keeps the original tenant's record and creates none for the replayer; a failed application leaves no inbox row and a retry succeeds; two concurrent identical deliveries apply once; direct table reads, inserts, updates and deletes are denied; and an app role without the callback capability cannot claim.
- `go test ./...`, `go vet ./...`, `go build ./...` and the migration suite pass locally, including the new migration against PostgreSQL.

## Limits

This is a code boundary. No HTTP route is mounted, no provider adapter or signature algorithm is configured, no runtime worker polls for callbacks, and no alert, metric series or replay UI exists. Signature verification and key rotation are K6.2 work, delivery retry/circuit breaking is K6.3, reconciliation cursors and repairs are K6.4, and adversarial late/duplicate/replay qualification is K6.5. Parent #46 stays open.

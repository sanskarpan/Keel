# K5.4 protected context vault

K5.4 is tracked by [parent issue #42](https://github.com/sanskarpan/Keel/issues/42). The first bounded foundation, [issue #284](https://github.com/sanskarpan/Keel/issues/284), defines envelope encryption for a single protected context record. [Issue #287](https://github.com/sanskarpan/Keel/issues/287) adds a PostgreSQL store for already-encrypted records, with forced tenant RLS and expiry-gated reads. [Issue #292](https://github.com/sanskarpan/Keel/issues/292) adds opt-in, versioned tenant/purpose retention snapshots and database-derived expiry. [Issue #294](https://github.com/sanskarpan/Keel/issues/294) adds a bounded, tenant-scoped expiry deletion function and immutable content-free deletion receipts. K5.4 still does not provide a production KMS runtime, durable deletion orchestration, legal-hold processing, qualified backup/replica scrubbing, authorized replay, or Langfuse.

## Envelope contract

- Each record version gets a fresh cryptographically random 256-bit data key and a fresh AES-256-GCM nonce.
- The data key is wrapped through the injected `KeyWrapper`, which receives a validated `KeyBinding` for the canonical tenant, record, version, policy digest, and key ID. A KMS/HSM adapter must authenticate every field using provider-side encryption context or an equivalent authenticated mechanism; passing scope as unauthenticated metadata is insufficient. The context is versioned (`keel:binding_version=1`) so future changes require an explicit compatibility plan. The production provider remains unselected until K0.1 qualification; issue #290 and PR #291 implement the provider-independent binding contract, not a vendor SDK or deployed key provider.
- The envelope persists only the algorithm name, key ID, wrapped data key, nonce, and ciphertext. AAD binds tenant ID, record ID, version, policy digest, and key ID.
- Tenant and record UUIDs are canonicalized before AAD creation. Version must be positive; the policy digest must be lowercase `sha256:<64 hex>`; one plaintext record is bounded to 1 MiB.
- Decryption requires the caller's expected scope, validates envelope shape before unwrapping, and returns plaintext only after AES-GCM authentication succeeds. Any scope or ciphertext change fails closed.
- The PostgreSQL store persists no plaintext. It inserts immutable tenant/record/version rows, accepts only exact idempotent retries, and reads an exact version only while its expiry is still in the future according to the database clock. Each insert requires the current enabled tenant/purpose snapshot and consent reference; PostgreSQL derives expiry from that snapshot. App, workflow-worker, operator, and projector roles have no table access. A separate context-policy role authors immutable policy snapshots and cannot read ciphertext; the vault role reads policy metadata but cannot author policy.

## Storage and lifecycle follow-up

The envelope type, ciphertext-only PostgreSQL store, opt-in retention snapshot, and controlled expiry deletion are foundations, not a complete vault. The erasure function processes at most 100 expired rows per call, scopes work to the tenant derived from the authenticated database session, orders candidates deterministically, and uses `FOR UPDATE SKIP LOCKED` for concurrent callers. A record is deleted only in the same transaction that inserts an immutable receipt containing its identity, retention/consent references, expiry/deletion times, and a SHA-256 digest over a versioned, length-prefixed binary serialization of the encrypted envelope; plaintext and ciphertext are not copied into the receipt. Callers receive only the bounded deletion count. This is a database primitive, not a worker: durable leases/retries, legal holds, backup/PITR/replica/restore qualification, and end-to-end erasure proof remain in [issue #297](https://github.com/sanskarpan/Keel/issues/297). Other remaining work includes authorized tenant/purpose-bound reads, orphan cleanup, and backup/replica erasure evidence. KMS key access must be workload-identity scoped, rotation must preserve decryptability only for records within retention, and key destruction must not precede verified data deletion.

Read-only replay must authorize the exact tenant, record, version, purpose and actor before unwrapping; run in a sandbox that cannot mutate orders, budgets, workflows or deliveries; redact tool/provider secrets; and produce a content-free audit record. Langfuse is a later adapter that receives safe metadata and an opaque vault reference only. Raw prompt/context content must never enter general logs or trace attributes.

The implementation deliberately provides no Langfuse client, production KMS integration, expiry-deletion worker, legal-hold processing, backup/replica scrubbing, end-to-end erasure proof, or replay endpoint. The database expiry-deletion primitive is tracked by #294; durable orchestration and legal-hold/backup qualification are tracked by #297. The other capabilities remain K5.4 work under #42.

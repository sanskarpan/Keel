## Envelope contract

- Each record version gets a fresh cryptographically random 256-bit data key and a fresh AES-256-GCM nonce.
- The data key is wrapped through the injected `KeyWrapper`, which receives a validated `KeyBinding` for the canonical tenant, record, version, policy digest, and key ID. A KMS/HSM adapter must authenticate every field using provider-side encryption context or an equivalent authenticated mechanism; passing scope as unauthenticated metadata is insufficient. The context is versioned (`keel:binding_version=1`) so future changes require an explicit compatibility plan. The production provider remains unselected until K0.1 qualification; issue #290 and PR #291 implement the provider-independent binding contract, not a vendor SDK or deployed key provider.
- The envelope persists only the algorithm name, key ID, wrapped data key, nonce, and ciphertext. AAD binds tenant ID, record ID, version, policy digest, and key ID.
- Tenant and record UUIDs are canonicalized before AAD creation. Version must be positive; the policy digest must be lowercase `sha256:<64 hex>`; one plaintext record is bounded to 1 MiB.
- Decryption requires the caller's expected scope, validates envelope shape before unwrapping, and returns plaintext only after AES-GCM authentication succeeds. Any scope or ciphertext change fails closed.
- The PostgreSQL store persists no plaintext. It inserts immutable tenant/record/version rows, accepts only exact idempotent retries, and reads an exact version only while its expiry is still in the future according to the database clock. Each insert requires the current enabled tenant/purpose snapshot and consent reference; PostgreSQL derives expiry from that snapshot. App, workflow-worker, operator, and projector roles have no table access. A separate context-policy role authors immutable policy snapshots and cannot read ciphertext; the vault role reads policy metadata but cannot author policy.

## Storage and lifecycle follow-up

The envelope type, ciphertext-only PostgreSQL store, opt-in retention snapshot, controlled expiry deletion, durable erasure queue, and legal-hold lifecycle are foundations, not a complete vault. Migration `0036` schedules a content-free job in the same transaction as each record insert, using the database-derived expiry. The worker can claim one due job for its explicitly supplied tenant, with `SKIP LOCKED`, a monotonically increasing lease epoch, a 12-failure ceiling, bounded exponential backoff, and a terminal blocked state. It cannot directly read the job table or live ciphertext; only scoped claim/process/retry functions are granted. The process function locks the exact expired record before its job, then inserts the immutable receipt, deletes the envelope, and completes the job in one transaction. Migration `0037` adds one or more exact-version holds behind a separate capability. It records content-free create/review/extend/release events with database timestamps and increasing revisions. Review deadlines are not automatic releases: an overdue unreviewed hold remains active and blocks the batch eraser, queue processor, and record-delete guard. Hold operations and erasure lock the context row before the queue row, so only one side of a placement/deletion race can succeed. The authority cannot read ciphertext, retention policy, or hold/event tables directly. The injectable polling runtime has no deployed service; actor IDs are only syntactically validated until an external identity authority is selected. No provider-specific backup/PITR/replica/restore guarantee is claimed; that qualification remains in #300 until K0.1 selects a hosted database/KMS profile. KMS key access must be workload-identity scoped, rotation must preserve decryptability only for records within retention, and key destruction must not precede verified data deletion.

Read-only replay must authorize the exact tenant, record, version, purpose and actor before unwrapping; run in a sandbox that cannot mutate orders, budgets, workflows or deliveries; redact tool/provider secrets; and produce a content-free audit record. Langfuse is a later adapter that receives safe metadata and an opaque vault reference only. Raw prompt/context content must never enter general logs or trace attributes.

The replay core under #306 is limited to one exact immutable version. The service authorizes before storage/key access, rejects held or expired records, uses a one-use content-free audit identity, and holds a shared record lock while a trusted diagnostic consumer receives plaintext so hold placement/deletion cannot race with release. A five-second context deadline and 1 MiB payload cap are passed to the adapters, which must honor cancellation. Replay-audit retention/archival policy and storage monitoring are not yet qualified; do not prune append-only events directly. The caller must supply actor/tenant from trusted identity middleware. The API endpoint remains unmounted, and the synthetic actor UUID does not authenticate an operator.

The Langfuse adapter implementation (#308/PR #309) emits a versioned OTLP/HTTP span contract with a bounded non-blocking queue, explicit host allowlisting, finite request timeouts, and no prompt/completion/tool payload fields. It is disabled by default, is not wired into an application runtime, and does not configure an endpoint or credentials. Langfuse retention/deletion is an independent system: vault expiry or deletion does not erase Langfuse traces, copies, or backups; deployment requires a reviewed Langfuse retention/deletion policy and operational owner. The implementation deliberately provides no production KMS integration, deployed worker, public legal workflow endpoint, external actor-identity adapter, backup/replica scrubbing, end-to-end erasure proof, or mounted replay endpoint. Durable queue processing is complete under #301 and the database-level hold lifecycle is complete under #302. Hosted backup/replica/restore qualification is tracked by #300 and depends on K0.1. The remaining K5.4 capabilities remain tracked under #42.

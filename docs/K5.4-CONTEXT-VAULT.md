# K5.4 protected context vault

K5.4 is tracked by [parent issue #42](https://github.com/sanskarpan/Keel/issues/42). The first bounded foundation, [issue #284](https://github.com/sanskarpan/Keel/issues/284), defines envelope encryption for a single protected context record. [Issue #287](https://github.com/sanskarpan/Keel/issues/287) adds a PostgreSQL store for already-encrypted records, with forced tenant RLS and expiry-gated reads. K5.4 still does not provide a KMS runtime, expiry deletion, legal-hold processing, authorized replay, or Langfuse.

## Envelope contract

- Each record version gets a fresh cryptographically random 256-bit data key and a fresh AES-256-GCM nonce.
- The data key is wrapped through the injected `KeyWrapper`. A runtime implementation must use the configured KMS/HSM; the application package has no local or in-memory production key provider.
- The envelope persists only the algorithm name, key ID, wrapped data key, nonce, and ciphertext. AAD binds tenant ID, record ID, version, policy digest, and key ID.
- Tenant and record UUIDs are canonicalized before AAD creation. Version must be positive; the policy digest must be lowercase `sha256:<64 hex>`; one plaintext record is bounded to 1 MiB.
- Decryption requires the caller's expected scope, validates envelope shape before unwrapping, and returns plaintext only after AES-GCM authentication succeeds. Any scope or ciphertext change fails closed.
- The PostgreSQL store persists no plaintext. It inserts immutable tenant/record/version rows, accepts only exact idempotent retries, and reads an exact version only while its expiry is still in the future according to the database clock. App, workflow-worker, operator, and projector roles have no table access; the dedicated vault role has tenant-scoped select/insert only.

## Storage and lifecycle follow-up

The envelope type plus ciphertext-only PostgreSQL store are foundations, not a complete vault. Remaining work includes authorized tenant/purpose-bound reads, retention-policy snapshots, expiry deletion, tombstones and deletion audit, orphan cleanup, and backup/replica erasure evidence. KMS key access must be workload-identity scoped, rotation must preserve decryptability only for records within retention, and key destruction must not precede verified data deletion.

Read-only replay must authorize the exact tenant, record, version, purpose and actor before unwrapping; run in a sandbox that cannot mutate orders, budgets, workflows or deliveries; redact tool/provider secrets; and produce a content-free audit record. Langfuse is a later adapter that receives safe metadata and an opaque vault reference only. Raw prompt/context content must never enter general logs or trace attributes.

The implementation deliberately provides no Langfuse client, KMS deployment, persistence schema, retention worker or replay endpoint. Those remain K5.4 work under #42.

# K5.4 protected context vault

K5.4 is tracked by [parent issue #42](https://github.com/sanskarpan/Keel/issues/42). The first bounded foundation, [issue #284](https://github.com/sanskarpan/Keel/issues/284), defines envelope encryption for a single protected context record. [Issue #287](https://github.com/sanskarpan/Keel/issues/287) adds a PostgreSQL store for already-encrypted records, with forced tenant RLS and expiry-gated reads. [Issue #292](https://github.com/sanskarpan/Keel/issues/292) adds opt-in, versioned tenant/purpose retention snapshots and database-derived expiry. [Issue #294](https://github.com/sanskarpan/Keel/issues/294) adds a bounded, tenant-scoped expiry deletion function and immutable content-free deletion receipts. [Issue #301](https://github.com/sanskarpan/Keel/issues/301) adds durable database-derived expiry jobs, fenced bounded claims/retries, and an injectable tenant-scoped polling runtime. Legal-hold lifecycle and deletion serialization remain in [issue #302](https://github.com/sanskarpan/Keel/issues/302); production backup/PITR/replica/restore qualification remains blocked on provider selection under [issue #300](https://github.com/sanskarpan/Keel/issues/300). K5.4 still does not provide a production KMS runtime, deployed erasure worker, authorized replay, or Langfuse.

## Envelope contract

- Each record version gets a fresh cryptographically random 256-bit data key and a fresh AES-256-GCM nonce.
- The data key is wrapped through the injected `KeyWrapper`, which receives a validated `KeyBinding` for the canonical tenant, record, version, policy digest, and key ID. A KMS/HSM adapter must authenticate every field using provider-side encryption context or an equivalent authenticated mechanism; passing scope as unauthenticated metadata is insufficient. The context is versioned (`keel:binding_version=1`) so future changes require an explicit compatibility plan. The production provider remains unselected until K0.1 qualification; issue #290 and PR #291 implement the provider-independent binding contract, not a vendor SDK or deployed key provider.
- The envelope persists only the algorithm name, key ID, wrapped data key, nonce, and ciphertext. AAD binds tenant ID, record ID, version, policy digest, and key ID.
- Tenant and record UUIDs are canonicalized before AAD creation. Version must be positive; the policy digest must be lowercase `sha256:<64 hex>`; one plaintext record is bounded to 1 MiB.
- Decryption requires the caller's expected scope, validates envelope shape before unwrapping, and returns plaintext only after AES-GCM authentication succeeds. Any scope or ciphertext change fails closed.
- The PostgreSQL store persists no plaintext. It inserts immutable tenant/record/version rows, accepts only exact idempotent retries, and reads an exact version only while its expiry is still in the future according to the database clock. Each insert requires the current enabled tenant/purpose snapshot and consent reference; PostgreSQL derives expiry from that snapshot. App, workflow-worker, operator, and projector roles have no table access. A separate context-policy role authors immutable policy snapshots and cannot read ciphertext; the vault role reads policy metadata but cannot author policy.

## Storage and lifecycle follow-up

The envelope type, ciphertext-only PostgreSQL store, opt-in retention snapshot, controlled expiry deletion, and durable erasure queue are foundations, not a complete vault. Migration `0036` schedules a content-free job in the same transaction as each record insert, using the database-derived expiry. The worker can claim one due job for its explicitly supplied tenant, with `SKIP LOCKED`, a monotonically increasing lease epoch, a 12-failure ceiling, bounded exponential backoff, and a terminal blocked state. It cannot directly read the job table or live ciphertext; only scoped claim/process/retry functions are granted. The process function locks the current job lease and exact expired record, then inserts the immutable receipt, deletes the envelope, and completes the job in one transaction. This runtime is injectable and tenant-scoped but is not wired to a deployable service. Legal-hold lifecycle and serialization remain in #302. No provider-specific backup/PITR/replica/restore guarantee is claimed; that qualification remains in #300 until K0.1 selects a hosted database/KMS profile. KMS key access must be workload-identity scoped, rotation must preserve decryptability only for records within retention, and key destruction must not precede verified data deletion.

Read-only replay must authorize the exact tenant, record, version, purpose and actor before unwrapping; run in a sandbox that cannot mutate orders, budgets, workflows or deliveries; redact tool/provider secrets; and produce a content-free audit record. Langfuse is a later adapter that receives safe metadata and an opaque vault reference only. Raw prompt/context content must never enter general logs or trace attributes.

The implementation deliberately provides no Langfuse client, production KMS integration, deployed worker, legal-hold processing, backup/replica scrubbing, end-to-end erasure proof, or replay endpoint. The database queue/processor is tracked by #301; the authorized hold lifecycle is tracked by #302; hosted backup/replica/restore qualification is tracked by #300 and depends on K0.1. The other capabilities remain K5.4 work under #42.

# K6.4 slice: audited idempotent reconciliation repair

Issue #382 (parent #49, checklist item K6.4). PR #383 merged as
`7421ba041359a51ec3491cf4957f17e87574c4f8`; contract CI #623 passed on reviewed head
`31ea75fe903cd86b28469fc2ccd4f505114d2068`. This slice applies a recorded dry-run page by
creating the still-missing deliveries for current active endpoints, with an append-only repair audit
and the existing delivery identity constraint.

## Durable model

Migration `0052_webhook_reconciliation_repair` adds:

- append-only `webhook_reconciliation_repair_runs` with the repair ID, source run, operator
  principal, selected gap-event count, inserted-delivery count and database time;
- append-only `webhook_reconciliation_repair_items` with the event, endpoint, subscription revision
  and delivery ID for each inserted delivery, plus foreign keys to the repair run and delivery
  ledger.

Both tables are forced through RLS, expose only a schema-owner policy, and grant no direct access to
any runtime role, including `keel_operator`. Existing repair rows cannot be updated or deleted.

## Repair path

`keel_meta.repair_webhook_reconciliation_run(repair_id,run_id,requested_by,limit)`:

- Requires membership in `keel_operator` and derives the tenant from
  `keel_private.current_tenant_id()`.
- Validates a bounded repair ID, source run ID, audit actor and event limit of 1-500.
- Serializes repair per tenant with a transaction advisory lock.
- Requires the source run to exist and refuses a duplicate repair ID.
- Selects up to the limit of that run's recorded gap events.
- Revalidates current active endpoints at their current subscription revision and ignores identities
  that already have a delivery.
- Fails closed if more than 10,000 delivery candidates would be repaired; the function is atomic.
- Inserts only missing delivery identities, allowing the normal trigger to create pending state.
- Records the repair run and one item per inserted delivery, then returns gap-event and
  inserted-delivery counts only.
- Exposes no endpoint URL, key, payload, signature or receiver response.

The Go `RepairRequest` validates the same bounds and `postgres.Store.RepairReconciliation` maps
duplicate repair IDs to `ErrReconciliationConflict`, missing/invalid runs to
`ErrInvalidReconciliation`, and the candidate cap to `ErrReconciliationRepairLimit`.

## Semantics

Repair uses the current active endpoint set, not historical state. It can therefore deliver an old
event to an endpoint that is active now even if that endpoint was inactive when the event was
appended. This is an explicit, operator-audited action, not an automatic scheduler behavior. The
repair does not change the cursor, mutate the source run or gap history, or reconstruct endpoint
status history.

## Verification

Coverage runs against a fresh PostgreSQL database with migrations through `0052`:

- a dry-run page with two gaps repairs to two pending deliveries and two repair items;
- a repeat with a new repair ID inserts zero and leaves the delivery count unchanged;
- a duplicate repair ID returns `ErrReconciliationConflict`;
- an event limit bounds the selected gap events;
- a delivery created after the dry run is revalidated and not duplicated;
- an unknown source run returns `ErrInvalidReconciliation`;
- application and webhook roles cannot execute repair; the operator cannot read repair tables
  directly; repair rows are immutable;
- request validation covers tenant, repair ID, run ID, actor and event limit.

Linux CI covers the race detector.

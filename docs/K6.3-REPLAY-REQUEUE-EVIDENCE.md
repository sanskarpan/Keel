# K6.3 slice: authorized replay requeue

Issue #365 (parent #48, checklist item K6.3). PR #367 merged as
`740a22797533e074f6d5402b8a3bddd694481b06`; contract CI #602 passed on reviewed head
`7cbd741de87dd3ab6e8ebaa460b56de0d3bbd5e9`. This slice turns an operator replay request into an audited state transition. The
delivery returns to `pending` for the existing worker, and it keeps its retry budget: `attempts`,
`first_attempt_at` and `lease_epoch` are not reset. This is not a fresh 12-attempt/24-hour cycle.

## Transition audit

Migration `0047_webhook_replay_requeue` adds `keel_meta.webhook_replay_transitions`:

| Column | Rule |
| --- | --- |
| `tenant_id`, `replay_id` | Primary key; foreign key to the immutable replay request |
| `tenant_id`, `delivery_id` | Unique; foreign key to the delivery ledger |
| `prior_state` | `failed` or `exhausted` only |
| `prior_attempts` | 1-100 |
| `prior_finished_at` | Required; the terminal finish time being requeued |
| `prior_lease_epoch` | The terminal lease epoch |
| `authorized_at` | Database clock |

The table has forced RLS, a schema-owner policy and no runtime-role grants. A guard trigger
refuses update and delete, so the transition is append-only. It contains no URL, key, signature,
payload, reason text or receiver response; the reason and actor stay in `webhook_replays`.

## Authorization

`keel_meta.authorize_webhook_replay_requeue(replay_id, delivery_id, requested_by, reason)` is a
`SECURITY DEFINER` function owned by `keel_schema_owner`, executable only by `keel_operator`. It
derives the tenant from `keel_private.current_tenant_id()` and never accepts a tenant argument.
In one transaction it:

1. Locks the delivery state row.
2. Returns the stored transition for an exact replay ID/delivery/actor/reason retry, with
   `created=false`.
3. Rejects a replay ID reused with different fields, a second replay ID for the same delivery, a
   missing delivery, or a delivery that is not `failed`/`exhausted` with a finished attempt.
4. Requires an active endpoint at the delivery's exact subscription revision with a non-empty
   signing-key reference. The URL is checked inside the database and never returned.
5. Reuses or inserts the `webhook_replays` row and inserts the transition row with the current
   prior state, attempts, finish time and lease epoch.
6. Updates the state to `pending`, sets `next_attempt_at=clock_timestamp()`, clears the lease,
   delivered and finished times, and preserves `attempts`, `first_attempt_at`, `lease_epoch` and
   identity.

The state update and both insertions commit or roll back together, so a failed transition does
not consume the single replay request. The replaced state guard allows

terminal `failed`/`exhausted` -> `pending` only when a transition row matches the old state,
attempts, finish time and lease epoch. `delivered -> pending`, unaudited terminal updates,
identity changes, counter decreases, invalid pending shapes under the existing checks and deletes
remain rejected.

The caller is responsible for keyring membership. The database verifies that the endpoint has a
key reference, but a missing key in the runtime keyring is still rejected at send time and the
lease expires without recording an attempt.

## Go surface

`webhook.ReplayAuthorization` validates the bounded result and exposes only the replay/delivery
identity, actor, reason and prior state/attempts/finish/epoch plus timestamps and `Created`.
`postgres.Store.AuthorizeReplay` validates the existing `ReplayRequest`, calls the function in one
operator tenant transaction, maps capability, not-found, ineligibility and conflict errors, and
rejects a result that differs from the request.

Because the transition leaves `attempts` unchanged, an exhausted-at-12 delivery gets one manual
send as attempt 13; the existing scheduler then records exhaustion again unless the send is
delivered or permanent. A delivery failed early keeps only its remaining retry budget. This is the
documented consequence of preserving the budget; a future fresh-budget design needs a separate
replay-attempt generation or queue.

## Verification

Coverage runs against a fresh PostgreSQL database with migrations through `0047`:

- failed and exhausted requeues, including state shape and `next_attempt_at`;
- preserved attempts, first attempt, lease epoch and identity, then a lease at attempts+1;
- exact retry idempotency and conflicts on actor, reason and a second replay ID;
- concurrent authorizations producing one winner and one conflict;
- delivered/pending/in-flight and inactive/unknown endpoint rejection;
- app and webhook capability denial, with no replay or transition row written;
- immutable transition update/delete and unaudited direct requeue rejection;
- cross-tenant delivery invisibility.

Commands: `go test -count=1 ./internal/delivery/webhook/...` and
`go vet ./internal/delivery/webhook/...` with the local operator, webhook, app and admin DSNs.

## Still open

There is no operator HTTP route or UI, authentication/session layer, batch replay, fresh retry
budget, replay execution/payload fanout or metric contract. An endpoint or key can change between
authorization and send; the worker rechecks at send time and fails closed, which may consume the
single replay. The replay ledger still allows one request per delivery.

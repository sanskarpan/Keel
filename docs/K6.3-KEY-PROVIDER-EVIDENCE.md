# K6.3 slice: file-based signing key provider

Issue #447 (parent #48, checklist item K6.3). PR #448 merged as
`2b3d059f029ffcdd922259d153016829f82ff03d`; contract CI #711 passed on reviewed head
`6261ad85761d3ddacb839cb868abc0d7d14bca4d`. This slice adds a code-owned JSON key file as an
alternative signing-key source for the webhook worker. No migration was needed and no signing
semantics change.

## Contract

- `webhook.LoadKeyringFromFile` builds the existing active-plus-optional-previous `Keyring`
  from `{"active":{"id","secret_b64"},"previous":{...optional}}`: strict JSON with unknown
  fields rejected, 64 KiB file bound, base64 secrets with the 32-byte floor, duplicate IDs
  rejected, and directories/empty/missing/oversized files refused.
- The `webhook-worker` runtime honors optional `KEEL_WEBHOOK_KEY_FILE`; when set, the four
  base64 environment key vars must be absent or settings load fails (no ambiguous sourcing).
  Environment sourcing remains the default.
- Coverage includes active+previous and active-only loads, an eleven-case bad-file matrix,
  missing/directory/oversized paths, runtime file acceptance, ambiguity rejection and missing
  file rejection. Secrets in tests are generated at runtime; none are committed.

## Limits

No per-endpoint multi-key signing (the executor still signs with the active key), no KMS
integration and no production secret deployment. File delivery matches how container
platforms (including the recorded Modal/DigitalOcean direction) mount secrets.

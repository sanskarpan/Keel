# K6.3 slice: unmounted operator replay API

Issue #394 (parent #48, checklist item K6.3). PR #395 merged as
`8c7977477c8d90ff4ee955f537982c09ac625086`; contract CI #639 passed on reviewed head
`2b46e6051b9b45d476823afd801db0a050692027`. This slice adds the capped operator replay surface as
an unmounted HTTP handler with injected identity, authorization and key-readiness adapters.

## Candidate query

Migration `0055_webhook_replay_candidates` adds a `keel_operator`-gated
`list_webhook_replay_candidates(limit)`:

- Returns failed or exhausted deliveries with at least one attempt.
- Returns delivery/event/endpoint IDs, subscription revision, state, attempts, replay flag, current
  endpoint status at the delivery revision and key reference.
- Returns no URL, payload, signature or receiver content; endpoint status is `unknown` when the
  delivery revision no longer resolves.
- Bounds the candidate set to 1-5000 and grants execute only to `keel_operator`.

`postgres.Store.ReplayCandidates` validates every row and exposes it as delivery metadata plus
endpoint status/key reference. The API supplies key readiness from its injected keyring function.

## HTTP surface

`internal/delivery/webhook/httpapi` is not mounted by the runtime. It injects:

- `PrincipalResolver` for the trusted tenant and actor;
- `Authorizer.CanReplayWebhooks`;
- `KeyReady(keyID) bool`.

`GET /v1/webhooks/replay-candidates` accepts `limit` (default 100, 1-500) and optional repeated
`delivery_id` filters. It fetches at most 5,000 candidates, applies `SelectReplay`, and returns only
selected delivery/event/endpoint IDs and fixed skip reasons. A batch over the cap returns 409
`replay_cap_exceeded`; the operator must narrow the filter or limit.

`POST /v1/webhooks/replays` accepts `replay_id`, `delivery_id` and `reason`, builds the replay
request from the trusted principal (never from the body), validates it and calls the audited
`AuthorizeReplay` path. Responses carry only the replay/delivery IDs, prior state/attempts,
authorization time and created flag.

Both routes set no-store and restrictive security headers. Errors use fixed problem codes and never
echo database detail, URLs, payloads or receiver responses.

## Verification

Handler tests cover eligible/skip selection, delivery-ID filtering, key-readiness failure, cap
overflow, invalid queries, authentication/authorization, trusted-principal request construction,
domain-error mapping and malformed/unknown-field bodies. PostgreSQL coverage seeds failed and
exhausted deliveries and checks candidate state, attempts, replay flag, endpoint status, key
reference, limit bounds and capability denial.

## Limits

No production identity/session adapter or route mounting is provided. There is no UI template,
batch replay execution, new replay semantics or key provider. The API must not be exposed until K0
identity and network policy are qualified.

# K2.6 Temporal workflow history and rollout evidence

## Compatibility contract

The deployed Temporal surfaces remain unchanged: workflow type `SupplierCaseWorkflowV1`, queue `keel-supplier-case-v1`, workflow ID prefix `keel.supplier-case.v1.`, signal `supplier-case-event-v1`, and state query `supplier-case-state-v1`. A pure test pins these names. This phase adds no workflow command, timer, activity, or state transition; it qualifies the existing metadata projection and sets a measured history budget before any future command changes.

The workflow receives only case/event identity and digest metadata. PostgreSQL remains authoritative for case state and the 72-hour deadline. V1 has no timers or activities, so elapsed wall time alone does not add Temporal history or decide expiry.

## History measurement and replay

Contract CI run [#101](https://github.com/sanskarpan/Keel/actions/runs/37263643335) used the pinned Temporal 1.29.7 service. The stress test sent all 138 allowed envelope identities with all 12 dispatch attempts per identity, for 1,656 signal calls. The recorded history contained 6,622 events and 1,146,147 serialized protobuf bytes (approximately 1.09 MiB). Keel's ceilings are strictly below 9,000 events and 8 MiB, leaving measured headroom; Continue-As-New is not needed at the current event/attempt bounds.

The test replayed pinned-service history snapshots at event versions 102, 135, and 138. It shifted every archived event timestamp by 72 hours and replayed again successfully, then stopped/restarted the worker against the still-running Temporal service and verified the live workflow resumed at version 138. GitHub Actions run #101 also passed the full contract checks, disposable PostgreSQL migrations/integration, Kafka/scanner setup, race check, and build.

The 138-event stress sequence is an upper-bound transport fixture, not a valid supplier-case state sequence. PostgreSQL enforces legal case transitions. The timestamp shift checks that V1 replay does not depend on absolute wall-clock time; it does not simulate a 72-hour service outage, and the service itself was not restarted. Real-duration staging and service-restart evidence remain part of the K2 gate.

## Rollout, rollback, and limits

Changes that only add metadata event identities preserve V1 workflow commands and replay order. Future deterministic command/timer/activity or state-semantics changes require a stable `workflow.GetVersion` marker with retained old/new branches, or a separately versioned workflow contract when histories cannot safely share a type. Keep compatible workers for every open execution. Roll back only while the target build can replay all recorded markers and event types; otherwise pause dispatch and roll forward with a compatible fix. Never edit workflow histories or delete durable intents.

No Continue-As-New or migration was introduced. Any future increase to event or dispatch-attempt bounds must rerun the pinned-service measurement and stay under both internal ceilings. Temporal hosting, worker identity, retention, alerting, paging, and accountable runtime ownership remain unqualified; the workflow is not mounted for customer traffic. The accelerated replay is not hosted-service or production-readiness evidence.

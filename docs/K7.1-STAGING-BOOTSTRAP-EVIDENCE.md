# K7.1 slice: Supabase staging bootstrap

Related to #52 (K7.1 partial; does not close it). This slice stands up the designated
Supabase staging database and records the two managed-Postgres behaviours that differ from
the local Compose profile. No production qualification is claimed.

## Contract

- `deploy/modal/staging-roles.sql.template` mirrors the reviewed local role bootstrap for a
  managed database: the same abstract capability roles, schemas, helper function and RLS
  probe, but no local-synthetic logins. Staging logins
  (`keel_staging_operator`/`_webhook`/`_migrator`) take passwords substituted at apply time
  from environment variables and are never committed.
- The managed `postgres` login is not a superuser, so the template avoids `ALTER ROLE`
  attribute changes (roles are created with final attributes) and grants the two owner
  roles back to the bootstrap login after creating them so `SET ROLE` works for owned DDL.
- Applied and verified 2026-11-01 against Supabase Postgres 17.11 (pgvector 0.8.2):
  `vector` extension installed, all 62 migrations applied, 93 `keel_meta` tables and 129
  functions present, and the migrator login resolves to `keel_staging_migrator` through the
  pooler.

## Managed-Postgres findings

- The pooler requires the project ref in the username (`role.<project-ref>`); a bare role
  name fails with `ENOIDENTIFIER no tenant identifier provided`.
- Session-mode pooling (port 5432) is required for role bootstrap and migrations: the
  runner pins one connection and relies on session semantics for `SET ROLE` and the
  session advisory lock. Transaction-mode (port 6543) is appropriate for runtime roles,
  whose capability functions are transaction-scoped.
- The direct database host is IPv6-only; the pooler is the IPv4 path.

## Limits

No Modal deployment is claimed here (see the scaffold evidence), no production region,
backup/PITR, failover or capacity qualification, and no customer data. Staging credentials
live only in the gitignored `.env` and in Modal secrets.

## Verification

- Bootstrap dry run (rolled back) then committed apply; migration bundle applied through
  the staging migrator login; state verified by a read-only query.
- Secrets created with `modal secret create` and verified by name/key listing.

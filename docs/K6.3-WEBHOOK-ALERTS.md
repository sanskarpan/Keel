# K6.3 webhook worker alerts and dashboard contract

This document defines the source-controlled local Prometheus rules and the dashboard queries for
the content-free `webhook-worker` series. It is not a deployed alerting or Grafana configuration.

## Local profile

1. Start the local stack and migrations with `make local-webhook-worker`; the worker management
   endpoint listens on `127.0.0.1:18082`.
2. On Linux Docker Engine, start the optional monitoring profile with `make local-monitoring-up`.
3. Open `http://127.0.0.1:19090/targets` to confirm the `keel-webhook-worker` scrape and
   `http://127.0.0.1:19090/alerts` to inspect local alert state.

The worker egress policy still rejects loopback/private receivers, so the local profile cannot
exercise a real delivery. It exercises discovery, leases, breaker deferrals, outcomes and alert
evaluation only.

## Alert rules

`deploy/monitoring/prometheus/keel-webhook-worker-alerts.yaml`:

| Alert | Condition | Severity | Meaning |
| --- | --- | --- | --- |
| `KeelWebhookWorkerDown` | `up{job="keel-webhook-worker"} == 0` for 30s | critical | Management target unreachable |
| `KeelWebhookDiscoveryStale` | last successful discovery older than 180s for 30s | critical | Scheduler cannot discover work |
| `KeelWebhookDiscoveryErrors` | discovery errors increased in 5m | warning | Discovery failures; backlog gauges are stale |
| `KeelWebhookTenantErrors` | tenant errors increased in 5m | warning | One or more tenant batches failed |
| `KeelWebhookDueBacklog` | more than 1,000 due deliveries for 5m | warning | Worker-visible fanout backlog |
| `KeelWebhookOldestDueAge` | oldest due age over 1h for 5m | warning | Work is aging beyond the retry target |
| `KeelWebhookExhaustion` | exhausted outcomes increased in 15m | warning | Terminal delivery failures need review/replay |
| `KeelWebhookStalledAttempts` | no attempts in 10m while due deliveries > 0, for 5m | warning | Worker may be stuck or fully deferred |

Thresholds are local starting points, not production SLOs. The rules use only fixed series and
outcome labels; they never carry tenant, endpoint, event, delivery, URL, payload or error strings.

## Dashboard queries

- **Target health:** `up{job="keel-webhook-worker"}`
- **Due tenants:** `keel_webhook_due_tenants`
- **Due deliveries:** `keel_webhook_due_deliveries`
- **Oldest due age:** `keel_webhook_oldest_due_age_seconds`
- **Last discovery age:** `time() - keel_webhook_last_discovery_timestamp_seconds`
- **Discovery failures:** `increase(keel_webhook_discovery_errors_total[5m])`
- **Tenant failures:** `increase(keel_webhook_tenant_errors_total[5m])`
- **Attempts started:** `sum(rate(keel_webhook_attempts_started_total[5m]))`
- **Outcome rates:** `sum by (outcome) (rate(keel_webhook_outcomes_total[5m]))`
- **Exhaustion count:** `increase(keel_webhook_outcomes_total{outcome="exhausted"}[1h])`

Panels must not add tenant or endpoint labels. A growing due backlog with a healthy discovery
timestamp points at worker/receiver capacity; a stale discovery timestamp points at the scheduler
or database; rising tenant errors point at database/lease failures.

## Limits

No Alertmanager, notification delivery, paging ownership, Grafana JSON, hosted monitoring, SLO
burn-rate qualification or production deployment is included. The local rules were validated with
the pinned Prometheus tooling and Compose config, not against a live receiver or deployed
monitoring stack.

# K3.6 implementation evidence (in progress)

This slice qualifies correctness and records a bounded synthetic workload for the PostgreSQL lexical path. It does not establish retrieval relevance, production capacity, or a production latency objective.

## Implemented checks

- `TestPostgreSQLLexicalPlanUsesPostingTermIdentity` builds 2,000 chunks with one unique marker per chunk, runs `ANALYZE`, and captures `EXPLAIN (FORMAT JSON)` for a selective tenant/cohort/build/term query inside the configured non-owner app-role connection and scope. The test requires the planner to use `retrieval_term_postings_pkey`.
- `TestPostgreSQLBM25MatchesIndependentReferenceAcrossLengthsAndFrequencies` compares exact scores and ordering with a separately calculated BM25 reference over documents with differing lengths and term frequencies.
- `TestPostgreSQLTenantVisibilityScopedLexicalPublication` exercises an eligible posting count greater than the configured query budget and verifies that `ErrPostingBudgetExceeded` is returned with no partial candidates or posting count.
- `BenchmarkPostgreSQLSearchScoresTenantSkew` creates independent 100- and 5,000-chunk cohorts. Every chunk contains `common`; each also contains a unique marker. It checks one-result rare-marker recall@5, then measures the common-term query while checking candidate count and posting rows. The verbose benchmark records PostgreSQL server version, cohort size, common posting count, rare recall, p50/p95 query latency, allocations, and the benchmark's standard ns/op/B/op/allocs/op metrics.

The benchmark is invoked in the contract workflow after the standard integration check against the pinned disposable `pgvector/pgvector:0.8.7-pg18-bookworm` service. Benchmark records are scoped to that CI run and corpus shape. They must not be represented as production SLOs or a capacity claim. CI evidence for the merged PR and exact final head will be added here after the workflow passes.

## Query-plan interpretation and limits

The posting primary key starts with tenant, build, and term identity, matching the selective posting lookup. `EXPLAIN` confirms that the test fixture's planner uses that index after statistics are refreshed; it does not prove efficient plans for every corpus distribution, query length, tenant size, visibility policy, or PostgreSQL version. The fixed test's 2,000-chunk shape is deliberately small enough for routine CI.

`SearchScores` bounds query terms, top-k, and total posting rows; the hard global ceiling is `MaxQueryPostingRows` (100,000). A request over its caller-supplied budget reads at most budget plus one rows and fails closed without returning a partial ranking. This bounds work by rows returned to the scorer, but does not bound all database CPU, buffer reads, lock wait, or time spent by an unfavorable plan. An extremely common term can therefore be rejected at the posting budget rather than ranked. No frequency-aware planner, timeout policy, adaptive budget, or resource-class admission control is established by this slice.

The fixture validates synthetic rare-term recall exactly (one expected match in top five) and verifies tenant/cohort isolation in the existing PostgreSQL integration contract. It is not a representative customer query set and does not establish human relevance, no-answer quality, recall at production scale, or behavior under simultaneous tenants and concurrent ingestion.

## Reproduction and cleanup

From the repository root, against a fresh disposable database with migrations and test roles installed:

```sh
KEEL_TEST_DATABASE_URL='postgres://<app-user>:<password>@127.0.0.1:5432/<disposable-db>?sslmode=disable' \
KEEL_TEST_RETRIEVAL_INDEXER_DATABASE_URL='postgres://<indexer-user>:<password>@127.0.0.1:5432/<disposable-db>?sslmode=disable' \
GOTOOLCHAIN=local go test -run '^$' -bench '^BenchmarkPostgreSQLSearchScoresTenantSkew$' -benchtime=100x -benchmem -v ./internal/retrieval/postgres
```

For the plan, BM25, and posting-budget assertions, run the package integration tests with the repository's normal disposable PostgreSQL fixture and admin DSN configured, for example `go test ./internal/retrieval/postgres -run 'TestPostgreSQL(LexicalPlanUsesPostingTermIdentity|BM25MatchesIndependentReferenceAcrossLengthsAndFrequencies|TenantVisibilityScopedLexicalPublication)$'`. The SQL-plan fixture requires the test admin DSN used by `retrievalTestDBsWithAdmin`.

The benchmark creates random tenant, cohort, build, and source IDs. It intentionally does not delete indexed rows: test data and migrations must only run in an isolated disposable database, which should be destroyed after the run. Never run this command against a shared or production database.

## Measurements still required before production use

Run the same query paths with representative, privacy-approved corpora at expected and peak tenant sizes, including Zipfian/common-term distributions, cohort skew, multi-term queries, long documents, concurrent readers/writers, cache-cold and cache-warm runs, and realistic storage/network placement. Record query-plan changes, p50/p95/p99, database CPU and I/O, buffer/cache hit rates, lock waits, memory, pool saturation, rejection rates, and recall/precision against a labeled evaluation set. Establish per-tenant fairness and timeout/admission policies, a reviewed capacity envelope, and operational alerts before claiming production readiness.

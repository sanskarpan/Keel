# K5.3.6 Database statement telemetry

Issue [#320](https://github.com/sanskarpan/Keel/issues/320) extends the bounded observer contract from [K5.3.5](K5.3-REPOSITORY-TELEMETRY.md) to the database statements the order repository executes.

## Event contract

Instrumented statements are reported as `query.read` and `query.write`. Outcomes are fixed to `ok` and `error`. A statement that returned no row is a statement that succeeded, so it is reported as `ok`; only a statement failure is reported as `error`. Elapsed time is capped at one hour. A trace ID is reported only after strict W3C traceparent parsing of the trusted server correlation context, so an untrusted or absent context produces no trace ID.

The logger observer writes only operation, outcome, `duration_ms`, and an optional `trace_id`. Envelope schema and relay retry fields stay restricted to the messaging operations, so statement events never carry `schema_version` or `retry_count`.

## Mechanism

`internal/platform/observability` owns a statement recorder that classifies a statement, bounds its duration, and buffers the resulting event. The recorder is bound to the operation context, so a statement helper can find it without threading a new parameter through every repository function. `internal/platform/dbquery` provides the statement helpers: `Read`, `ReadRow`, `Write`, and `WriteRow`. They wrap `database/sql` and add no retry, timeout, statement rewriting, or error translation, so a statement that succeeds through the helper succeeds in the database and a statement that fails through the helper fails the same way.

Each instrumented repository operation starts one recorder. Statement timings are buffered while the transaction runs and are published only after the transaction has finished, so observation never extends a transaction or holds database locks open. The repository operation event is published after the buffered statements.

## Privacy boundary

The recorder accepts only a statement class, an elapsed duration, and the statement error. It has no parameter for statement text, arguments, rows, identifiers, or result contents, so those values cannot reach an event even by accident: the statement helpers read the statement text to execute it and then drop it. A failure is reported as the fixed `error` outcome with no error text, so constraint names, connection strings, and row data cannot reach the log pipeline. Statement events carry no tenant, order, event, aggregate, idempotency, or principal values.

Custom observers must remain non-blocking; observer panics are recovered and cannot alter a returned value, an error, a transaction, an RLS decision, an authorization result, an idempotency outcome, or an ordering guarantee.

## Operational use

Operators can separate slow database work from upstream request or broker time by grouping statement events on operation and comparing bounded read and write durations, and can count statement failures independently of the operation that raised them. These records do not identify an individual statement, prove a query plan, or replace canonical database health checks and the restricted diagnostics described in the order relay runbook. Because the observer is optional and wired per repository instance, an absent observer means the runtime did not configure one; that is not by itself an incident.

## Limits

This is a structured log/observer hook only. It is not a SQL span, a query-plan record, a Prometheus series, an exporter, an application runtime, or end-to-end distributed tracing. It reports statement classes rather than statement identities, so a slow statement cannot be named from this signal alone; naming statements would require a reviewed allowlist of statement names and is not part of this slice. A multi-row read is timed until its first row is returned, so row iteration time is not included in a read duration. Coverage is limited to the instrumented order repository operations: the order command path, the order and state-feed read path, and the outbox repair path. The relay, projector, supplier, retrieval, and AI packages, and the worker prune paths, report no statement events. It configures no per-tenant metrics, no Temporal, model, provider, or delivery spans, and no retention or egress policy. Any future exporter or runtime wiring requires its own issue, privacy review, and deployment qualification. The existing RLS, authorization, idempotency, and ordering behavior is unchanged.

## Validation

- Unit tests cover read and write classification, rejection of an unregistered statement class, the missing-row outcome, the failed-statement outcome, validated trace-present and trace-absent behaviour, the per-operation statement bound, single publication on flush, the nil-observer default, observer failure isolation, and the recorder context round trip.
- Real-PostgreSQL integration tests cover the statement helpers directly: read and write classification, a failing statement reported as an error, a missing row reported as a successful statement, an event free of statement content and messaging-only fields, and the no-recorder default.
- Real-PostgreSQL integration in the order repository covers a create reporting write statements and a load reporting read statements under the least-privilege `keel_local_app` role with forced tenant RLS.

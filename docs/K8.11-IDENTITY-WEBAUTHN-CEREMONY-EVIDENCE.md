# K8.11 slice 6: WebAuthn ceremonies over the stored challenges

Related to #70 (K8.11 partial; does not close it). Storage proved the state
machine; this slice proves the cryptography: registration and authentication
ceremonies verified with `go-webauthn/webauthn` v0.18.2 against the
database-backed single-use challenges, served on four unmounted routes. No
route is mounted and no production RP identity is provisioned.

## Contract

- Dependency: `github.com/go-webauthn/webauthn v0.18.2` pinned in
  `go.mod`/`go.sum` (transitives only; testify/objx bumps ride along).
- `internal/auth/httpapi/webauthn.go` (enabled via `EnableWebAuthn`
  with a deploy-time `WebAuthnConfig{RPDisplayName,RPID,RPOrigins}`;
  without it the ceremony routes answer `501`):
  - `POST /v1/auth/webauthn/registration/options` (Bearer session):
    resolves and validates the session, excludes existing keys,
    `BeginRegistration`, records the library challenge (5 min) and
    returns the creation options with `X-Challenge-ID`.
  - `POST /v1/auth/webauthn/registration/verify?challenge_id=`
    (body is the raw attestation response): consumes first (ready or
    `409`/`410`/`404`), enforces registration purpose and session
    ownership (`403`), verifies attestation with the library (`400` on
    failure), validates id/key/transports defensively, then stores:
    `201 {credential_id}`, `409 credential_conflict`,
    `403` for inactive principals.
  - `POST /v1/auth/webauthn/authentication/options` `{email}`: unknown,
    non-active or keyless principals all resolve to `404 not_found`
    (the ceremony inherently names its user; documented limit).
  - `POST /v1/auth/webauthn/authentication/verify?challenge_id=`:
    consumes first, checks purpose, throttle pre-check (`429` +
    `Retry-After`), verifies the assertion, then
    `advanced→reset-throttle→mint 24 h session (201)`,
    `cloned→record failure + 403 credential_cloned`,
    library failure→record failure (`429` if that locked, else `401`).
  - Sessions are reconstructed from the consumed nonce plus principal
    bytes and the library default credential parameters; RP identity
    comes only from server config, never the request.
- Migration `0071_identity_webauthn_direct_store`:
  `store_identity_webauthn_credential` plus the guard relaxed for
  inserts only (a ceremony may open with a nonzero counter).
- `internal/auth/postgres.StoreWebAuthnCredential` with outcome
  mapping; the `httpapi.Repository` interface grows the five ceremony
  reads plus store (the atomic register path stays store-tested).

## Verified

- `go vet ./internal/auth/...` and `gofmt` clean;
  `go test ./internal/auth/...` pass, including 7 WebAuthn handler
  groups: 501 without config, config rejection, session/consume/
  purpose/ownership mappings, options uniformity, a real-crypto
  counterless replay failing `403 credential_cloned`, and a real fmt=none
  registration storing once then `409` on reuse — all against fakes
  except the library, which verifies real ECDSA.
- A synthetic P-256 `fmt=none` authenticator (CBOR attestation,
  ASN.1 assertions, in-process JSON transport) drives the live test.
- In-container against real capability roles:
  `--- PASS: TestHTTPWebAuthnCeremonyAgainstPostgres` — register
  options 200, attestation verify `201` with echoed key id, same key
  re-registration `409`, assertion options 200, assertion verify `201`
  with a resolving valid session, regressed counter `403`.
  Store-level outcomes (`principal_inactive`, `stored`,
  `credential_reuse`) pass in `TestPostgreSQLIdentityWebAuthn`.
- Two live-caught integration bugs fixed pre-commit: the reconstructed
  session omitted credential parameters (library: credential algorithm
  unsupported — fixed by carrying `CredentialParametersDefault`) and
  migration `0071` was built but never applied (store 500 — ledger now
  records `0071`).

## Limits

- No routes mounted; RP identity is test-only (`example.test`) and no
  production RP/origin is provisioned.
- Assertion options enumerate key ownership by email (`404` shape);
  password login stays fully non-enumerating.
- No credential deletion/rename, no per-credential policy, no UV-level
  policy, no discoverable-credential (passkey autofill) flow, no audit.
  Attestation trust (MDS/metadata) is not evaluated — `fmt=none`
  self-assertion only, matching the local-synthetic profile.

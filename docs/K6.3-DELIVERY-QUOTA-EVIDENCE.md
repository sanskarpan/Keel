# K6.3 slice: per-tenant delivery batch quota

Issue #407 (parent #48, checklist item K6.3). This slice adds a per-tenant per-pass delivery
lease ceiling so one tenant's backlog cannot monopolize a worker pass.

## Contract

- Migration `0057` adds `webhook_tenant_delivery_policies` (limit 1-100) and append-only
  `webhook_tenant_delivery_policy_history`, both behind forced RLS with direct runtime access
  revoked, plus an immutable-history trigger.
- `keel_operator`-gated `set_webhook_delivery_batch_limit` creates (expected version 0) or
  updates (exact version match) one tenant's limit with a per-tenant advisory lock, a bounded
  operator principal and a 1-512 byte non-control reason. Duplicate change IDs, existing-policy
  recreates and stale versions fail; history rows are immutable.
- `keel_meta.webhook_delivery_batch_limit` returns the configured limit or the default 5.
- Tenant discovery is re-created with `r_batch_limit`; the scheduler leases at most
  `min(process batch, tenant limit)` per tenant per pass. A zero limit from older fixtures means
  the process default. Deliveries above the ceiling stay due for a later pass; nothing is dropped.
- Go adds `MaxDeliveryBatchLimit = 100`, `DefaultDeliveryBatchLimit = 5`,
  `DeliveryBatchChange`/`DeliveryBatchPolicy`, `Store.SetDeliveryBatchLimit` with conflict
  mapping, `DueTenant.BatchLimit` with source validation, and the scheduler clamp.

## Limits

No global due-backlog cap, attempt quota, fair-share ordering, HTTP/UI, billing integration or
automatic over-cap remediation. Raising a tenant limit above the process batch has no effect until
the process batch is raised. Database audit tables remain authoritative.

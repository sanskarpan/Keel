# K3.5 cache and queued-work safety contract

Status: **disabled pending authorization-version and runtime qualification**.

## Current system boundary

Keel does not mount a retrieval content cache or an asynchronous retrieval/reranking work queue. Search and citation resolution use live PostgreSQL authorization checks. Source eligibility is scoped by tenant, visibility cohort, and immutable document version. Withdrawal advances a sticky eligibility generation. Lexical/vector publication locks the source eligibility rows and rejects a withdrawn or stale source version.

The supplier workflow uses Temporal for unrelated supplier-case projections; it is not a retrieval cache or a retrieval indexing/reranking queue. Do not treat the presence of Temporal in the repository as evidence that retrieval work is queued.

Per-user ACL generations and their trusted identity provider are not implemented (#138). Cache or queued retrieval features must remain disabled until that authority, provider ownership, and runtime activation gates are satisfied. The current withdrawal generation is not a substitute for a future per-user ACL generation.

## Cache contract required before activation

A cache entry is a candidate optimization, never an authorization decision. Any future cache key must include, at minimum:

- tenant ID;
- visibility cohort key;
- immutable source document version ID;
- source eligibility generation;
- authoritative per-user ACL generation;
- retrieval corpus/build generation and any model/reranker version affecting the result.

Values must preserve the source identities and immutable citation references used to form the result. Before returning a hit, the caller must verify current tenant/cohort membership, source eligibility, ACL generation, and citation authorization against their authoritative stores. Missing, stale, or unavailable authority means the hit is discarded and the request fails closed; a cache hit must never bypass live authorization.

No cache can be enabled with missing authorization generations. When enabled in the future, entries must have a hard maximum 30-second TTL, and generation mismatch must make an entry unreachable immediately even if asynchronous eviction has not run. TTL limits data residency; it is not an authorization mechanism. Invalidation must be tenant/cohort scoped, bounded, idempotent, and observable. An invalidation backlog beyond its configured budget disables cache reads/writes for the affected scope and raises an alert. Cache contents must not be logged.

## Queued-work contract required before activation

Every future indexing, embedding, or reranking work item must carry tenant ID, visibility cohort, source document version ID, source eligibility generation, authoritative ACL generation where user access affects the work, and an idempotency key. The worker must revalidate all applicable generations before reading source content, before external provider calls, before writing derived output, and before publication or returning a result.

Cancellation is best effort only. Correctness comes from generation checks and the existing database publication fence. A stale task may not publish, overwrite a newer generation, or return a citation. Retry and replay must preserve the original scoped identity and cannot silently bind to a newer source generation.

## Activation gates and qualification

Keep cache and retrieval queue adapters unconfigured until all of these are complete:

1. K0/K3.5 names the identity and ACL authority and provides monotonically increasing per-user ACL generations (#138).
2. The runtime has explicit cache/queue provider ownership, credentials, isolation boundaries, and fail-closed configuration.
3. Tenant/cohort crossing, withdrawal during work, ACL revocation during work, stale worker replay, generation mismatch, and invalidation-backlog tests pass against real PostgreSQL and the selected providers.
4. Metrics and alerts cover stale-hit rejection, invalidation lag/backlog, stale work rejection, and retry/poison outcomes.
5. A rollout and rollback plan keeps the feature off by default and can disable it without deleting authoritative source state.

## Evidence and limits

Current evidence is the live source-eligibility filtering and repeatable-read fences, citation revalidation, and stale-publication PostgreSQL tests documented in [K3.5 implementation evidence](K3.5-EVIDENCE.md). These checks qualify the synchronous retrieval path only. They do not qualify a cache, a per-user ACL provider, or an asynchronous retrieval worker. There is no cache or retrieval queue to revoke today, and no product behavior should infer that future cached or queued data is already covered.

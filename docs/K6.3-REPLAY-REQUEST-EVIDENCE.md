# K6.3 slice: manual replay request ledger

Issue #360 (parent #48, checklist item K6.3). PR #361; merge SHA and contract CI are recorded by the
evidence update after merge. This slice makes a manual replay request durable before any replay is
executed: one immutable, tenant-scoped record per delivery with the operator identity, a bounded
reason and a caller-supplied replay ID. It does not select, authorize, transition or execute a
replay.

## Record

Migration `0044` adds `keel_meta.webhook_replays`:

| Column | Rule |
| --- | --- |
| `tenant_id` | Non-zero tenant; part of the primary key and the delivery foreign key |
| `replay_id` | Caller-supplied idempotency identity, 8-64 `[A-Za-z0-9_-]` |
| `delivery_id` | 8-64 `[A-Za-z0-9_-]`; unique per tenant, so one delivery has at most one replay request |
| `requested_by` | Operator principal, 1-128 `[A-Za-z0-9_.:@-]`, never a secret |
| `reason` | 1-512 bytes, no leading/trailing whitespace and no control bytes |
| `requested_at` | Database clock |

The row references `keel_meta.webhook_deliveries` with `ON DELETE` default (restrict), is forced
through RLS with only a schema-owner policy, and has all direct privileges revoked from every
runtime role, including the operator and webhook roles. A guard trigger refuses every update and
delete, so the request is an append-only audit record. No URL, key, signature, payload or receiver
data is stored.

## Capability and idempotency

`record_webhook_replay(replay_id, delivery_id, requested_by, reason)` is a `SECURITY DEFINER`
function gated on membership in `keel_operator`. It derives the tenant from
`keel_private.current_tenant_id()` and never accepts a tenant argument.

- An exact retry of the same replay ID with the same delivery, actor and reason returns the stored
  row with `created=false`, so a retried operator call does not duplicate the request.
- Reusing a replay ID with any different field raises a conflict instead of returning or
  overwriting the stored request.
- A different replay ID for a delivery that already has a request raises `already replayed`; the
  unique `(tenant, delivery_id)` constraint is the final guard.
- A missing delivery fails through the foreign key; a cross-tenant delivery cannot be claimed
  because the insert uses the authorized tenant.

`webhook_replay_recorded(delivery_id)` exposes the tenant-scoped existence check to the same
operator capability. Direct selects are not granted, so the predicate used by replay selection
stays behind the capability boundary.

## Go surface

`webhook.ReplayRequest` validates the tenant, both identities, the audit actor and the reason with
the same bounds as the database and reports only `ErrInvalidReplay` for invalid input.
`postgres.Store.RecordReplay` validates before opening a tenant transaction, maps the two recorded
conflicts to `webhook.ErrReplayConflict`, and returns the stored record with UTC time.
`postgres.Store.ReplayRecorded` returns the capability-scoped existence bit. Both run through the
shared tenant transaction helper, which sets `keel.tenant_id` locally and never trusts a
caller-supplied tenant inside SQL.

## Coverage

Unit tests cover valid requests and each rejected field (identity shape, actor, empty/oversized/
whitespace/control reason, zero or malformed tenant). PostgreSQL tests cover creation and round-trip
fields, exact-retry idempotency, replay-ID reuse with a different delivery/actor/reason, a second
replay ID for the same delivery, recorded/not-recorded lookups, tenant isolation, direct update and
delete refusal, and denial for the application and webhook capabilities.

## What is still missing

Selection still runs in memory over caller-supplied candidates. There is no operator HTTP route,
authentication/authorization beyond the database capability, replay state transition, execution
attempt, audit export, metric or UI. The worker must not replay a delivery until an audited
transition and execution path exist.

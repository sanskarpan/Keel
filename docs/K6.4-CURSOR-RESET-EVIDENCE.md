# K6.4 slice: audited reconciliation cursor reset

Issue #385 (parent #49, checklist item K6.4). PR #386 merged as
`54a956add6dd0c0e4d9057d2a44d7727c0b425da`; contract CI #627 passed on reviewed head
`431328ef4e38aa82de191ae3f90965c03cb47518`. This slice lets an operator rewind a tenant
reconciliation cursor to a bounded past time, with an append-only audit row and no delivery or
history mutation.

## Durable model

Migration `0053_webhook_reconciliation_cursor_reset` adds append-only
`webhook_reconciliation_cursor_resets` with the tenant, reset ID, operator principal, prior/new
cursor watermark, bounded non-control reason and database time. The table is forced through RLS,
exposes only a schema-owner policy, and grants no direct access to any runtime role, including
`keel_operator`. Reset rows cannot be updated or deleted.

The cursor guard now permits a backward cursor move only when a reset row exists whose prior and new
watermarks exactly match the update. A normal update that moves backward without that audited row is
rejected; deletes remain rejected and forward moves remain valid.

## Reset path

`keel_meta.reset_webhook_reconciliation_cursor(reset_id,requested_by,to,reason)`:

- Requires membership in `keel_operator` and derives the tenant from
  `keel_private.current_tenant_id()`.
- Validates a bounded reset ID, audit actor, target time, reason length and control characters.
- Rejects a future target time and a target at or after the current cursor.
- Requires an existing cursor and refuses a duplicate reset ID.
- Serializes per tenant with a transaction advisory lock and locks the cursor row.
- Appends the prior/new watermark and reason, then moves the cursor to `(target time, zero UUID)`.
- Returns the prior/new watermark only; it exposes no endpoint, URL, payload, delivery or receiver
  data.

The Go `CursorResetRequest` validates the same fields and `postgres.Store.ResetReconciliationCursor`
maps duplicate resets to `ErrReconciliationConflict` and missing/invalid/backward targets to
`ErrInvalidReconciliation`.

## Semantics

The next planner run rescans outbox events after the reset watermark. Reset does not change
reconciliation run/gap history, deliveries, delivery state or cursor generation; there is no
automatic rescan, scheduler integration, delete, or forward jump. The operator must supply a reason
and a distinct reset ID for every rewind.

## Verification

Coverage runs against a fresh PostgreSQL database with migrations through `0053`:

- a plan advances the cursor, then an audited reset moves it back to the requested watermark;
- the reset audit records the prior/new watermark, actor and reason;
- the next plan rescans the same events and advances the cursor again;
- duplicate reset IDs conflict;
- a reset with no cursor and a future reset are rejected;
- application and webhook roles cannot execute reset; the operator cannot read the reset table
  directly; reset rows are immutable;
- an un-audited backward cursor update is rejected by the guard;
- request validation covers tenant, reset ID, actor, target time and reason.

Linux CI covers the race detector.

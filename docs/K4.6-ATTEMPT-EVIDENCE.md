# K4.6 provider-attempt policy and ledger evidence

## Delivered scope

Issue #194 adds content-free attempt planning and fallback rules beneath parent issue #36. `internal/ai/attempt` does not make network calls and does not claim that a provider outcome or charge is verified. A future dispatcher must persist the attempt and liability before provider send and must pass only verified provider outcomes into this policy.

Each planned attempt binds tenant, inference, distinct attempt ID and ordinal, active policy digest, provider/model capability digest, and a maximum liability. Capability digest includes provider/version/model, immutable adapter artifact digest, idempotency support, and the bounded per-attempt liability. A fallback must be pinned before dispatch and its maximum allowance must already fit inside the inference reservation.

The planner allows only primary attempt ordinal 1 plus one preplanned fallback ordinal 2. It will create the fallback only after a primary outcome states rejected before acceptance, confirmed no charge, zero provider output, zero client-visible token bytes, and an explicitly retryable connect-before-send, rate-limited-rejected, or unavailable-rejected class. The active policy digest must still match and the deadline must remain live. Accepted, charged, ambiguous, timeout-after-send, any output/token, missing fallback capability, insufficient reserved allowance, or any second retry refuses fallback. Unknown acceptance/charge remains unknown; it is never converted into permission to retry.

When a capability declares idempotency support, each attempt gets a key derived with injected HMAC-SHA256 material from tenant, inference, unique attempt, and pinned capability. Distinct attempts receive distinct keys. A capability without idempotency support receives no fabricated key; its uncertain outcomes remain subject to the fail-closed rule. Outcome fingerprints contain only outcome metadata and support exact replay detection by a future ledger; changed facts conflict.

## Durable ledger slice (PR #264)

PR #264 closes subtask #263 with migration `0031_ai_provider_attempt_ledger`. When a `JobSpec` includes an `AttemptPlan`, `queue.Enqueue` persists its primary and optional single fallback capability snapshot in the same transaction as the K4.3 reservation and K4.4 queue job. The database binds tenant, inference, primary attempt, policy digest, reservation amount, and deadline. Plans store primary and fallback candidates as ordinals 1 and 2, along with content-free capability digests; outcome rows persist their attempt ordinal. The plan stores provider/model identity, provider version, artifact digest, idempotency support, and maximum per-attempt liability. Capability objects accept only those six fields.

The worker-only outcome function requires the current tenant, lease owner, and lease epoch. Evidence is append-only; exact concurrent replay succeeds without another row, while conflicting facts fail closed. A fallback outcome cannot be recorded unless its timestamp is later than the primary's `rejected_before_acceptance` outcome, which must have confirmed no charge, no output, no client-visible bytes, and one of the explicitly retryable failure classes. Outcome evidence itself does not settle or release budget liability, mutate the queue state, or authorize network dispatch. App SQL cannot write plans or outcomes directly; app access to plans is read-only, and worker access to outcomes is read-only outside the fenced function.

## Remaining parent issue gates

The durable ledger persists attempt plans and typed outcome evidence, but it does not couple individual provider charges to K4.3 settlement or authorize reservation release. No live provider adapter or network retry/streaming path exists, and provider-specific idempotency behavior is not qualified. Parent #36 remains open for atomic charge settlement/reconciliation coupling, the production K4.4 executor integration, operational metrics/runbooks, and end-to-end qualification that fallback is impossible after output or uncertain acceptance. These pieces together are not a production fallback runtime.

# K7.5 slice: local alert delivery without a paid paging service

Related to #56 (K7.5 partial; does not close it). Owner direction 2026-11-01 removed
PagerDuty on cost grounds and asked for the free alternative to actually be used, so the
Prometheus/Alertmanager stack now delivers to a real receiver instead of a dead
placeholder.

## Contract

- `deploy/monitoring/alert-sink/sink.py` is a small stdlib HTTP sink that accepts
  Alertmanager webhook POSTs on `/hooks/ops-alerts`, keeps the last 50 alerts
  (alert name, status, severity, start/end timestamps) and serves them at `/alerts` for
  verification. It records no tenant, endpoint, delivery, URL or error content, matching
  the content-free label contract of the alert rules.
- Compose runs the sink pinned (`python:3.12-alpine`) on loopback port 19095 under the
  `monitoring` profile, hardened (`read_only`, `cap_drop`, memory/PID/CPU limits).
- Alertmanager's critical and warning receivers both post to
  `http://127.0.0.1:19095/hooks/ops-alerts`; routing, grouping and WorkerDown inhibition
  are unchanged. Alertmanager's cluster port moved to 19096 because the sink owns 19095.

## Verified end to end

- `amtool check-config` passes; Compose monitoring config validates.
- With the profile running, `amtool alert add alertname=KeelWebhookWorkerDown
  severity=critical` reached the sink:
  `{"alertname":"KeelWebhookWorkerDown","status":"firing","severity":"critical",...}` and
  the sink logged `alert_received alertname=KeelWebhookWorkerDown status=firing
  severity=critical`.
- The test alert was then expired and the profile stopped.

## Limits

The sink is a local development receiver: it holds alerts in memory, has no
acknowledgement, escalation, deduplication or on-call rotation, and loses history on
restart. To use a real free service instead, change the two receiver URLs to that
service's incoming-webhook URL (Slack, Discord, or any HTTP endpoint) — nothing else in
the stack changes. The monitoring profile uses host networking, so it is Linux-Docker-Engine
oriented; on Docker Desktop for Windows the containers are reachable from inside the VM but
not from the Windows host loopback.

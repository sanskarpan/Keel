# K5.3.5 Order repository operation telemetry

Issue [#316](https://github.com/sanskarpan/Keel/issues/316) extends the bounded observer contract from [K5.3.4](K5.3-RELAY-TELEMETRY.md) to the top-level order PostgreSQL repository operations.

## Event contract

Instrumented operations are `order.create`, `order.submit`, `order.read`, `order.history`, `order.view`, `order.page`, `order.readpage`, `order.stream.snapshot`, `order.stream.updates`, `outbox.repair.list`, and `outbox.repair.apply`. Outcomes are fixed to `ok`, `not_found` (read operations only), and `error`. Each public repository operation is one timed unit; the observer runs after the transaction has finished rather than holding it open. Elapsed time is capped at one hour. A trace ID is reported only after strict W3C traceparent parsing of the trusted server correlation context, so untrusted or absent context produces no trace ID.

The logger observer writes only operation, outcome, `duration_ms`, and an optional `trace_id`. Envelope schema and relay retry fields are emitted only for the messaging operations from K5.3.4, so database events never carry `schema_version` or `retry_count`.

## Privacy boundary

Events never contain tenant, order, event, or aggregate identifiers; idempotency keys or principal bindings; SQL statements, argument values, or query plans; row contents; or raw database errors. A failure is reported as the fixed `error` outcome with no error text, so connection strings, constraint names, and row data cannot reach the log pipeline. Custom observers must remain non-blocking; observer panics are recovered and cannot alter a returned value, error, transaction, RLS decision, authorization result, idempotency outcome, or ordering guarantee.

## Operational use

Operators can separate slow order reads and writes from upstream request or broker time by grouping on operation and comparing bounded durations. These records do not prove a specific query plan, identify an individual order, or replace canonical database health checks and the restricted diagnostics described in the order relay runbook. Because the observer is optional and wired per repository instance, an absent observer means the runtime did not configure one; that is not by itself an incident.

## Limits

This is a structured log/observer hook only. It is not a SQL span, a query-plan record, a Prometheus series, an exporter, an application runtime, or end-to-end distributed tracing. It configures no per-tenant metrics, no Temporal, model, provider, or delivery spans, and no retention or egress policy. Any future exporter or runtime wiring requires its own issue, privacy review, and deployment qualification. The existing RLS, authorization, idempotency, and ordering behavior is unchanged.

## Validation

- Unit tests cover validated trace-present and trace-absent behavior, rejected remote trace context, `ok`/`error`/`not_found` outcome classification including a wrapped not-found error, absence of messaging-only fields, and identifier/raw-error exclusion.
- Observer failure isolation, the nil-observer default, and repositories built without the option are covered directly.
- PostgreSQL integration covers a real create, snapshot read, authoritative read view, and a missing-order read emitting the expected fixed operations and outcomes under the `keel_local_app` role with forced tenant RLS.
- Merge and contract-run evidence will be recorded in `docs/CHECKLIST.md` after the implementation PR is merged.

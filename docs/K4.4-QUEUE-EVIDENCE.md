# K4.4 durable AI queue evidence

## Scope in this slice

`internal/ai/queue` adds a tenant-scoped persistence boundary for admitted inference work. It does not call a model, run a worker loop, or store prompts or responses. A queue row must reference an existing K4.3 admission and its exact reserved budget attempt before PostgreSQL will accept it.

## Admission and execution bounds

- An installed `ai_execution_profiles` row supplies the policy digest, provider/model identity, queue-depth cap, concurrent-attempt cap, maximum output tokens, and absolute attempt duration. App and worker roles can read profiles but cannot create or change them.
- Enqueue takes tenant, inference, attempt, period, policy digest and principal binding from the K4.3 admission object; callers can supply only a provider/model route and output bound. The database trigger independently checks the principal hash against that immutable admission. No input text or user identifier is stored in queue/fairness rows.
- Queue admission runs inside the budget repository's reservation transaction. A disabled/missing profile, capacity failure, identity conflict or SQL error rolls back a newly created reservation together with the job. Replays verify that the existing job matches the same admission and route.
- One advisory transaction lock per tenant/provider/model serializes queue-cap admission and concurrency decisions. The database trigger takes the same lock, so direct SQL insert cannot bypass the queue-depth cap.
- Fairness is per verified principal within one tenant/provider/model, with separate fairness rows and service history for each route. Principals with no prior service sort before already served principals, and each claim updates a database timestamp and count. Jobs within a principal remain FIFO by availability and creation time. This is a deterministic round-robin approximation, not a weighted global scheduler.
- A worker claim uses `FOR UPDATE SKIP LOCKED`, increments the lease epoch and attempt count, and records both a short renewable lease and an immutable maximum attempt deadline. Only a separate `keel_ai_worker` role can change lease state; the app role cannot forge or complete claims.
- Renewal requires the exact tenant, inference, owner, epoch and a still-live lease. It can only move the lease forward and never past the profile's absolute attempt deadline. Workers must use that deadline as their provider-call context timeout and enforce the returned output-token cap at the adapter boundary.
- A live or unresolved attempt counts against the profile's concurrency cap. Expired leases are never silently reclaimed: a provider may have accepted and charged the request despite worker loss. This deliberately fails closed and can reduce available concurrency until a separately authorized reconciliation path is implemented.
- Claim rechecks the queued job's policy digest and output-token bound against the currently installed profile. If a control-plane change makes an old queued job incompatible, it stays unclaimable and retains its reservation until an authorized cancellation/reconciliation path is available; it cannot execute under changed limits.

## Verification

`queue_test.go` covers malformed tenant, inference, attempt, period, provider, model, principal, digest and output-token inputs. `queue_integration_test.go` uses distinct least-privilege app/worker connections plus the disposable CI database administrator to verify atomic budget reservation and enqueue, idempotent replay, principal fairness, provider concurrency limits, owner/epoch fencing, bounded renewal, app-role mutation denial and tenant isolation.

The complete migration chain applied successfully through `0025_ai_job_claims.up.sql` on a fresh, isolated PostgreSQL 18/pgvector container. The integration test passed using separate app and AI-worker database logins, and passed again under Go's race detector. The full `make check` suite and `git diff --check` also passed. The ephemeral database was isolated from the shared workspace database and is removed after verification. PR CI remains configured to repeat the migration and integration path on its disposable service.

## Remaining gates

This is not a provider executor. K4.4 still needs a lease-expiry reconciler coupled safely to K4.3 unknown-liability accounting, terminal settlement/release transactions, worker liveness/heartbeats, queue runtime assembly, starvation/load measurements, operational alarms and recovery runbooks. Provider-specific request shaping and proof that adapters enforce token/time caps also remain required before dispatch. Installed execution-profile ownership and version rollout are unassigned. No customer inference traffic is enabled by this migration.

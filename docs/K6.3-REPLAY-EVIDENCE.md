# K6.3 slice: capped webhook replay selection

Issue #347 (parent #48, checklist item K6.3). PR #348 merged as `dabd766de5aaaf197fa8c517cc05ac48273f6043`; contract CI #573 passed on reviewed head `f22f93d196c4188f04b8f7a28ba1a0d37219e0b8`. This slice adds the pure selection contract behind
manual replay: which failed deliveries may be replayed, in what batch size, and why a candidate is
refused. It does not persist replay records, authorize the operator, write an audit entry or run a
new attempt.

## Bounds

| Bound | Value | Behavior |
| --- | --- | --- |
| `MaxReplayBatch` | 500 | A request limit outside 1-500 is invalid |
| `MaxReplayCandidates` | 5000 | A larger candidate set is invalid before evaluation |
| Overshoot | none | More eligible deliveries than the limit fails the whole request with `ErrReplayTooLarge` |

The cap fails closed instead of truncating: an operator who selects 800 eligible deliveries gets no
selection and must narrow the batch. A truncated selection could silently leave failures behind
while reporting success, and the audit record would understate the request.

## Eligibility

A candidate is selected only when all of the following hold. `SelectReplay` evaluates candidates in
input order and preserves that order.

- The delivery identity satisfies the wire contract.
- The delivery state is `exhausted` or `failed`. `delivered` is reported separately; `pending`,
  `in_flight` and unknown states are not replayable.
- At least one attempt was recorded; a terminal row that never attempted is an inconsistency to
  investigate, not a replay.
- No earlier replay record exists for the delivery.
- The current endpoint registration is `active`, its subscription revision equals the delivery's
  subscription revision, and a signing key is ready.

The endpoint data is caller-supplied `EndpointEligibility`; the caller must resolve it from the live
registry and keyring, never from the replay request. The policy cannot detect a registry that lies,
so the operator surface must recheck immediately before execution as well.

## Skip reasons

| Reason | Meaning |
| --- | --- |
| `invalid_delivery` | Identity violates the wire contract |
| `already_delivered` | A receiver accepted the delivery |
| `not_replayable` | State is not a terminal failure |
| `no_attempts` | No attempt row exists |
| `already_replayed` | A replay record already exists |
| `endpoint_inactive` | Endpoint is disabled or unsubscribed |
| `endpoint_unknown` | Endpoint could not be resolved (fails closed) |
| `subscription_mismatch` | Delivery targets a stale subscription revision |
| `signature_unavailable` | No usable signing key is configured |
| `duplicate` | The same delivery ID appeared earlier in the request |

Skip reasons are stable, content-free values safe to show in an operator UI and to aggregate. They
carry no URL, secret, response body or receiver content.

## Deduplication

The first candidate for a delivery ID fixes that delivery's decision for the request, even when it
was refused. A later duplicate is reported as `duplicate` rather than re-evaluated, so a repeated
entry cannot bypass an ineligible verdict. An invalid identity is not registered as seen, so a
malformed entry does not block a valid delivery with the same ID.

## Relationship to execution

A selected delivery is not replayed by this slice. Execution would re-lease the delivery, produce a
fresh attempt ID/timestamp/signature through the K6.2 wire contract, and record an audited replay
before allowing a new attempt. The delivery and event IDs stay fixed. Today the state row is
terminal and immutable, so a later slice needs an explicit, audited transition (or a separate replay
record) before a replay can be leased; changing terminal state directly is refused by design.

## Coverage

Unit tests cover selection of exhausted and failed deliveries, ordering, every skip reason, the
first-decision-wins duplicate rule, the exact cap, rejection of an oversized limit or candidate set,
empty input and reason validity.

## Boundaries

No persistence, operator route/UI, authorization, audit record, rate limit per tenant, re-attempt
execution or metric. The policy also does not decide whether a receiver still wants the event after
a subscription change; it refuses stale revisions and leaves re-subscription to the endpoint
lifecycle. `K6.3` and parent #48 remain open.

# K5.3.3 — Order outbox trace correlation

## Contract

Order event schema v1 remains byte-compatible and contains no trace context. At the repository command boundary, caller-supplied event metadata is overwritten from the typed server correlation context; if that context is absent, traceparent is cleared. A validated W3C version 00 `traceparent` captured in the protected event metadata is written using envelope schema v2. V2 adds one required `traceparent` field, and is used only when that value is valid and present. Events without it continue to use v1.

The Kafka relay publishes the exact persisted envelope and, for v2 only, exactly one `traceparent` header. The projector accepts v1 without that header and v2 only when the envelope and single header values are identical and pass the strict shared parser. Unknown or duplicate headers, malformed values, unsupported versions, and mismatches are durably quarantined before projection changes. The inbox digest includes the canonical envelope including traceparent, so conflicting redeliveries cannot reuse an event ID silently.

The traceparent is correlation metadata. It does not participate in tenant derivation, authorization, partition keys, aggregate ordering, command idempotency, or event identity. V1 records remain readable. Retries and broker redeliveries load the same immutable envelope, preserving correlation exactly.

## Privacy and failure behavior

Protected order-event history remains the authoritative source. The public state feed and order API projections do not include trace IDs. Kafka payloads contain only the existing allowlisted order-event metadata plus the validated traceparent in v2; no baggage, request IDs, actor references, tenant/customer fields, or arbitrary attributes are added. The broker already carries the tenant and aggregate identifiers in the v1 envelope and partition key; trace context adds no new identity authority.

Malformed, duplicate, unsupported, or mismatched trace metadata makes that transport record invalid and follows existing digest-only quarantine behavior. Missing trace context remains a valid v1 event and does not affect business application. A valid v2 message creates a new local child span ID at the consumer boundary while preserving its trace ID, parent span ID, and flags. This context is available to downstream processing but does not by itself instrument database, Temporal, model, delivery, or provider operations.

No exporter is wired or enabled by this slice. It does not establish end-to-end distributed tracing, a production observability endpoint, or a retention policy. Any downstream exporter remains subject to separate provider, identity, egress, access, retention, and deletion qualification.

## Verification

- Unit tests cover v1 compatibility, v2 canonical digest, exact header agreement, malformed/missing/duplicate/mismatched context, and child-context creation.
- PostgreSQL integration tests cover persistence of the exact traceparent in the v2 outbox envelope, exclusion from state-feed data, canonical projection matching, and repair validation against immutable event history.
- Kafka integration tests cover the v2 header on the exact retried envelope while keeping the tenant/aggregate partition key stable; v1 publication has no trace header.
- Contract CI and merge evidence are recorded in `docs/CHECKLIST.md` when this slice is merged.

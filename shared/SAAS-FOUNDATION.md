# SaaS foundation for Keel and Ghostlight

Revision 2, 4 October 2026. This is a common behavioral specification, implemented separately in each product. It does not introduce a third deployable project, shared customer database, shared subscription, or coupled release train. The original 15 topics are a minimum learning/proof set, not a product feature limit.

## 1. Customer and organization lifecycle

Organization states: `provisioning -> trial -> active -> restricted -> closing -> closed`; an organization can recover from restricted after reconciliation. Subscription states are separate provider observations, not the organization state machine. Region selection and terms/privacy acceptance happen before any customer document or repository secret is ingested. Organization creation is idempotent, reserves trial capacity, creates an initial owner, and records policy versions. Provisioning failures expose a retryable operation; they never create duplicate billable organizations.

A person may belong to multiple organizations, but every request selects one authorized organization. Switching changes cursors, caches, stream subscriptions and UI state; it cannot reuse grants from the previous organization. Keel organization ID is its tenant ID. Ghostlight organization owns projects, repositories, environments, templates, cloud connections and evidence. Platform support is a distinct role and never becomes a customer owner by default.

First-party identity bootstrap, sign-in, verified email, session lifecycle/revocation, owner MFA, recovery and lockout are launch-critical product capabilities; a tenant cannot be created by an untrusted or unauthenticated caller. Email/passwordless or OIDC onboarding uses a qualified identity provider, verified email, bot/rate protection and required MFA for owners/billing/security administrators. Enterprise federation/SCIM follows in 2.0. Domain verification proves domain control, not permission to steal an existing organization or merge users automatically. Invitations bind organization, intended principal, role, inviter and expiry; accept under current policy, hash tokens, invalidate revoked tokens. Owner transfer is a two-party verified operation and cannot leave zero active owners.

Trial defaults proposed for qualification: 14 days, synthetic guided sample mode, low resource/AI caps, one trial per verified commercial identity unless reviewed. Samples are labeled and can be removed without deleting real customer data. Trial abuse controls use only documented, proportionate signals needed to prevent resource abuse; do not fingerprint customer documents, source repositories, payment contents or private prompts. Minimize signal collection, restrict access, delete raw risk signals within 30 days unless a documented legal/security hold applies, and expose an appeal with accountable human review and a reversible override. No silent permanent denial based solely on an opaque score. No unbounded free cloud or provider spend. A workspace setup checklist resumes across sessions and hides tasks completed by another administrator.

## 2. Authorization and identity lifecycle

Roles are capability bundles. Server enforcement combines current membership, resource visibility, project/business-unit scope, sensitive-action strength, subscription entitlement and safety policy. A subscription entitlement never grants an RBAC permission. All billing and API mutations are audited. API keys belong to an organization plus service principal, have explicit scopes/expiry, are displayed once, hashed at rest and revocable. Human offboarding revokes sessions, personal keys and pending invitations; service-owned connector credentials require transfer/rotation rather than silent deletion.

Membership revision increments on changes. Critical commands always consult current grants; ordinary-read caches have <=60s bounds and invalidation. Active streams/download grants expire and reauthorize at bounded intervals; disabling a user cuts new access within a <=60s qualification target, while bytes already delivered cannot be retracted. SCIM disable blocks automatic JIT reactivation; late directory events use provider version/current-state fetch and cannot resurrect a suspended principal. Last-owner deprovisioning escalates to a configured recovery contact, never silently skips the security action.

Enterprise SSO enforcement has a tested, customer-visible recovery process using separately protected break-glass identities. Support sessions require a purpose, time bound, explicit organization scope, customer consent where required, and immutable access records. Support impersonation never supplies arbitrary customer API credentials or bypasses business approvals.

## 3. Subscription, entitlements and product meters

Plan names are design proposals: Starter, Team and Enterprise. Pricing amounts require customer interviews, measured service costs and margin tests. Launch can sell a single Team plan; no need to ship three commercial plans before the product works. Safety controls, isolation, privacy export/deletion and verified cleanup exist in every plan. Enterprise adds administrative controls and qualified infrastructure options, not basic security.

Keel meters: active internal licensed users, contracted supplier/workflow allowance, retained storage and qualified AI/OCR usage. External supplier participants are excluded from internal seats to reduce collaboration friction. Ghostlight meters: contracted concurrency, active environment compute duration by published profile, retained storage, separately priced experiment capacity and approved live-provider usage. Review-only guests do not consume developer seats by default. Plan implementation defines exact counting, deduplication, proration and retention windows before paid launch. Supplier participation and reviewer guest policy must resist invite-based bypass of employee licensing.

Four money concepts stay distinct: customer procurement commitments; customer AI safety budgets; SaaS subscription/invoice amounts; Ghostlight infrastructure reservations/cost attribution. They have separate ledgers and currency/unit types. Never treat approved order value or a forecasted cloud invoice as subscription revenue. Hosted subscription checkout/invoicing uses a qualified payment processor; neither product holds card numbers or creates customer bank-transfer workflows.

Billing event ingestion verifies exact signatures, records provider event ID/hash and acknowledges a durable inbox. Event ordering is not authoritative: fetch/reconcile current subscription/invoice state and compare provider revision where available. Checkout return URLs cannot grant a plan. Store organization-to-customer mapping under trusted control; user metadata cannot claim another organization. Entitlement snapshots contain plan version, purchased add-ons, effective interval and revision; server-side admission reads the current revision. Short-lived caches cannot extend expensive creation when state is unknown.

The usage ledger records immutable meter observations keyed by organization, logical operation, meter and interval. Daily reconciliation against application/resource sources detects gaps and double counts. Invoice adjustments append corrections with provenance; previously invoiced observations are not rewritten. Display estimated, finalized, credited and disputed amounts separately. Do not silently rebill duplicate retries or invent credits from uncertain provider outcomes.

Trial expiry, cancellation, downgrade and nonpayment do not erase customer evidence or disable emergency safety actions. A proposed seven-day dunning/grace window is configurable and disclosed. Restrictions stop new costly work; allow login, billing repair, exports, authorized decisions needed to safely close existing workflows, incident aborts, credential revocation and verified teardown. Ghostlight can drain expired paid resources after notices and bounded contractual grace. Keel does not turn overdue subscription payment into automatic rejection of a purchase approval. Retained data still has a priced/contracted limit.

Downgrade is scheduled at period end or explicitly agreed; evaluate resources exceeding the new envelope and show remediation before acceptance. Grandfather existing committed approval/workflow semantics, but new work uses effective entitlements. Entitlement changes never change immutable recipe, evidence or policy digests silently. Cancellation requests have durable status and clear access/data-retention dates. Disputed billing does not permit new uncapped external spend.

## 4. Collaboration and notifications

Comments are scoped to resources, use sanitized Markdown with attachment restrictions, and maintain edited/deleted history according to retention policy. Resolve every mention against current membership and resource visibility. An external supplier/reviewer sees only explicitly shared threads; hidden comments cannot leak via counts, search snippets, notification subjects or export manifests. Business approval cannot be completed by posting a comment or reacting to a message.

Notification intent is committed with the underlying business event. A deduplicated delivery worker supports in-app and email at 1.0; Slack/Teams follow after connector qualification. Templates contain safe summaries and authenticated deep links, not supplier documents, secrets, signed cloud state or sensitive prompts. User preference, timezone, quiet hours and digest settings control noncritical reminders; required security/billing notices have documented exceptions. Notification delivery state never controls business state.

Delivery retries reuse logical notification IDs. Daily recipient/channel caps and digest coalescing prevent storms. Unsubscribe tokens alter only an allowed preference, not organizational policy. Chat interactive actions require exact signature, nonce/expiry, principal mapping and reauthorization; default chat messages direct users to the authenticated product for approvals. SMTP/chat outage leaves durable in-app work visible.

## 5. Trustworthy console and customer operations

Customer console includes overview, personal tasks, organization switching, search/navigation, product resources, integrations, usage/billing, members/security, audit and help. Every async operation has status/progress and retry guidance. Empty, loading, partial, permission-denied, expired-link, offline, quota and reconciliation states are designed; no fabricated success toast before commit. Destructive actions show affected scope and retain durable operation references.

Responsive browser experience and WCAG 2.2 AA are release targets: keyboard navigation, visible focus, labeled controls, live updates that do not steal focus, reduced motion, sufficient contrast, screen-reader progress and accessible tables/charts. Critical actions work on a narrow viewport. Browser/UI availability is measured separately from backend success. Internationalized messages, timezone display and localized currency formatting are foundations; qualified translated interfaces and language-specific search are later deliverables.

Support includes onboarding guidance, searchable documentation, ticket/contact channel, public status page containing no private identifiers, incident communications, maintenance notices and a feedback/roadmap mechanism. A customer-visible integration health page shows last success, lag, auth expiry and recovery actions. No full support portal platform must be built internally; integrate qualified services behind privacy controls. Product analytics use event allowlists, consent where required, bounded retention and organization context; no prompt bodies or supplier text in session replay.

## 6. Import, export, privacy and offboarding

Imports use bounded CSV/API batches, field mapping, dry-run validation, external-key deduplication, per-row outcomes and resumable jobs. Neutralize spreadsheet formulas in exports. Data portability includes machine-readable records, immutable version IDs, attachments allowed by visibility, audit references and a checksum manifest. Prepare exports asynchronously with per-org concurrency/storage quotas; signed downloads expire and current permission is rechecked. Export delivery email contains no bearer credential in an unsafe redirect.

Before live customer-data launch, counsel and accountable product/security owners review applicable jurisdictions and approve terms, privacy notice, data-processing agreement, subprocessor disclosures, breach-response procedure, rights-request handling and retention/deletion statements. This is a scoped launch gate, not a universal legal-compliance claim.

Closure requires current owner/privacy authority, legal-hold checks, a disclosed recovery grace, connector revocation and a deletion manifest. Product-domain retention, contracted billing/audit retention and legal holds are separate. No immediate deletion promise for regulated accounting records/backups. Verify all object versions, caches/indexes and exported bundles; apply erasure journal after recovery. Ghostlight closes only after environment access is revoked and native resources are absent or explicitly unresolved; subscription closure cannot hide a resource leak.

## 7. Foundation persistence and APIs

Each product owns `organizations/tenants`, `principals`, `memberships`, `invites`, `service_principals`, `api_keys`, `identity_connections`, `directory_events`, `plan_versions`, `subscriptions`, `billing_event_inbox`, `entitlement_snapshots`, `meter_events`, `invoice_observations`, `notification_intents`, `notification_deliveries`, `comments`, `imports`, `exports`, `privacy_jobs`, `support_grants` and `product_feedback`. Organization keys participate in tenant-owned unique/FK scopes and RLS. Platform-wide catalog/price/provider registries use explicitly separate platform roles, not customer-set context.

Common API family, refined by project OpenAPI: organization creation/settings; invitations/members/service principals; trial/checkout/customer-portal operations; subscription/entitlement/meter reads; notification preferences/inbox; resource comments; import dry-run/commit; export/closure/privacy jobs. Billing webhook is a signature-authenticated provider endpoint, never an ordinary tenant-write route. Portal URLs are created server-side for the trusted organization-to-customer mapping, short-lived and allowlisted.

SaaS foundation modules live within the existing modular backend; billing, notification and lifecycle jobs use durable queues and scoped process identities. Product billing credentials are separate from customer integration/provider credentials. Commercial restrictions are enforced at every admission path, including workflow schedules, API keys, CLI and internal automation. Shared code reuse does not imply a shared deployment dependency.

## 8. Release evidence

Before paid 1.0: end-to-end signup-to-value, membership revocation, hostile org-switch tests, real hosted checkout sandbox, duplicate/reordered subscription events, cancellation/dunning/downgrade tests, usage reconciliation, accessible core journeys, notification privacy, bounded import/export, support access and deletion/cleanup drills. Before enterprise 2.0: actual IdP SSO/SCIM, offboarding races, scoped audit export, infrastructure/residency qualification and contractual support readiness. No compliance badge is inferred from architecture documentation.
